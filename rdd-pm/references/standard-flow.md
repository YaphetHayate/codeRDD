# 复杂需求标准流程

以下流程适用于复杂度判定为"标准流程"的需求。若为快速通道需求，请加载 `fast-track.md`。

PM 的判断力（何时守门员/教练/顾问、如何提问、何时拆分）→ 加载 `pm-judgment-guide.md`。

---

## 第一步：场景识别

根据 SKILL.md 中的场景路由表判断场景类型，加载对应对话策略：
- 探索型 → `exploration-strategy.md`
- Bug 修复 → `execution-strategy.md#bug-修复`
- 迭代计划 → `execution-strategy.md#迭代计划`
- 技术优化 → `execution-strategy.md#技术优化`
- 文档补充 → `execution-strategy.md#文档补充`

若无法判断，直接问用户："你这个需求更偏向探索讨论，还是已经有明确的改动方向？"

---

## 第二步：场景对话

按加载的策略文件执行对话。不同场景的对话方式差异很大，严格遵循策略文件中的角色定位和流程指引。

**说明**：策略文件中的"对话结束"或"归档"标记意为**本阶段对话完成，返回本流程的第三步**。实际的归档操作（创建文件夹、写入文件）在第五步统一执行。

---

## 第三步：收敛总结

按 `overview-template.md` 和 `requirement-item-template.md` 中的模板格式整理需求清单草稿，呈现给用户确认。

用户确认后，检查需求是否足够清晰：

**硬性标准（不过关不能继续）：**
1. 每个需求是否有可检验的验收标准？
2. 如果有多个需求，它们之间是否有明确的边界？只有一个需求时跳过此项

**提醒项（缺失不卡流程，但应标注让后续环节注意）：**
3. 影响范围是否已识别？
4. 异常和边界情况是否考虑过？
5. 是否混入了实现细节？

硬性标准未通过 → **回到第二步**继续讨论。

---

## 第四步：需求评估

按 `evaluation-guide.md` 中的评估指南，从合理性、必要性、价值三个维度审视需求是否值得投入。

将评估结论呈现给用户。如果结论为负面，不要阻止用户推进，而是诚实说明判断依据，给出"继续归档"或"回到讨论"两个选项。

**用户选择"回到讨论" → 回到第二步**。最终决定权始终在用户手上。

---

## 第五步：归档并引导下一步

> **重要：本步骤是退出 PM 模式的硬性前置条件。只要本次会话讨论过需求，必须完成归档后才能响应任何模式切换请求。**

1. 在 `.rdd/changes/archive/` 下创建 `日期-需求简称` 文件夹（如 `2026-04-26-addUserRole`）
2. 按第三步确认的内容生成 `overview.md`（按 `overview-template.md` 模板）
3. 为每个需求生成独立文件（按 `requirement-item-template.md` 模板），文件名由 PM 确定的简短主题名词命名
4. 按 `task-template.md` 中的格式生成 `task.md`，填写需求文件和设计文件关联（含"角色参与计划"表）
5. **确认归档完成**后，执行分流：
   - **告知归档位置**
   - **前端/视觉需求检测**：需求涉及页面设计、UI、交互体验、视觉优化、前端界面时 → 建议启动 **/RDD-UX**（UX 设计师模式）
   - **UX 与 CTO 关系**：前后端设计不耦合时可同时启动 UX 和 CTO 并行；有耦合时建议先 CTO 后 UX
   - **建议路径**：涉及多模块/架构变更/技术选型 → 建议 CTO；涉及前端视觉/交互 → 建议 UX；其余情况建议 DEV 直接开发
   - **QA 并行判断**：验收标准具体可检验、用户场景明确时，可询问是否同时启动 QA
   - **用户确认后自动流转**：输出模式切换声明 → 通过 skill 工具加载目标模式 → 如需 QA 并行则通过 Task 工具启动
   - **用户拒绝则手动引导**：告知用户可输入 `/RDD-CTO`、`/RDD-UX` 或 `/RDD-DEV`

如果用户的问题还需要继续讨论，不要急着推进到归档。
