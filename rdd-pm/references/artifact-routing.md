# 产物路由规则

> PM 专属：归档时如何为每个需求文档设置路由目标，以及被打回后如何响应。

---

## 路由判定规则

归档时，为每个需求文档设置 `## 流转控制 > 当前责任人`，按以下优先级判定：

### 1. 简单需求 → DEV

以下全部满足时，直接路由到 DEV：
- 范围明确，仅涉及单一模块/功能
- 无架构影响，不涉及技术选型或模块间重构
- 不涉及前端页面/UI/交互体验设计

### 2. 复杂需求 → CTO

任一满足时，路由到 CTO：
- 涉及多模块、架构变更、技术选型
- 需要跨模块协调或数据模型变更
- 用户不确定技术方案的可行性
- 需要引入新框架/中间件/库

### 3. 前端/视觉需求 → UX

需求涉及以下任一项时，路由到 UX：
- 新页面设计
- UI 组件开发
- 交互体验优化
- 视觉风格变更

### 4. 复合需求 → 串行路由

需求同时涉及技术和视觉时：
- 前后端耦合 → 先 CTO 后 UX（CTO 设计完成后将当前责任人改为 UX）
- 前后端独立 → CTO 和 UX 可并行处理（PM 归档时两个需求文档分别路由到 CTO 和 UX，或在 task.json 中标注建议并行）

---

## 被打回后的响应流程

当 PM 产出的需求文档被下游角色通过驳回协议打回时：

### 1. 发现被打回

- 扫描 task.json 路由（`rdd-flow show -Role PM`），找到 `currentOwners` 含 PM 的任务
- 读取对应需求文档的 `## 驳回记录` 章节，了解驳回原因

### 2. 修订需求

- 使用 `/session` 回溯到原需求讨论的上下文
- 根据驳回理由修改需求文档
- 如果驳回被接受：清空驳回记录（状态改为「已驳回」），旧文档标为 deprecated，基于修订后内容新建需求文档
- 如果驳回不被接受：在驳回记录中填写辩解，状态改为「待裁决」

### 3. 重新路由

- 修订完成后，重新按路由判定规则设置 `currentOwners`（调用 `rdd-flow set-route`）
- 告知用户修订内容和新的路由去向
