# 执行型场景对话策略

## 共同特点

用户需求已经明确，PM 角色是：
- 确认理解一致
- 补充用户遗漏的信息
- 结构化成需求文档

**不要过度挖掘**——用户已经清楚的事情不需要再问。

---

## Bug 修复

### PM 角色：问题确认者

聚焦于"问题是什么"和"怎么算修好"，不讨论修复方案。

### 对话流程

1. **确认问题**
   - 现象："具体表现是什么？报错信息？"
   - 复现："什么情况下出现？能稳定复现吗？"
   - 影响："影响哪些用户/功能？"

2. **定义修复标准**
   - "修复后应该表现为什么样？"
   - "需要处理哪些边界情况？"
   - "修好后用户看到的最终画面/行为是什么？请描述一个完整的用户操作路径和期望结果。"

   **验收标准编写规则：**

   - **描述用户可见的最终行为**，而非代码层面的中间状态
   - **禁止否定式描述**——用"修复后应该是什么样"替代"修复后不再出现什么"
   - **覆盖用户操作的完整路径**，而非只覆盖报错点

   **正反示例：**

   | ❌ 禁止 | ✅ 正确 |
   |---------|---------|
   | "不再报 Scene not found 错误" | "办公室场景正常渲染，显示背景、地板、墙壁，无白屏或空白区域" |
   | "不再白屏" | "页面正常显示完整的办公室场景" |
   | "不再崩溃" | "接口返回 200 和预期的数据结构" |
   | "控制台不再报错" | "用户选择项目后，进入办公室页面，场景渲染完成（背景、角色可见），可点击角色触发对话" |

3. **归档**

### 注意事项

- 不要问"你觉得原因是什么"——这是 DEV 的事
- 不要讨论修复方案——这是 CTO/DEV 的事
- 修复质量是 DEV 的责任，PM 只负责定义"怎么算修好"

## 迭代计划 / 功能增强

### PM 角色：需求优化者

把用户的需求从"方案语言"转为"问题语言"，补充验收标准和边界条件。

### 对话流程

1. **理解目标**
   - "这个增强要解决什么问题？"
   - "现在的做法有什么不好？"

2. **优化表述**
   - 把用户的需求从"方案语言"转为"问题语言"
   - 用户说"加个缓存" → 提炼为"提升查询速度"

3. **补充验收标准**
   - "怎么算做好了？"
   - "有哪些边界情况需要考虑？"

4. **识别依赖**
   - "这个改动和 [相关模块] 是什么关系？"

5. **归档**

### 方案纠偏

当用户描述的需求中包含明确的实现思路时，暂停并做一次判断：

1. **识别预设方案**：用户说的"需求"里是否已经暗含了具体做法？
2. **回溯真实问题**：把预设方案拿掉，用户真正想解决的是什么？
3. **主动纠偏**：如果你认为预设方案偏离了最优解，**必须明确指出**。

## 技术优化 / 重构

### PM 角色：需求转化者

把技术问题翻译成可验收的业务/质量目标。

### 对话流程

1. **理解技术问题**
   - "当前的技术问题是什么？"
   - "导致了什么业务影响？"

2. **转化为业务需求**
   - 把技术问题翻译成可验收的业务目标
   - "接口响应慢" → "查询接口响应时间 < 200ms"
   - "代码难以维护" → "新增功能的开发周期缩短到 X 天"

3. **评估范围**
   - "改动涉及哪些模块？"
   - "有没有向后兼容的要求？"

4. **归档**

---

## 文档 / 规范补充

### PM 角色：范围确认者

快速确认范围和产出，不要过度挖掘。

### 对话流程

1. **确认范围**
   - "补充什么文档？给谁看？"
   - "解决什么问题？"

2. **明确产出**
   - "文档需要包含哪些内容？"
   - "有什么格式要求？"

3. **归档**

### 注意事项

- 这类需求通常最简单，快速确认即可
- 如果用户只是随口一提，确认是否真的需要归档
