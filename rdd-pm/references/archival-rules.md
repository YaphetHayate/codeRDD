# PM 归档与保真规则

在收敛总结和正式归档前读取。目标是在结构化需求时不丢失关键信息，也不把用户设想的实现方案误写成强制要求。

## 成熟度门禁

- L0 模糊想法：只输出探索结论，不生成正式需求和 task。
- L1 模糊问题：只输出问题定义草稿，不生成正式需求和 task。
- L2 明确需求：可以整理需求草稿，但必须补齐验收标准、边界和依赖后才能归档。
- L3 可归档需求：允许生成 `pm/overview.md`、独立需求文件和 `task.md`。

## 明确输入的保真规则

当用户输入已经很详细时，PM 需要先提取"不可丢失的信息点"：

```markdown
## 需求细节清单

- D1: [用户明确提到的目标/约束/场景/验收偏好]
- D2: ...
```

每个细节必须有去向：

- 写入某个需求项；
- 写入关键约束；
- 写入技术相关信息；
- 明确标注暂不纳入并说明原因。

## 覆盖率检查

归档前检查：

- 用户明确说出的目标是否都被覆盖；
- 用户明确说出的场景是否都被覆盖；
- 用户明确说出的约束是否都被覆盖或说明不纳入；
- 验收标准是否能验证这些目标；
- 被拆分后的需求是否仍保留原始意图；
- 是否存在被 PM 自行概括后丢失的细节。

如未通过，回到讨论或重新整理，不生成 `task.md`。

## 技术相关信息分类

技术相关内容不要简单删除，也不要直接变成实现要求。按以下类别记录：

```markdown
## 技术相关信息

### 已知事实
- [当前系统、代码、流程或工具的事实]

### 设计约束
- [必须遵守的兼容性、基础设施、性能、安全、部署或组织约束]

### 用户实现设想
- [用户提出的具体做法，作为 CTO 的参考输入，不作为强制方案]

### 留给 CTO/DEV 的实现决策
- [需要后续角色评估的技术选择]
```

判断规则：

- 如果是外部限制、业务规则、基础设施边界或兼容性要求，记录为**设计约束**。
- 如果是用户提出的具体实现做法，记录为**用户实现设想**，作为 CTO 的参考输入。
- 如果需要技术选型、架构权衡或代码实现判断，记录为**实现决策**，交给 CTO/DEV。

## Task 生成规则

`task.md` 只是需求项的跟踪索引，不替代 PM 需求文档。

- 每个 Task 必须引用一个 PM 需求文件。
- Task 标题可以简短，但细节必须保留在对应 PM 需求文件中。
- 禁止为了让 Task 清爽而删减需求中的场景、约束、验收标准或技术相关信息。
