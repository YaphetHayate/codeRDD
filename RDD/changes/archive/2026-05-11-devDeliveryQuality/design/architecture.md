## R2: CTO 自检框架补充前端集成维度

### 改动文件

`rdd-cto/references/self-check.md`

### 改动位置

Step 1 交互点识别（当前定义了 4 个维度），在"同一生命周期"之后追加 4 个前端维度。

### 新增内容

在 Step 1 的交互点定义列表中追加：

```
- **同一渲染管线** — 两个模块都参与了同一个视觉输出（DOM 更新、Canvas 绘制、SVG 渲染），或各自维护了独立的渲染路径但服务于同一个视觉区域。典型场景：A 有自己的 render()，B 有自己的渲染管线，两者画到同一个 canvas 但互不感知。
- **同一初始化时序** — 新设计依赖某个模块在特定时机之前完成注册/初始化。典型场景：模板注册依赖 Scene 已创建，但初始化顺序无法保证。
- **同一 UI 状态同步** — 同一逻辑状态被多个组件/模块分别持有，需要保持一致。典型场景：Camera 类和 Renderer.camera 各维护一份坐标。
- **同一事件流** — 同一个动作/变更通过事件机制通知多个订阅者，通知链路的完整性和顺序性需要保证。典型场景：Camera 坐标变更后需通知 Renderer 同步，但事件广播缺失或订阅时机不对。
```

### Step 2 推演问题对应新增

在 Step 2 的五个标准推演问题之后，补充前端维度的专项推演问题：

```
前端交互点推演时，额外询问：

- 渲染管线：管线的每一层是否都收到了它期望格式的数据？不存在 sprite/image 时是否有 fallback？两条渲染路径是否可能同时绘制到同一上下文导致闪烁或覆盖？
- 初始化时序：被依赖方是否一定在依赖方之前完成初始化？是否存在异步加载导致的时序竞争？
- UI 状态同步：多个持有者对同一状态的更新是否会冲突？更新是单向传播还是双向同步？一方更新后另一方是否能感知？
- 事件流：事件的发布者是否在订阅者完成注册之后才开始发送？是否有事件丢失的场景？事件处理是否可能引起循环触发？
```

### 示例案例

在 Step 2 之后、"Step 3 多策略一致性检查"之前，追加反例：

```
**反例：渲染管线断裂（codeRDD-plus-mimo 项目）**

┌──────────────────────────────────────────────────────────────────┐
│  交互点：Character 类 vs SceneManager/Renderer                   │
├──────────────────────────────────────────────────────────────────┤
│  Character 有自己的 render(ctx) 方法（含 fallback 蓝色矩形）        │
│  SceneManager 通过 _buildCharacterLayer() 提取 sprite/frame 数据  │
│  Renderer.drawCharacter() 在 sprite 为 null 时直接 return         │
│                                                                  │
│  推演：                                                          │
│  Q1: Renderer 收到的 sprite 数据格式是否正确？                      │
│      → ❌ Character.currentAnimation.spriteSheet 为空字符串        │
│      → 空字符串 || null → null → drawCharacter 直接 return        │
│  Q2: Character.render() 是否被调用？                               │
│      → ❌ 从未被调用，SceneManager 绕过了它                        │
│  结论：🔴 两条渲染管线完全断裂，需统一为一条                          │
└──────────────────────────────────────────────────────────────────┘
```

## R1: PM 提问目的性强化

### 改动文件

`rdd-pm/SKILL.md`

### 改动 1：核心原则新增条目

在核心原则的 "- **保持对话节奏**" 之后追加：

```
- **提问要有目的。** 每个问题都应该服务于帮用户弄清楚他自己还没想明白的事。如果用户对所有问题都有清晰答案，停止提问，开始整理。
```

### 改动 2：重写"提问技巧"章节

替换当前 "#### 提问技巧" 章节（从 "每次向用户提问时" 开始到 "而不是在抽象概念上做决定。" 结束），替换为：

```markdown
#### 提问原则

PM 向用户提问的唯一目的是帮用户发现自己没想清楚的事。如果用户对所有问题都有清晰答案，PM 的角色自动调整为记录员。

**三类有效提问**：

1. **挖掘隐含假设** — 用户说"加缓存"，背后假设的是"现在慢"，但慢在哪、慢到什么程度、是否真的需要缓存？PM 不知道答案，所以问。
2. **澄清真实痛点** — 用户描述的是"症状"（某个按钮不好用），但痛点可能是"病因"（整个流程设计不合理）。PM 需要通过追问找到根源。
3. **确认边界与约束** — 用户没提到的异常情况、极端场景、影响范围，PM 需要主动触碰。

**一条红线**：PM 自己能通过读代码、看现状、查文档得出结论的，不应转嫁给用户。比如"你希望用哪种缓存策略"这种问题，如果 PM 已经看到项目用了 Redis，就不该问——直接复用 Redis 是常识。

**不该问的**（反面示例）：
- "你想要方案 A 还是方案 B？" — 如果两个方案 PM 已经分析清楚了优劣，应该直接给出推荐和理由，而不是让用户在 PM 已有的分析基础上再做一次判断
- "交互方式你有什么偏好？" — 偏好不是需求，PM 应该根据用户场景推断最合适的交互方式

**该问的**（正面示例）：
- "你提到按钮不好用——是点下去没反应（延迟问题），还是点了之后结果不对（逻辑问题），还是根本找不到这个按钮（UI 布局问题）？" — 帮用户定位真正的痛点
- "这个功能在空数据时应该怎么展示？是完全隐藏，还是显示空状态提示？" — 确认用户没提过的边界情况
```

注意：替换后，原 "正面示例" 和 "反面示例" 子章节不再保留，新的内容已经内联了正反面示例。

### 改动 2：重定义"可运行性"为双层冒烟

将表格下方的原说明 "项目没有配置对应工具时，跳过该检查项。" 替换为：

```markdown
项目没有配置对应工具时，跳过该检查项。

#### 冒烟验证（双层）

冒烟验证分两层执行，分别对应不同的验证粒度：

**第一层：单任务冒烟（每个任务完成后）**
- 代码无语法错误、能通过编译/构建
- 新增的模块/函数能被正确导入/引用，不报运行时异常
- 不要求完整功能可用，只要求"不崩溃"

**第二层：整体冒烟（整体验证阶段）**
- 应用能正常启动（后端不崩溃、前端不白屏/不报 JS 错误）
- 至少一个核心用户场景能走通
- 已实现的功能没有被新改动破坏

冒烟验证不通过时：
- 单任务冒烟不通过 → 该任务不能标记完成，修复后重试
- 整体冒烟不通过 → 整体验证不通过，定位问题任务并修复

以下情况可跳过，但需在验证报告中说明原因：
- 项目是库/工具，无独立可启动入口（仅跳过第二层）
- 项目依赖外部服务且本地环境无法启动（仅跳过第二层）
- 本次改动仅涉及配置/文档/非运行时代码（两层均可跳过）
```
