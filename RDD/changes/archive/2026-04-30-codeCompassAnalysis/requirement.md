# code-compass 能力增强 — 函数级依赖分析与入口导航

## 背景

当前 code-compass 只有 `/map`（代码全景图）和 `/readme`（文档生成）两个功能。`/map` 生成的全景图以目录结构 + 文件描述为主，缺少函数级的依赖关系、调用链路和概念索引。当 AI Agent 需要在陌生项目中定位代码或评估改动影响时，仍然需要大量手动阅读代码，token 消耗高、效率低。

本需求旨在为 code-compass 新增函数级的依赖分析和入口导航能力，使 AI 能通过预先构建的结构化索引快速定位代码并评估影响范围。

## 需求列表

### 需求 1：模块化存储架构

- **描述**：将当前的单一 `map.md` 文件拆分为分层模块化存储结构，支持按模块独立读取和更新
- **验收标准**：
  - 生成结果存储在 `.code-compass/` 目录下，包含 manifest、overview、依赖关系、方法签名等分层文件
  - 每个源码文件对应独立的依赖关系数据和方法签名数据文件
  - AI Agent 可通过读取 manifest 获取全局索引，按需读取单个模块的详细数据
- **优先级**：高
- **影响范围**：`code-compass/references/map/map.md`（重写）、`code-compass/SKILL.md`
- **边界与异常**：需要兼容已有的 `.code-compass/` 目录（如已有旧版 map.md，需迁移或清理）

### 需求 2：函数级调用关系图

- **描述**：通过静态分析提取函数间的调用关系（二元关系：A 调用 B），存储为结构化数据，供 AI 按需沿链条跳转导航
- **验收标准**：
  - 对 Python、TypeScript/JavaScript 项目能提取函数级调用关系
  - 每个源码文件的调用关系独立存储为对应的数据文件
  - AI 可从任意函数出发，查询"谁调用了我"和"我调用了谁"
- **优先级**：高
- **影响范围**：`code-compass/references/map/map.md`
- **边界与异常**：
  - 动态调用（反射、`getattr`、回调等）无法静态分析，属于可接受的遗漏
  - 跨语言调用链（如前端 → 后端 API）不在本次范围内

### 需求 3：入口点识别与描述生成

- **描述**：自动识别项目中的入口点（API 路由、定时任务、CLI 命令），并为每个入口生成由 AI 读取调用链后产出的业务摘要描述
- **验收标准**：
  - 能识别 FastAPI/Flask 的路由装饰器作为 API 入口
  - 能识别常见的定时任务和 CLI 命令定义作为入口
  - 每个入口点包含：路径/名称、触发方式、AI 生成的业务摘要、直接调用的函数列表
  - AI Agent 扫描入口描述即可判断某个业务概念对应哪些入口和函数
- **优先级**：高
- **影响范围**：`code-compass/references/map/map.md`
- **用户场景**：AI 收到"修改员工雇佣逻辑"的需求，扫描入口描述找到 `POST /api/employees/hire — 雇佣新员工`，然后沿调用链定位到所有相关函数
- **边界与异常**：入口描述为 AI 生成，可能存在不准确，属于可接受的精度

### 需求 4：增量更新机制

- **描述**：支持基于文件变更检测的增量更新，避免每次都全量重建。关系数据实时更新，AI 生成的描述数据允许标记为 stale 后延迟刷新
- **验收标准**：
  - manifest 中记录每个源码文件的修改时间（mtime）或哈希值
  - 再次执行 `/map` 时，只对发生变化的文件重新执行静态分析
  - 关系数据（依赖、签名）在文件变化后立即更新
  - 入口描述在调用链中的任一函数变化后标记为 stale，不立即重新生成
  - 提供刷新 stale 描述的机制（使用时自动刷新或用户手动触发）
- **优先级**：高
- **依赖关系**：依赖需求 1（模块化存储）和需求 2（调用关系图）

## 关键约束

- 静态分析能力覆盖 Python、TypeScript/JavaScript（优先），Java、Go（后续扩展）
- 不依赖外部向量数据库或额外服务，所有数据存储为项目内的静态文件（JSON/Markdown）
- code-compass 本身是一个 AI Skill（Markdown 指令集），不具备独立运行能力，所有分析工作由执行该 Skill 的 AI Agent 完成

## 讨论记录

- 放弃向量数据库方案：构建和查询成本过高，AI Agent 已有 Grep/Read 工具，需要的是结构化索引而非搜索引擎
- 调用链选择二元关系存储（A 调用 B）而非预生成完整调用链：避免大项目中图的爆炸性增长，AI 按需跳转更灵活
- 概念索引融入入口描述而非独立维护：入口天然是业务概念的聚合点，减少维护成本
- 描述数据采用最终一致性：关系数据实时更新，AI 生成的描述允许 stale 标记后延迟刷新

## 评估结论

**推荐做。** 需求清晰、价值明确、技术上可行。CTO 需重点评估 Python 静态调用分析的可行性和精度——Python 的动态特性（装饰器、`getattr`、动态导入等）会导致较多盲区，需明确取舍边界。
