# PM 自动流转 + CTO 自动流转 — 设计文档

## 一、需求概述

PM 归档后和 CTO 归档后，不再让用户手动输入命令切换模式。改为询问确认后通过 `skill` 工具在当前对话中加载目标模式，实现无缝流转。

## 二、技术方案

### 2.1 自动流转统一模式

两个需求共享相同的流转模式：

```
1. 完成本阶段工作并归档
2. 呈现建议 + 理由，询问用户确认
3. 用户确认 →
   a. 输出模式切换声明（"XX 模式已结束"）
   b. 输出上下文传递信息（路径、状态、建议顺序）
   c. 调用 skill 工具加载目标模式
4. 用户拒绝 → 回退到手动引导
```

### 2.2 PM 归档后自动流转（需求 1）

#### 改动位置

`rdd-pm/SKILL.md` 第五步中的 4b 和 4e。

#### 4b 路径分流 — 改为询问确认

**现有行为**：直接给出建议，然后等用户手动输入命令。

**改为**：

```
归档完成后 → 给出建议路径 + 理由 → 询问用户确认 → 确认后 skill 工具加载
```

具体话术：

```
> 📋 PM 阶段已完成，需求已归档。
>
> 基于需求复杂度，建议进入 CTO 模式设计方案。理由：[涉及跨模块改动，建议先做方案设计]
>
> 是否进入 CTO 模式？（是 / 否，我自己选择）

用户："是"

> PM 模式工作已结束。正在切换到 CTO 模式...
>
> 上下文传递：
> - 归档路径：RDD/changes/archive/2026-05-01-xxx/
> - 需求概览：[简要列出 task.md 中的需求]
> - 共 X 个 task，CTO 状态均为 ⬜
>
> [调用 skill 工具加载 RDD-CTO]
```

#### 4d 并行 QA — 调整

保持现有 Task 子 agent 启动 QA 的机制不变。CTO/DEV 的启动从 Task 改为 skill 工具（因为需要交互）。

并行场景的话术：

```
> 部分需求可以直接生成测试用例，是否在后台同时启动 QA？
>
> 用户确认后：
> - QA → Task 子 agent 后台启动
> - CTO/DEV → skill 工具在当前对话加载
>
> 两者同时发起
```

#### 4e 用户拒绝 — 保留回退

用户说"否"时，保留现有的手动引导（显示可用命令），不变。

#### 模式切换声明

PM 加载新 skill 前，必须输出模式切换声明。格式固定：

```
> PM 模式工作已结束。正在切换到 [目标模式] 模式...
>
> 上下文传递：
> - [关键信息列表]
>
> [调用 skill 工具加载目标模式]
```

此声明的目的是：
1. 明确告知用户当前模式已切换
2. 将关键上下文以文字形式呈现，确保新加载的模式能立即获取
3. 在对话上下文中形成一个明确的分界线，新模式的规则从此处开始生效

### 2.3 CTO 归档后自动流转（需求 2）

#### 改动位置

`rdd-cto/SKILL.md` Phase 4 第 4 步。

#### 具体改动

**现有行为**：

```
> 方案已归档到 ...。接下来你可以：
> - 输入 /RDD-DEV 进入开发模式
> - 如果方案还有需要调整的地方，我们继续讨论
```

**改为**：

```
> 方案已归档到 RDD/changes/archive/.../design/
>
> 建议进入开发模式，基于设计方案开始实施。是否进入？（是 / 否）

用户："是"

> CTO 模式工作已结束。正在切换到 DEV 模式...
>
> 上下文传递：
> - 归档路径：RDD/changes/archive/2026-05-01-xxx/
> - 设计文档：[列出 design/ 下的文件]
> - 建议开发顺序：[从设计方案确认总览中提取]
> - task.md 状态：[哪些 CTO ✅，哪些 ⏭️]
>
> [调用 skill 工具加载 RDD-DEV]
```

用户拒绝时回退到：

```
> 接下来你可以：
> - 输入 /RDD-DEV 进入开发模式
> - 如果方案还有需要调整的地方，我们继续讨论
```

#### 同样使用模式切换声明

格式与 PM 一致：

```
> CTO 模式工作已结束。正在切换到 [目标模式] 模式...
>
> 上下文传递：
> - [关键信息列表]
>
> [调用 skill 工具加载目标模式]
```
