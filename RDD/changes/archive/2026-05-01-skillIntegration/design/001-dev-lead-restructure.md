# DEV 升级为开发主管 + DEV→QA 自动流转 — 设计文档

## 一、需求概述

将 DEV 模式从"纯执行者"升级为"开发主管"，负责阅读需求和设计文档、按职责拆分独立任务、协调子 agent 并行开发、审查产出质量。简单任务或强关联任务由 DEV 直接执行。全部开发完成后自动流转到 QA。

## 二、技术方案

### 2.1 核心改动范围

`rdd-dev/SKILL.md` 的以下章节需要修改：

| 章节 | 改动类型 | 说明 |
|------|----------|------|
| 核心原则 | 修改 | 增加"协调优先""质量把关"原则 |
| 模式边界 | 修改 | 增加任务拆分、子 agent 调度、代码审查职责 |
| 三种工作模式 | 增强 | 每种模式增加任务分析阶段 |
| 实现工作流 | 重构 | 拆为任务分析→执行→审查→整体验证→QA 流转 |
| 进度追踪 | 更新 | 支持并行任务追踪 |
| 新增：子 agent 调度规范 | 新增 | prompt 模板、文件冲突防护、结果处理 |

### 2.2 新 DEV 工作流全景

```
DEV 进入
  │
  ├── 输入处理（保持现有优先级 A-E，不变）
  │
  ├── 确定工作模式（设计引导/需求引导/直接开发，不变）
  │
  ├── [新增] 任务分析阶段
  │   │
  │   ├── 通读文档（设计文档/需求文档/用户指令）
  │   ├── 列出所有实现任务，标注文件范围和依赖关系
  │   ├── 检查文件冲突（同一并行组内不能有两个任务改同一文件）
  │   ├── 按职责拆分，分类：DEV 直接 / 子 agent
  │   ├── 呈现拆分计划表给用户确认
  │   └── 用户确认后进入执行
  │
  ├── [重构] 执行阶段
  │   │
  │   ├── 按并行组顺序执行
  │   │   │
  │   │   ├── DEV 直接任务：按原流程自己写
  │   │   │
  │   │   ├── 子 agent 任务：构造 prompt → Task 工具启动 → 等结果
  │   │   │   （同组内无依赖的子 agent 并行启动）
  │   │   │
  │   │   └── 本组全部完成后：DEV 审查子 agent 产出
  │   │       ├── 通过 → 进入下一组
  │   │       └── 有问题 → 整理后问用户，再决定下一轮
  │   │
  │   └── 所有并行组完成
  │
  ├── [重构] 整体验证
  │   ├── lint / typecheck
  │   ├── 测试
  │   ├── 构建
  │   └── 验收标准逐条检查
  │
  ├── 提交（保持现有逻辑，用户确认后）
  │
  └── [新增] QA 流转
      ├── 询问用户是否启动 QA
      ├── 确认 → Task 工具启动 QA 子 agent
      └── QA 完成 → 汇总结果呈现给用户
```

### 2.3 任务分类标准

| DEV 直接执行 | 子 agent 执行 |
|-------------|--------------|
| ≤2 个文件 | 3+ 个文件 |
| 目标明确无歧义 | 独立模块，边界清晰 |
| 与其他任务强关联（拆开会引入一致性风险） | 与其他任务无文件交叉 |
| | 有足够复杂度值得并行 |

### 2.4 任务拆分原则：按职责拆分

每个文件/模块只承担一个明确的职责。拆分维度：

- 数据层（数据库模型、Repository）
- 业务层（Service、核心逻辑）
- 接口层（Controller、API 路由）
- 工具函数（Utils、Helpers）
- 配置（Config、常量定义）

任务标注"涉及文件"列表，同一并行组内文件列表不能有交集。冲突时三种处理：

```
文件冲突处理：
  方案 A：将冲突任务合并为一个更大的任务
  方案 B：将冲突任务放入不同并行组（串行执行）
  方案 C：其中一个改为 DEV 直接执行
```

### 2.5 三种工作模式的任务分析

| 工作模式 | 任务分析阶段的输入 |
|---------|-----------------|
| 设计引导模式（有 CTO 设计） | DEV 读 design/*.md，将每个设计文档的实现步骤映射为实现任务 |
| 需求引导模式（只有需求文档） | DEV 读 requirement.md + 探索代码后自行制定实现计划，然后做任务拆分 |
| 直接开发模式（用户直接指令） | 指令明确、≤2 职责维度 → 直接做；3+ 职责维度或范围模糊 → 引导用户去 PM 模式 |

直接开发模式的分流：

```
用户指令
  │
  ├─ 目标明确、涉及 ≤2 个职责维度 → DEV 直接执行
  │
  └─ 涉及 3+ 个职责维度或范围模糊 → 引导用户：
     "这个指令涉及多个职责方向，建议先通过 PM 模式梳理清楚再开发。
      输入 /RDD-PM 进入需求讨论。"
```

### 2.6 子 agent 调度规范

#### Prompt 模板

DEV 为每个子 agent 构造的 prompt 固定结构：

```markdown
## 身份
你是一位拥有多年开发经验的工程师，擅长高质量代码实现。

## 任务信息
- 任务编号：T1
- 任务描述：[具体要实现什么，引用设计文档中的章节]
- 优先级：[高/中/低]

## 需求上下文
[相关 requirement.md 片段]

## 设计上下文（仅设计引导模式）
[相关 design/*.md 中的核心设计片段]

## 项目信息
- 技术栈：[框架、语言版本]
- 代码风格：[命名规范、缩进风格等关键约定]

## 实现指引
- 涉及文件：[具体文件路径列表，子 agent 唯一允许修改的范围]
- 参考实现：[项目中已有的类似功能，指出文件路径和函数名]
- 前置依赖：[前面任务已完成的产出，如新增的模型、接口等]

## 编码约束
- 单一职责：每个文件/模块只承担一个明确的职责（数据层、业务层、UI层、工具函数）
- 清晰可读：使用有意义的命名；关键逻辑注释说明"为什么"而非"做什么"
- 易扩展：面向接口/抽象编程；使用依赖注入或工厂模式解耦；对扩展开放，对修改封闭
- 遵循项目已有代码风格，新代码看起来应该像项目原有的代码

## 约束
- 只修改"涉及文件"中列出的文件
- 不引入新的外部依赖
- 遇到不确定的问题，在结果中说明，不要自行假设

## 输出要求
完成后汇报：
1. 修改了哪些文件，每个文件的改动摘要
2. 是否遇到问题或超出任务范围的调整
3. 建议的验证方式
```

#### 分层审查策略

| 任务复杂度 | 审查深度 |
|-----------|---------|
| 简单（≤2 文件） | lint + 快速扫描关键逻辑 |
| 标准（3-5 文件） | lint + 通读核心实现代码，检查是否符合设计意图 |
| 复杂（5+ 文件或关键路径） | lint + 完整 code review：逐文件检查实现质量、边界处理、与设计文档的一致性、与其他模块的兼容性 |

#### 结果处理策略

| 问题类型 | 处理方式 |
|---------|---------|
| 小偏差（风格、遗漏的边界处理） | DEV 直接修复，在汇报中说明 |
| 实现偏离设计 | DEV 评估影响，小偏离直接修，大偏离问用户 |
| 无法完成的任务 | 整理问题，问用户决策，按回答启动下一轮 |
| 文件范围越界 | 拒绝越界改动，重新执行该任务 |

### 2.8 QA 自动流转（需求 3 融入）

全部 task 开发完成并整体验证通过后：

```
> 所有开发任务已完成，验证通过。
>
> 是否启动 QA 进行测试验证？（是 / 否）
>
> 用户确认后：
> [通过 Task 工具启动 QA 子 agent，prompt 包含：
>   1. "加载 RDD-QA skill"
>   2. 归档路径
>   3. "基于 task.md 定位需求条目，执行 QA 流程"
> ]
>
> QA 子 agent 完成后，DEV 汇总结果：
> - 测试通过率
> - 失败用例列表
> - 建议后续操作
>
> 用户拒绝时：
> > 接下来你可以：
> > - 输入 /RDD-QA 手动启动测试
> > - 如果还有需要调整的地方，我们继续
```
