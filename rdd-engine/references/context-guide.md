# /context 指令执行指南

本文档详细说明 `/context` 指令的执行方式，供 rdd-engine 调用时参考。

## 采样策略

rdd-engine 不使用脚本建索引，直接通过 Glob/Grep/Read 采样代码。采样流程：

### 第一步：扫描目录结构

```
用 Glob 扫描项目顶层目录（1 层深度），排除标准噪声目录：
- node_modules, .git, dist, build, __pycache__, vendor
- .rdd, .claude, .vscode, .idea
- coverage, .nyc_output, .next, .nuxt
```

### 第二步：识别源码目录

```
按常见模式识别主要源码目录：
- src/, lib/, app/, cmd/, internal/, pkg/
- 如果项目根目录直接是源码（无 src/ 子目录），直接扫描根目录
- 忽略：tests/, test/, spec/, docs/, scripts/, assets/, static/
```

### 第三步：采样文件

```
每个源码目录采样 1-2 个文件：
- 优先采样：入口文件、配置文件、核心业务文件
- 采样依据：
  ├── 目录名 + 常见入口文件名（index.*, main.*, app.*）
  ├── 各目录下最大的源码文件（通常包含核心逻辑）
  └── 配置文件（如 config.*, settings.*）

总采样量控制：
├── 大项目（10+ 源码目录）：每目录 1 个，共 3-8 个
└── 小项目（< 10 源码目录）：每目录 1-2 个，共 3-8 个
```

### 第四步：生成文件 hash

```
对每个采样文件计算 MD5 hash，记录到 meta.json 的 file_hashes 字段。
用于后续新鲜度检测。

注意：hash 计算是轻量操作，只需读取文件内容即可。
不需要对整个项目做 hash，只 hash 采样的文件。
```

## 产物生成指南

### 生成 style.md 时的分析要点

从采样代码中提取以下信息：

1. **命名规范**：
   - 观察文件名、类名、函数名、变量名、常量名的命名模式
   - 判断：camelCase / PascalCase / snake_case / kebab-case
   - 找到主流模式，标注例外

2. **代码格式**：
   - 缩进：tabs 或 spaces，缩进大小
   - 引号：single / double / template literals
   - 分号：有 / 无
   - 尾逗号：有 / 无
   - 行宽：观察大多数行的长度

3. **项目特定约定**：
   - 错误处理模式（try-catch / Result 类型 / 错误码）
   - 日志方式
   - 状态管理模式
   - 依赖注入方式
   - 注释风格和密度

4. **风格不一致处**：
   - 如果发现主流风格之外的模式，记录偏离点
   - 标注偏离位置和主流风格，建议新建代码遵循主流

### 生成 structure.md 时的分析要点

1. **目录布局**：
   - 基于第一步的目录扫描结果
   - 去掉噪声目录，保留有意义的目录结构
   - 简要标注每个目录的推测职责

2. **模块职责**：
   - 基于目录名 + 采样文件内容推断每个模块的职责
   - 列出每个模块的关键文件

3. **模块依赖关系**：
   - 观察采样文件中的 import/require 语句
   - 推断模块间的调用关系
   - 如果发现循环依赖，标注为高严重程度代码质量问题

4. **代码质量问题**：
    - 在采样文件中检查坏味道
    - 评估严重程度：高（影响架构）/ 中（影响可维护性）/ 低（风格问题）

### 代码坏味道检测规则

| 类型 | 规则 |
|------|------|
| 过长函数 | 函数体 > 50 行 |
| 深层嵌套 | 缩进层级 > 4 |
| 重复模式 | 多文件出现相似代码结构 |
| God 文件 | 单文件 > 500 行且职责混杂 |
| 分层违反 | UI 层直接访问数据库 |

### 生成 glossary.md 时的分析要点

1. **模块术语**：
   - 从目录名、类名、文件名中提取项目特有术语
   - 推断每个术语的含义和对应能力
   - 关联到具体文件路径

2. **业务概念**：
   - 从函数名、变量名、注释中提取业务领域术语
   - 标注术语出场的文件/函数

## 新鲜度检测详细流程

```
检测流程：

1. 读取 .rdd/context/meta.json
   ├── 不存在 → 产物不存在，需生成
   └── 存在 → 继续

2. 检查 sampled_files 是否仍存在
   ├── 某文件已删除 → 过期
   └── 全部存在 → 继续

3. 计算当前文件的 MD5 hash
   ├── 与 meta.json.file_hashes 对比
   ├── 有差异 → 过期
   └── 无差异 → 继续

4. 检查是否有新增的关键源码目录
   ├── 对比当前目录结构与采样时的记录
   ├── 有重要新增 → 建议重新生成（非强制）
   └── 无变化 → 新鲜
```

## 用户交互模板

### 产物不存在时

```
未找到项目理解产物，正在生成...
[执行采样 + 分析 + 生成]
项目理解产物已生成到 .rdd/context/：
- style.md — 代码风格约定
- structure.md — 代码结构与模块关系
- glossary.md — 项目术语表
```

### 产物过期时

```
项目理解产物已过期（生成于 [时间]）。
- 重新生成（推荐）
- 继续使用旧产物
```

### 检测到代码质量问题时

```
⚠️ 检测到 [N] 个代码质量问题：
- [高] [type] at [file] — [description]
- [中] [type] at [file] — [description]
- [低] [type] at [file] — [description]

如需重构，可输入 /RDD-PM 将其立为需求。
```
