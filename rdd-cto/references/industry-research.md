# 业界方案调研指南

> 本文件为 CTO 处理 L2/L3 需求时方案设计的调研方法论。**调研是方案置信度的组成部分**——空口方案用户无法决策。两级调研：第一级"知识内核对"每次方案设计必做（不联网）；第二级"检索式调研"按触发条件执行 web 搜索。

## 两级调研定位

每个方案的依据链 = **业界依据**（设计模式 / 成熟方案 / 知名采用）+ **项目依据**（现状文件 / 已有模式）。两级调研分别供给业界依据的两个来源：

### 第一级：知识内核对（每次必做，不联网）

方案设计前先核对：**这个问题在业界是不是已有经典解法？**

- 命中经典设计模式（策略、观察者、Repository、绞杀者迁移、防腐层……）→ 方案中点名模式 + 说明在本项目的适配理由与偏离点
- 业界有通用做法/事实标准（如缓存一致性走旁路缓存、定时任务走幂等轮询、配置热更新走观察者）→ 点名做法 + 采用理由
- 确实没有成熟解法、需要自建 → 过下文「自建方案的门槛」，把"为什么不用成熟方案"写清楚

这一级用已有知识完成，不需要搜索。**跳过它直接给方案属于流程违规**——没有依据链的方案等于让用户盲签。

### 第二级：检索式调研（web 搜索，任一命中即触发）

1. **引入新技术**：需求涉及引入项目未使用过的框架、库或中间件
2. **认知盲区**：基于已有知识无法给出高置信推荐（不确定成熟度、兼容性或业界主流选择）
3. **显著分叉**：存在多个成熟候选且选择对项目影响显著

三条**任一命中**即执行 web 调研。示例：

| 场景 | 新技术 | 盲区 | 显著分叉 | 是否搜索 |
|------|--------|------|----------|---------|
| 项目要加消息队列，CTO 不熟悉 Python 生态选项 | ✅ | ✅ | — | **搜索** |
| 项目要加 Redis 缓存，CTO 清楚怎么用且事实标准明确 | ✅ | ❌ | ❌ | 不搜索（第一级点名事实标准即可） |
| 要选 date parsing 库，多个成熟候选且影响范围小 | ✅ | ❌ | ❌ | 不搜索 |
| 缓存策略有旁路/读写穿透多个成熟流派，选择影响数据一致性 | ❌ | ❌ | ✅ | **搜索** |
| 接口改造或数据模型变更 | ❌ | — | — | 不搜索（第一级照常执行） |

**未触发检索时**：第一级核对结论（模式名/做法名 + 适配理由）写入方案依据，即满足置信度要求。

## 调研流程

### 1. 明确调研范围

在开始搜索前，先明确要解决的核心问题是什么：

```
调研目标：[一句话说清楚要解决什么技术问题]
必须满足的条件：
- [条件 1，如"支持 Python 3.10+"]
- [条件 2，如"能集成 FastAPI"]
加分项：
- [非必须但有更好]
```

### 2. 搜索策略

使用 web 搜索工具，按以下优先级搜索：

**第一轮：广度搜索**
- 搜索关键词：`[技术领域] best practices <当前年份>`、`[技术领域] tools comparison`
- 目的：了解该领域有哪些主流工具

**第二轮：深度搜索**
- 对第一轮发现的 2-3 个候选方案，分别搜索：
  - `[工具名] documentation`
  - `[工具名] vs [竞品名] comparison`
  - `[工具名] [用户项目技术栈] integration`（如 `langchain fastapi`）
- 目的：深入了解每个方案的优劣

**第三轮：验证搜索（可选）**
- 搜索 `[工具名] issues/limitations/problems`
- 目的：发现候选方案的已知问题和陷阱

### 3. 评估维度

对每个候选方案从以下维度评估：

| 维度 | 评估要点 |
|------|---------|
| **成熟度** | 版本号（是否 1.0+）、发布历史、是否有 breaking change 历史 |
| **社区活跃度** | GitHub stars、近期 commit 频率、issue 响应速度 |
| **与项目技术栈兼容性** | 是否支持项目使用的语言/框架版本、集成难度 |
| **学习成本** | 文档质量、API 复杂度、团队是否需要大量学习 |
| **功能覆盖** | 是否覆盖需求的核心功能、缺失的功能是否有替代方案 |
| **维护前景** | 背后是否有公司/组织维护、社区贡献者数量趋势 |

### 5. 自建方案的门槛

只有在以下情况下才考虑自建而非使用成熟工具：

- 成熟工具的核心功能确实不满足需求（需要具体说明缺什么）
- 成熟工具与项目技术栈存在根本性不兼容（需要具体说明不兼容点）
- 需求极其简单，引入工具的集成成本远高于自建成本

选择自建时，必须给出：

```
自建理由：
- 为什么不用 [成熟方案 A]：[具体原因]
- 为什么不用 [成熟方案 B]：[具体原因]
- 自建方案的范围控制：[明确边界，避免范围蔓延]
```

## 调研结论落盘

调研不是聊完就忘，结论必须落为产物里的**依据链**：

- 方案呈现与设计文档「技术方案」的**方案依据**行：模式/做法/方案名 + 代表采用或来源
- `*-decisions.md` 决策记录的**依据**列：同上 + 项目现状证据（文件/已有模式）
- 引用了外部来源时附链接，官方文档优先

## 注意事项

- 调研结果的质量直接影响方案质量，不要跳过或敷衍
- 搜索结果可能包含过时信息，注意甄别发布时间
- 优先参考官方文档而非第三方博客
- 如果搜索结果不足以做出判断，诚实告知用户，请用户提供更多信息或建议
