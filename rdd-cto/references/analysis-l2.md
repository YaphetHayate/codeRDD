# L2 标准需求 — 方案评估模板

**执行时机**：候选方案形成**之后**（`feature-design.md` 2.4c）。评估对象是**每个候选方案在本项目落地的可行性**——不是脱离方案的抽象"需求可行性"（连方案都没有就评估可行性是流程违规）。对进入对比的候选逐个执行下表，候选之间的评估差异本身就是推荐依据的一部分。单一候选（无真实分叉）时**同样执行一次**——此时评估表就是推荐方案的影响范围与风险素材，直接喂给 2.4e 呈现的风险部分。

## 方案可行性评估

对每个候选方案，给出结构化的评估：

```
┌──────────────────────────────────────────────────────────────┐
│  方案：[候选名称]（对应需求 [标题]）                              │
├──────────────┬───────────────────────────────────────────────┤
│  技术可行性   │  ✅ 可行  /  ⚠️ 需预研  /  ❌ 存在障碍          │
│  说明         │  [具体说明哪些技术点可行，哪些需要验证]             │
├──────────────┼───────────────────────────────────────────────┤
│  影响范围     │  [受影响的模块/文件/接口]                          │
│  现有功能影响 │  无影响  /  需兼容  /  需迁移  /  需重构          │
│  数据影响     │  无  /  新增表  /  修改表  /  数据迁移            │
├──────────────┼───────────────────────────────────────────────┤
│  技术风险     │  🟢 低  /  🟡 中  /  🔴 高                      │
│  风险点       │  [具体列出风险项]                                 │
├──────────────┼───────────────────────────────────────────────┤
│  外部依赖     │  [无  /  列出具体依赖]                           │
├──────────────┼───────────────────────────────────────────────┤
│  已有功能交互 │  [无  /  列出交互的已有功能]                       │
│              │  ⚠️ 交互点>0：设计阶段按 self-check.md 两段式自检   │
└──────────────┴───────────────────────────────────────────────┘
```

## 需求依赖关系

当存在 2 个及以上 L2/L3 需求时，绘制依赖图并说明开发顺序（服务于第一步的排序与锁定；已绘制且仍准确则沿用，不重画）。只有 1 个 L2 需求且无 L3 需求时跳过。

依赖图格式参考 `analysis-l3.md` 中的依赖图模板。
