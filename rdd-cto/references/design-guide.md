## 决策点呈现格式

当某个需求的实现有多种可行方案时，必须将选择权交给用户。用以下格式完整呈现：

```
╔══════════════════════════════════════════════════════════════════════╗
║  决策点：[一句话说清楚需要决定什么]                                      ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  方案 A：[名称]                                                       ║
║  ┌──────────────────────────────────────────────────────────────────┐║
║  │  思路：[怎么做]                                                   │║
║  │                                                                  │║
║  │  优点：                                                           │║
║  │  • ...                                                           │║
║  │                                                                  │║
║  │  缺点：                                                           │║
║  │  • ...                                                           │║
║  │                                                                  │║
║  │  适合场景：...                                                     │║
║  └──────────────────────────────────────────────────────────────────┘║
║                                                                      ║
║  方案 B：[名称]                                                       ║
║  ┌──────────────────────────────────────────────────────────────────┐║
║  │  思路：[怎么做]                                                   │║
║  │                                                                  │║
║  │  优点：                                                           │║
║  │  • ...                                                           │║
║  │                                                                  │║
║  │  缺点：                                                           │║
║  │  • ...                                                           │║
║  │                                                                  │║
║  │  适合场景：...                                                     ║
║  └──────────────────────────────────────────────────────────────────┘║
║                                                                      ║
║  ╭──────────────────────────────────────────────────────────────────╮║
║  │  我的推荐：方案 X                                                  │║
║  │                                                                  │║
║  │  推荐理由（综合三个维度）：                                          ║
║  │                                                                  │║
║  │  架构维度：[这个方案在架构质量、扩展性、维护性上为什么好]             ║
║  │  业务维度：[这个方案和当前业务场景的匹配度分析]                       ║
║  │  框架维度：[这个方案和项目已有代码、技术栈的兼容性分析]                ║
║  │                                                                  ║
║  │  权衡取舍：[推荐方案牺牲了什么，换来了什么]                           ║
║  ╰──────────────────────────────────────────────────────────────────╯║
╚══════════════════════════════════════════════════════════════════════╝
```

推荐必须同时考虑三个维度，缺一不可：
- **架构优劣**：方案的架构质量、扩展性、维护性
- **业务匹配**：方案与当前业务场景的契合度
- **现有框架**：方案与项目已有代码、技术栈的兼容性

## 设计文档模板

每个需求生成一份独立的设计文档。这是最终归档的交付物。标注 **(可选)** 的章节按需覆盖，没有内容则省略。

```markdown
---
requirement_id: 需求编号或标题
priority: 高/中/低
depends_on:
  - 需求A的ID
  - 需求B的ID
blocks:
  - 需求C的ID
analysis_date: YYYY-MM-DD
status: draft
  tech_stack:
   - 技术栈1
   - 技术栈2
---

# [需求标题] — 设计文档

## 一、需求概述

> 从 requirement.md 提取该需求的核心内容，2-3 句话说清楚要做什么。

## 二、技术方案

### 2.1 技术选型

[需要引入或使用的技术，优先复用现有技术栈。说明选型理由。无新引入技术时省略。]

### 2.2 模块归属

[在现有架构中的位置。归属哪个模块、是否需要新建、划分理由。]

### 2.3 核心流程

[用 ASCII 图表配合文字描述。覆盖正常流程和异常分支。图表类型按需选用。]

### 2.4 数据模型 (可选)

[表结构或数据模型的初步设计。如涉及表变更，说明是新增还是修改。无数据变更时省略。]

### 2.5 接口设计

[关键接口的输入输出定义、调用方式、错误码。对于具体改动，列出改造清单表格更实用。]

### 2.6 非功能需求 (可选)

[性能、安全、可观测性等，按需覆盖。]

## 三、决策点记录 (可选)

| 决策点 | 选项 | 最终选择 | 选择理由 |
|--------|------|----------|----------|
| ...    | A/B  | A        | ...      |

无决策点时省略。

## 四、风险与应对 (可选)

| 风险 | 影响 | 应对措施 | 优先级 |
|------|------|----------|--------|
| ...  | ...  | ...      | P0/P1  |

无显著风险时省略。

## 五、实现优先级建议

在整体需求序列中的建议开发顺序和理由。

## 六、实现步骤清单 (可选)

按文件粒度列出改动顺序，便于 DEV 模式直接执行。简单需求可省略。
```

## 分级结果呈现格式

用于 Phase 1 向用户展示需求分级结果：

```
需求分级评估：

┌──────────────────┬──────┬──────────────────────────────────┐
│  需求              │ 等级  │ 理由                              │
├──────────────────┼──────┼──────────────────────────────────┤
│  需求 1：XXX       │  L1  │ 2 个文件，无选型，无外部依赖        │
│  需求 2：YYY       │  L2  │ 跨 3 个 API 文件 + 数据模型变更     │
│  需求 3：ZZZ       │  L3  │ 需引入消息队列做选型决策             │
└──────────────────┴──────┴──────────────────────────────────┘
```

## L1 快速结论格式

用于 Phase 1 对 L1 简单需求给出快速结论。每个 L1 需求用以下格式输出：

```
需求：[标题] (L1)
  可行性：✅ 可行  |  风险：🟢 低
  影响范围：[涉及的 2-3 个文件或模块]
  备注：[如有需要注意的点，一句话说明；没有则省略]
```

## 全局架构评审格式

用于 Phase 2.5 展示全局架构评审结果：

### 需求间依赖关系图

```
需求依赖关系：

  ┌──────────┐
  │  需求 A   │ (无依赖)
  └────┬─────┘
       │
  ┌────▼─────┐
  │  需求 B   │ (依赖 A)
  └────┬─────┘
       │
  ┌────┴────────────┐
  │                  │
┌──▼─────┐     ┌─────▼──┐
│ 需求 C  │     │ 需求 D  │  (均依赖 B，可并行)
└────────┘     └────────┘
```

### 评审结果表

```
全局架构评审：

┌──────────────────┬──────────────────┬──────────────────────────────────┐
│ 检查项             │ 结果              │ 说明                              │
├──────────────────┼──────────────────┼──────────────────────────────────┤
│ 依赖关系图         │ [依赖图]          │ [是否有循环依赖]                   │
│ 架构一致性         │ ✅ 一致 / ⚠️ 冲突 │ [冲突点说明]                       │
│ 重复/冲突          │ ✅ 无 / ⚠️ 发现   │ [具体描述]                         │
│ 合并机会          │ ✅ 无 / 💡 建议   │ [哪些需求建议合并]                  │
└──────────────────┴──────────────────┴──────────────────────────────────┘
```

### 调整建议格式

```
发现 [N] 个需要调整的问题：

1. [需求 A] 与 [需求 B] 的认证方案冲突：
   - 需求 A：使用 JWT Token
   - 需求 B：使用 Session Cookie
   - 建议：统一使用 JWT Token，理由：[...]
   - 影响文件：[需求 B 的设计文档]

2. [需求 C] 和 [需求 D] 共享相同的数据模型：
   - 建议：合并设计文档，统一数据模型定义
```
