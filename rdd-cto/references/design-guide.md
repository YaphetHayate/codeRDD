# 技术方向设计指南

本文件是 CTO 各场景流程的**格式与模板参考库**。按需查阅，不按顺序通读。

---

## 决策点话术

每个决策点按固定结构表达：

```
"需求 X 需要解决 Y 问题。我建议 [方案]，因为 [理由]。
对于 [不适用场景]，可以 [兜底策略]。你觉得这个方向可以吗？"
```

---

- **架构优劣**：方案的架构质量、扩展性、维护性
- **业务匹配**：方案与当前业务场景的契合度
- **现有框架**：方案与项目已有代码、技术栈的兼容性

## 技术方向文档模板

每个需求生成一份技术方向文档。标注 **(可选)** 的章节按需覆盖。

```markdown
---
requirement_id: 需求编号或标题
priority: 高/中/低
status: draft
role: cto
---

# [需求标题] — 技术方向文档

## 一、需求概述

> 从对应需求文件提取该需求的核心内容，1-2 句话说清楚要做什么。

## 二、涉及文件

| 操作 | 文件路径 | 说明 |
|------|----------|------|
| 新增 | `src/xxx/XxxFilter.java` | 鉴权拦截器 |
| 修改 | `src/config/WebConfig.java` | 注册拦截器 |

> DEV 应理解此清单为方向指引，具体实现时可据实际情况调整。

## 三、技术方案

### 3.1 技术选型 (可选)

[需要引入或使用的技术，优先复用现有技术栈。说明选型理由。无新引入时省略。]

### 3.2 模块归属

[在哪个模块/包下实现。归属哪个现有模块、是否需要新建、划分理由。]

### 3.3 关键要素

[需要新建的关键类/接口名、文件位置、职责描述（一句话）。不写方法签名和代码片段。]

### 3.4 配置方案 (可选)

[配置方式、配置项说明。无配置变更时省略。]

## 四、决策记录 (可选)

| 决策点 | 选项 | 最终选择 | 选择理由 |
|--------|------|----------|----------|
| ...    | A/B  | A        | ...      |

无决策点时省略。

## 五、风险提示 (可选)

| 风险 | 影响 | 应对方向 | 优先级 |
|------|------|----------|--------|
| ...  | ...  | ...      | P0/P1  |

无显著风险时省略。
```

> **注意**：技术方向文档中如需要引用已有模块（文件路径、类名），必须说明新元素与已有模块的关系（谁调谁、依赖什么），但不需要写方法签名或代码片段。

## 分级结果呈现格式

```
需求分级评估：

┌──────────────────┬──────┬──────────────────────────────────┐
│  需求              │ 等级  │ 理由                              │
├──────────────────┼──────┼──────────────────────────────────┤
│  需求 1：XXX       │  L1  │ 2 个文件，无选型，无外部依赖        │
│  需求 2：YYY       │  L2  │ 跨 3 个 API 文件 + 数据模型变更     │
│  需求 3：ZZZ       │  L3  │ 需引入消息队列做选型决策             │
└──────────────────┴──────┴──────────────────────────────────┘
```

## L1 快速结论格式

每个 L1 需求用以下格式输出：

```
需求：[标题] (L1)
  可行性：✅ 可行  |  风险：🟢 低
  影响范围：[涉及的 2-3 个文件或模块]
  备注：[如有需要注意的点，一句话说明；没有则省略]
```

## 设计方案确认总览格式

全部需求设计确认后，用以下格式汇总：

```
设计方案确认总览:

┌──────────┬──────────┬──────────┬──────────┬──────────┐
│  需求     │  优先级   │  状态     │  待确认    │  文档     │
├──────────┼──────────┼──────────┼──────────┼──────────┤
│  需求 A   │  P0      │  ✅ 已确认│  无       │  ✓ 完成   │
│  需求 B   │  P0      │  ✅ 已确认│  无       │  ✓ 完成   │
│  需求 C   │  P1      │  ✅ 已确认│  无       │  ✓ 完成   │
│  需求 D   │  P2      │  ✅ 已确认│  无       │  ✓ 完成   │
└──────────┴──────────┴──────────┴──────────┴──────────┘

建议开发顺序：A → B → C (D 可并行)
```

## 归档结构示例

```
.rdd/changes/archive/2026-05-16-topicName/
├── overview.md             (PM 归档)
├── fixbug.md               (PM 归档：需求独立文件)
├── optimizeCache.md        (PM 归档：需求独立文件)
├── task.md                 (PM 归档：任务跟踪)
└── design/                 (CTO/UX 归档)
    ├── fixbug-cto.md
    ├── fixbug-ux.md
    ├── optimizeCache-cto.md
    └── optimizeCache-ux.md
```
