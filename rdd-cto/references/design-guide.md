本文件是 CTO 各场景流程的**格式与模板参考库**。按需查阅，不按顺序通读。

## 决策点纪律（什么时候抛、怎么抛）

**先问该不该抛**。只有满足以下任一条件才构成用户决策点：

1. **真实分叉**：存在多条 CTO 都愿意为之辩护的可行路线，选择会改变后续走向
2. **用户必须兜底的取舍**：P1 风险、不可逆改动、新增依赖/成本、安全相关

其余（模块归属、命名、文件组织等专业判断）CTO 直接定，写入 `*-decisions.md` 留痕，不抛决策点。**为了决策而决策是流程违规。**

**陪跑检验**：多方案决策点里，每个选项都必须通过检验——"如果用户选它，我能负责任地继续设计下去吗？"只为衬托推荐方案而存在的选项禁止出现。落选选项不冤：不是因为缺点多到不可用而落选，而是在本项目语境下推荐方案更优。

**表达纪律**（每个抛出的决策点必须做到）：

- **讲清目的**：这个决策为什么需要用户拍板、它决定什么、定错了影响什么
- **白话表达**：术语纪律见下节；选项用"做法"命名，不堆产品名
- **后果具体**：每个选项"选了会发生什么 / 不选会错过什么"用具体影响描述（改动范围、依赖、风险），不用空泛形容词
- **优缺点有证据**：每条优缺点必须能指向具体出处——项目里的文件/既有模式、依赖的 documented 行为、调研来源；写不出证据的不许列

**单方案推荐格式（默认形态）**：

```
"这条需求要解决 [一句话问题]。
我建议 [方案]，具体做法是 [白话描述]。
依据：业界这类问题的成熟做法是 [模式/方案名]（[知名采用或来源]）；
我们项目里 [现状证据：文件/已有模式]，契合点在 [一句话]。
代价与风险：[具体说明]；不适用场景的兜底：[策略]。
这个方向可以吗？"
```

推荐必须同时考虑三个维度，缺一不可：
- **架构优劣**：方案的架构质量、扩展性、维护性
- **业务匹配**：方案与当前业务场景的契合度
- **现有框架**：方案与项目已有代码、技术栈的兼容性

## 术语纪律

- 面向用户的输出（决策点、方案呈现、现状摘要）中，**首次出现的术语**必须紧跟一句白话解释，或直接换成白话说法。例："建议引入旁路缓存（Cache-Aside：读的时候先查缓存，没有再查数据库并回填缓存）"
- 决策点文字**禁用未解释的缩写**（ORM、SSR、CJK……要么解释，要么不用）
- 判定标准：这句话拿给不懂技术的产品经理看，能否看懂"在决定什么"。看不懂就重写
- 设计文档（给 DEV 的产物）不受此限——DEV 具备技术语境，术语正常使用

## 技术方向文档模板

主体文档，1 页纸以内。决策记录与风险提示独立为附带产物。

> **模板文件单源**：`../design-template.md`（主体）与 `../design-decisions-template.md`（附带产物）——变更地图机读契约（delivery-bridge / planner-scenarios 的文件重叠检测）以模板文件为准，下方为同源展示；两处修改必须同步。

```markdown
---
requirement_id: req-xxx
priority: 高
role: cto
status: active
acceptance_ref: requirements/{name}.md（对齐验收标准 1/2/3）
---

# 需求标题 — 技术方向文档

## 需求概述
一句话说清要解决什么。

## 变更地图

project-root/
├── backend/app/
│   ├── `backend/app/models/xxx.py`             [修改] 字段扩展说明
│   └── `backend/app/api/xxx.py`                [修改] 处理逻辑说明
├── frontend/src/
│   ├── `frontend/src/types/index.ts`           [修改] 类型新增说明

[新增] 0 | [修改] N | [删除] N | 无新增依赖

## 技术方案
每项一句话，不做展开：

- **方案依据**：xxx（业界成熟做法/设计模式 + 项目契合点一句话）
- **存储**：xxx
- **落盘时机**：xxx

- **字段命名**：xxx

> 对方案有疑问或需了解决策理由，请查阅附带产物 `*-decisions.md`。

|------|------|--------|------|-------------|----------|------|
| - | - | - | - | - | - | - |
```

```

| 回退自 | 回退到 | 原因 | 后续动作 | 受影响检查点复核结果 |
|--------|--------|------|----------|---------------------|
```

## 分级标准（内部判据）

分级是 CTO 的**内部分工判断**（哪些需求直接发开发、哪些开完整设计），**不作为对用户的呈现产物**——不对用户输出 L1/L2/L3 标签表，用户看到的是分级的后果：L1 分流清单 + L2/L3 锁定推荐。用户追问分级依据时，按 `feature-design.md` 1.2 的判定条件表解释。

## L1 快速结论格式

每个 L1 需求用以下格式输出（面向用户讲清"为什么不用设计"）：

```
需求：[标题] —— 无需完整设计，直接发开发
  为什么：[一句话：改动 ≤3 个文件、不涉及选型/外部依赖/数据模型变更]
  影响范围：[涉及的 2-3 个文件或模块]
  备注：[如有需要注意的点，一句话说明；没有则省略]
```
