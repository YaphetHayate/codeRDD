# Bug 根因分析流程

> **前提**：本流程由 SKILL.md 场景路由触发。CTO 角色为**调查员**——深入代码追踪调用链，定位根因。
>
> **适用边界**：本流程针对 L2/L3 的 Bug 需求。命中 L1 标准（≤3 文件、无选型、无外部依赖、无数据模型变更）的简单 bugfix 走 `feature-design.md` 1.4 快速分流直接发开发，不做根因深挖；归档内多条待处理时，先按 `feature-design.md` 第一步（扫描 → 分级 → L1 分流 → 锁定单条）锁定本条，锁定的是 Bug 类需求才进入本流程。

## 流程

### 1. 读取 Bug 需求

从 PM 归档中读取 Bug 需求文件，明确：
- 问题现象（什么报错/异常行为？）
- 复现路径（什么操作触发？）
- 验收标准（修复后用户应该看到什么？）

### 2. 深度代码追踪

**这是本流程的核心**——不是走马观花看代码，而是像调试一样追踪调用链。

1. **定位入口**：从需求中描述的用户操作路径，找到对应的代码入口（Controller、路由、事件处理器等）
2. **追踪调用链**：沿着入口向下逐层追踪——入口 → Service → Repository/外部调用 → 返回值处理。每一层都要读到具体代码
3. **找到异常点**：定位出问题的具体代码位置（文件 + 行号 + 出问题的逻辑）
4. **回溯根因**：从异常点向上回溯，找出根本原因——是边界条件未处理？是状态不一致？是第三方依赖行为变化？是异步时序问题？

> 追踪中若发现根因源于某条已归档设计文档的方向性缺陷（设计本身有洞，而非实现走样），按 `rdd-engine/references/rejection-protocol.md` 正式反馈该设计文档，不在修复方向里私自绕过或掩盖。

### 3. 向用户呈现根因

用清晰的因果链呈现发现，而非仅给出结论：

```
根因分析：

  用户操作 → [入口函数] → [关键路径] → [异常点：文件:行号]
                                            │
                                    根因：[一句话根因]
                                    
  触发条件：[什么情况下会出现]
  影响范围：[影响哪些用户/功能]
```

### 4. 提出修复方向

给出修复方向建议，但**不写具体代码**：

```
修复方向：

  - 改动位置：[文件路径] 的 [函数/方法]
  - 修复思路：[做什么，用一两句话说清楚方向]
  - 注意事项：[修复时需要注意的边界条件或副作用]
  - 涉及文件：预计修改 [N] 个文件
```

### 5. 逐决策点确认

每个修复方向按 `design-guide.md` 的决策点纪律向用户呈现（单一方向用单方案推荐格式；多方向先过陪跑检验），一次一个。用户确认后推进下一个。

**Bug 修复通常决策点很少**（一般 1-2 个），如果只有一个显然的方向，直接说"我建议在 [位置] 做 [修复]，因为 [理由]。你觉得可以吗？"

**自检轻量门**：修复方向涉及跨模块交互、共享状态或多文件联动时，按 `self-check.md` 对交互点做一轮完整推演（识别 → 推演 → 结论，单段轻量执行即可），发现的隐患写入设计文档风险提示——单文件局部修复可豁免。

### 6. 确认后归档

用户确认所有决策点后：

1. 在归档目录下确保 `design/` 子目录存在（不存在则创建），写入轻量设计文档，命名为 `design/{需求文件名}-cto.md`
2. 文档内容（精简版，只需覆盖以下章节；`## 驳回记录` 空表为驳回协议占位，发生驳回时按 `rdd-engine/references/rejection-protocol.md` 追加行）：

```markdown
---
requirement_id: [需求标识]
priority: [优先级]
status: active
role: cto
---

# [需求标题] — Bug 修复技术方向

## 一、根因

[因果链描述]

## 二、修复方向

- **改动位置**：[文件路径]
- **修复思路**：[方向描述]
- **注意事项**：[边界/副作用]

## 三、变更地图

- `src/auth/token.ts`        [修改] 刷新逻辑边界条件补全
- `src/auth/session.ts`      [修改] 过期判定状态一致性

[新增] 0 | [修改] 2 | [删除] 0

> 文件行机读契约与 `design-template.md` 同源：仓库根相对完整路径以反引号包裹、与 [新增]/[修改]/[删除] 标注同行（并行文件冲突检测的机械机读基础，不合契约报 `DESIGN_MAP_INVALID` 并使重叠检测对该文档失明）。

## 四、风险提示（可选）

[如有需要注意的风险]

## 驳回记录

| 轮次 | 日期 | 发起方 | 理由 | 被驳回方回应 | 最终裁决 | 状态 |
|------|------|--------|------|-------------|----------|------|
| - | - | - | - | - | - | - |
```

3. 本条经用户确认的修复方向决策入统一决策账本留痕：`delivery-bridge.cmd -Command decide -Kind checkpoint -Archive <归档> -Checkpoint <名> -Decision <结论> [-Reason] [-Role CTO]`（同 `feature-design.md` 第三步）
4. 调用 rdd-flow add-design 追加设计文档路径，然后 `set-route -To "DEV" -Phase IMPL` 推进路由（同任务还有其他设计阶段角色时先阶段内收窄，语义见 `feature-design.md` 第三步）
5. 按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（路由已更新 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

**推荐角色分支**：
- **CTO 仍有待办**（`next` 显示 CTO `taskCount > 0`）→ 推荐重入 CTO（新会话）处理下一条。话术补充："本条 Bug 已闭环，CTO 还有 N 条待处理，建议 `/new` 开新会话继续。"
- **CTO 已清空** → 交下游 DEV

> 完整流程、模式检测、同会话切换规则见 `rdd-engine/references/transition-guide.md`。
