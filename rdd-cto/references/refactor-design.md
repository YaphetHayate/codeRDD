# 重构设计流程

> **前提**：本流程由 SKILL.md 场景路由触发。适用于 PM 归档为重构/技术优化的场景。CTO 角色为**架构师**——诊断现状、设计目标架构、规划迁移路径。

## 流程

### 1. 读取全部需求 + 理解现状

从 PM 归档中读取重构需求文件，然后**深入阅读现有代码**——必须理解当前架构的问题所在，才能设计合理的改造方案。需要理解代码时委托 engine：
```powershell
explore.ps1 -Type explore -Query "分析重构需求涉及的代码模块"
```

参照 `code-quality-assessment.md` 评估现有代码的系统性问题（循环依赖、模块职责混乱、架构模式不一致等）。

### 2. 确定依赖顺序

如果有多条重构需求，分析它们之间的依赖关系，确定处理顺序。重构需求的依赖通常比功能需求更强——先改基础设施，再改上层模块。

### 3. 逐条设计（按依赖顺序）

一次只处理一条需求，确认后再进入下一条。每条执行：

**a. 现状诊断**
- 当前架构的问题是什么？引用具体文件路径
- 导致了什么业务/技术影响？
- 边界在哪——改哪里、不动哪里？

**b. 目标架构**
- 按"5 问"框架描述改造后的方向：
  - 技术选型（如涉及）
  - 模块归属（如何重新组织）
  - 关键要素（要新建/重命名的类或接口）
  - 配置变更
  - 涉及文件

**c. 迁移路径**
- 分几步走？每步改什么？
- 每步完成后系统是否仍然可运行？（逐步迁移 vs 大爆炸）
- 新旧代码的共存策略

**d. 向后兼容**
- 对外接口是否变化？
- 数据是否需要迁移？
- 依赖方是否需要同步升级？

**e. 自检**：L2/L3 级别重构 → 加载 `self-check.md` 执行自检

**f. 交叉校验**：与已确认的前序重构方案做一致性检查

**g. 逐决策点对话确认用户**

**h. 确认 → 立即写设计文档**（完整版，使用 `design-guide.md` 模板，额外增加"迁移路径"章节）

### 4. 归档

全部需求确认后：
1. 更新 `task.md` 路由总览：已设计需求的行，`当前责任人` 改为 DEV，`关联设计文档` 填入实际路径
2. 按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（路由已更新 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

> 完整流程见 `rdd-engine/references/transition-guide.md`。
