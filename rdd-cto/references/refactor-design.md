# 重构设计流程

> **前提**：本流程由 SKILL.md 场景路由触发。适用于 PM 归档为重构/技术优化的场景。CTO 角色为**架构师**——诊断现状、设计目标架构、规划迁移路径。
>
> **核心范式**：一次只深耕一条重构需求。重构需求间依赖通常更强（先改基础设施再改上层），但仍在每会话锁定一条做透、归档后引导 `/new`。详见 SKILL.md 核心原则。

---

## 第一步：扫描与锁定

### 1.1 理解现状

从 PM 归档中读取重构需求文件，然后**深入阅读现有代码**——必须理解当前架构的问题所在，才能设计合理的改造方案。需要理解代码时委托 engine：
```powershell
$rdd = (Get-ChildItem (git rev-parse --show-toplevel) -Recurse -Directory -Depth 3 -Filter 'rdd-engine' | Select-Object -First 1).FullName; & "$rdd\scripts\explore.cmd" -Type explore -Query "分析重构需求涉及的代码模块"
```

参照 `code-quality-assessment.md` 评估现有代码的系统性问题（循环依赖、模块职责混乱、架构模式不一致等）。

### 1.2 确定依赖序 + 锁定单条

分析多条重构需求之间的依赖关系（重构依赖通常比功能需求更强——先改基础设施，再改上层模块），据此推荐处理顺序。

**锁定单条**（话术与功能设计流程一致）：

```
本次待设计的重构需求：
  • [标题 A] — [一句话问题]
  • [标题 B] — [一句话问题]

重构强依赖，我推荐先做 [标题 X]，因为 [它是基础设施层 / 被其他需求依赖]。
[若识别到强相关簇：标题 B 与 标题 C 同属 XX 层重构，建议作为一组一起做。]

本次专注这一条，其余留到后续会话。
是否确认锁定 [标题 X]？
```

**强相关簇判定**：PM 备注复合标注 + 需求文件「依赖关系」字段 + 同模块/同文件重叠（重构场景下"同模块"信号权重更高）。

**锁定后约束**：只读锁定需求；未归档可弃换条，归档后不换需走驳回。

---

## 第二步：设计锁定需求

> 以下流程只针对锁定的那一条（或强相关簇），不循环回其他需求。

### 2.1 前序设计影响扫描

重构对前序设计尤其敏感（前一次重构可能已经改动了当前需求的根基）。设计前主动感知同归档内已完成的设计：

**a. 找出已完成的设计**：扫描 `task.md` 路由总览，找 `关联设计文档` 已填真实路径（非 `(待产出)` 占位）、且 `当前责任人` 已越过设计阶段的行。注意：这里的"前序"指**跨批次、跨会话已归档**的设计，不是同会话内已确认的。

**b. 三信号判断是否影响**：
- PM 路由备注标注与当前需求复合/关联
- 当前锁定需求文件「依赖关系」字段指向该需求
- 该前序设计的「变更地图」（重构后的模块结构、新建/重命名的类接口、迁移路径）与本次预估涉及范围有重叠

**c. 分流处理**：命中任一信号 → 先读其设计文档，把"重构后的目标架构"作为本次的约束基线（本次重构是在前次重构的基础上继续，而非另起炉灶）；全不命中 → 跳过。

**d. 发现冲突**（前序重构方向与本次矛盾）：按 `rdd-engine/references/rejection-protocol.md` 正式反馈。

> 这一步替代旧的"与已确认的前序重构方案做一致性检查"——旧是同会话事后对照，新是跨批次设计前的前置感知。

### 2.2 现状诊断

- 当前架构的问题是什么？引用具体文件路径
- 导致了什么业务/技术影响？
- 边界在哪——改哪里、不动哪里？

### 2.3 目标架构

按"5 问"框架描述改造后的方向：
- 技术选型（如涉及）
- 模块归属（如何重新组织）
- 关键要素（要新建/重命名的类或接口）
- 配置变更
- 涉及文件

### 2.4 迁移路径

- 分几步走？每步改什么？
- 每步完成后系统是否仍然可运行？（逐步迁移 vs 大爆炸）
- 新旧代码的共存策略

### 2.5 向后兼容

- 对外接口是否变化？
- 数据是否需要迁移？
- 依赖方是否需要同步升级？

### 2.6 自检

L2/L3 级别重构 → 加载 `self-check.md` 执行自检三步。自检聚焦"本次重构 vs 已有代码库"；跨批次一致性已在 2.1 前序扫描中处理。

### 2.7 逐决策点对话确认用户

按 `design-guide.md` 决策点格式，一次一个决策点，用户确认后推进下一个。

### 2.8 确认 → 立即写设计文档

完整版，使用 `design-guide.md` 模板，额外增加"迁移路径"章节。

---

## 第三步：归档（单条）

1. 更新 `task.md` 路由总览：本次完成的需求行，`当前责任人` 改为 DEV，`关联设计文档` 追加自身设计文档路径（与单元格已有路径 `+` 连接、去重，移除 `(待产出)` 占位，不覆盖他人路径）
2. 告知用户文件位置（单条收尾，不做总览汇总——自检即闸门）

---

## 第四步：引导下一步（/new 分支）

按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（路由已更新 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

**推荐角色分支**：
- **CTO 仍有待办**（`next` 显示 CTO `taskCount > 0`）→ 推荐重入 CTO（新会话）处理下一条。话术补充："本条重构已闭环，CTO 还有 N 条待设计，建议 `/new` 开新会话继续。"
- **CTO 已清空** → 交下游 DEV

> 完整流程见 `rdd-engine/references/transition-guide.md`。
