# 全局架构评审

逐需求设计完成后、逐个讨论确认之前，做一次全局审视。目的是发现跨需求的问题——单独看每个方案都合理，放在一起可能冲突或重复。

---

## 适用条件

存在 2 个及以上 L2/L3 需求时执行。全部为 L1 需求时跳过。

## 评审内容

1. **需求间依赖关系图** — 用 ASCII 图展示所有需求之间的上下游依赖，直观呈现执行顺序
2. **架构一致性检查** — 各需求的设计方案是否存在矛盾（如 A 用了缓存策略 X，B 用了缓存策略 Y；A 定义了接口 I，B 也定义了功能重叠的接口 I'）
3. **重复/冲突识别** — 多个需求是否设计了相同或冲突的能力，是否可以合并
4. **合并机会** — 识别可以合并设计的需求（强关联、共享同一模块、依赖链紧邻）
5. **新旧功能交互一致性** — 新增/修改的功能与已有功能是否存在交互隐患。重点检查：多策略层的周期是否对齐、某层失败后其他层能否感知并回滚、是否存在"A 策略放过但 B 策略卡住"导致的资源浪费。设计自检已发现的问题在此做交叉验证和汇总。

## 评审结果呈现

```

┌──────────────────┬──────────────────┬──────────────────────────────────┐
│ 检查项             │ 结果              │ 说明                              │
├──────────────────┼──────────────────┼──────────────────────────────────┤
│ 依赖关系图         │ [ASCII 图]        │ [是否有循环依赖]                   │
│ 架构一致性         │ ✅ 一致 / ⚠️ 冲突 │ [冲突点说明]                       │
│ 重复/冲突          │ ✅ 无 / ⚠️ 发现   │ [具体描述]                         │
│ 合并机会          │ ✅ 无 / 💡 建议   │ [哪些需求建议合并]                  │
│ 新旧功能交互       │ ✅ 无 / ⚠️ 发现   │ [交互隐患及修复方向]                │
└──────────────────┴──────────────────┴──────────────────────────────────┘

[如有问题，列出具体的调整建议]
```

## 评审后的处理

- **发现冲突**：与用户讨论后统一方案，同步更新相关设计文档
- **发现合并机会**：向用户建议合并，确认后更新设计文档和 task.md
- **无问题**：直接进入讨论与确认阶段

评审结果需用户确认后才进入讨论与确认阶段。
