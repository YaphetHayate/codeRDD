# 设计自检指南

本文件提供设计自检的完整方法论。自检分两段执行——轻量预扫（检查点 ①②③ 后）+ 完整推演（检查点 ④），详见下方第一节。

**核心目标**：在设计阶段主动发现新设计与已有功能库的交互隐患，避免"每个设计单独看合理、放在一起出问题"的情况流入 DEV 环节。

**职责边界**：本指南只负责"当前需求 vs 已有代码库"。跨需求、跨批次的一致性由流程中的「前序设计影响扫描」承担——设计前主动读取同归档内已完成的其他设计文档作为约束。自检不重复做跨批次校验。

---

## 一、自检时机与范围

自检分**两段**执行，配合 `feature-design.md` 的四检查点推进模型。两段各自承担不同职责，**预扫不能替代完整推演**。

| 阶段 | 时机 | 范围 | 动作 | 产物 |
|------|------|------|------|------|
| **轻量预扫** | 检查点 ①②③ 各自达标后 | 当前需求 vs 已有代码库（快速标记） | 只做下方 Step 1（交互点识别）的快速版——标记潜在交互模块/数据/路径，**不展开推演** | 逐步累积的"交互点清单" |
| **完整推演** | 检查点 ④ | 当前需求 vs 已有代码库（深度分析） | 执行完整三步法（Step 1 → 2 → 3），把前面预扫标记的所有交互点逐一推演 | 冲突判定 + 修复方向 |

**两段边界**：
- 预扫只"标记"，不"下结论"——产物是交互点清单，供 ④ 集中推演。
- 完整推演必须覆盖预扫清单中的**每一个**交互点，不得遗漏。
- 检查点 ④ 跳过完整推演属于流程违规——预扫时未发现明显交互，不等于无风险，完整推演仍是闸门。

> 跨批次已归档的同批设计对当前需求的影响，由流程中的「前序设计影响扫描」在设计前先行感知，不在自检范围内重复校验。

---

## 二、自检三步法

### Step 1：交互点识别

先列出新设计与已有功能的**所有交互点**。不列交互点就开始分析等于猜。

**交互点定义**：新设计中的某个环节与已有功能共享了以下任一元素：
- **同一数据**（同一张表、同一个缓存 key、同一个内存状态）
- **同一执行路径**（同一个请求链路、同一个方法调用链）
- **同一资源**（同一个锁、同一个限流配额、同一个连接池）
- **同一生命周期**（同一个创建/销毁过程、同一个定时任务）
- **同一渲染管线**（两个模块都参与了同一个视觉输出——DOM 更新、Canvas 绘制、SVG 渲染，或各自维护了独立的渲染路径但服务于同一个视觉区域）
- **同一初始化时序**（新设计依赖某个模块在特定时机之前完成注册/初始化）
- **同一 UI 状态同步**（同一逻辑状态被多个组件/模块分别持有，需要保持一致）
- **同一事件流**（同一个动作/变更通过事件机制通知多个订阅者，通知链路的完整性和顺序性需要保证）

**前置检查**：在技术方向文档中搜索所有引用了已有代码的地方（文件路径、类名）。对每个引用点，确认文档中已说明新元素与已有模块的关系。未覆盖的，要求补全后再执行自检。

**输出格式**：

```
┌─────────────────────────────────────────────────────────────────┐
│  交互点识别                                                       │
├────────────┬──────────┬──────────────────┬──────────────────────┤
│  新设计环节  │ 已有功能  │ 共享元素          │ 交互方式              │
├────────────┼──────────┼──────────────────┼──────────────────────┤
│  全局限流   │ 资源限流  │ 同一请求链路      │ 顺序执行              │
│  检查       │          │ (execute 方法)    │ (先全局后资源)         │
│  ...       │ ...      │ ...              │ ...                  │
└────────────┴──────────┴──────────────────┴──────────────────────┘
```

**触发提示**：以下模式是高交互概率的信号，必须执行 Step 1：

- 新方案是一个"全局"或"统一"的层（全局拦截器、统一过滤器、公共中间件）
- 新方案是对已有功能的"补充"或"增强"
- 新方案修改了已有功能的触发条件或执行顺序
- 新方案引入了新的异步/并发路径，可能与已有同步路径交叉

---

### Step 2：冲突推演

对 Step 1 列出的每个交互点，检查是否存在方向性冲突：

```
Q1: 两个方案对同一数据/资源的处理方式是否矛盾？
    → [检查：A 用了缓存策略 X，B 用了策略 Y，是否冲突？]
Q2: 执行顺序是否可能导致逻辑错误？
    → [检查：A 在 B 之前执行，B 失败时 A 的副作用是否需要回滚？]
Q3: 是否存在循环依赖？
    → [检查：A 依赖 B 的产物，B 依赖 A 的状态？]
```

---

### Step 3：多策略一致性检查（当涉及多个限制/守卫层时必做）

当新设计中存在**多个策略层/守卫层**作用于同一操作路径时（例如：全局限流 + 资源限流、多层校验、多层缓存），必须检查各层之间的一致性。

**检查矩阵**：

```
┌──────────────────────┬──────────────────┬──────────────────┬──────────┐
│  一致性维度            │ 层 A (如全局)    │ 层 B (如资源)    │ 结论      │
├──────────────────────┼──────────────────┼──────────────────┼──────────┤
│  生效/解除周期         │ [周期描述]       │ [周期描述]       │ 一致/不一致│
│  状态传播              │ B 失败时 A 是否  │ A 失败时 B 是否  │ 是否闭环  │
│                      │ 感知并回滚？     │ 感知？           │          │
│  资源消耗              │ 本层消耗的资源   │ 本层消耗的资源   │ 是否存在  │
│                      │                 │                  │ 浪费链    │
│  执行顺序              │ [先/后]         │ [先/后]          │ 是否合理  │
│  错误隔离              │ 本层失败对下游   │ 本层失败对上游   │ 是否分级  │
│                      │ 的影响          │ 的影响           │          │
└──────────────────────┴──────────────────┴──────────────────┴──────────┘
```

**关键判断**：如果"状态传播"不是闭环（即某层失败后，其他层无法感知并回收已消耗的资源），且"生效/解除周期"不一致，则**必然存在资源浪费隐患**。

**典型反例**（你遇到的限流问题）：

```
  请求进入 → 全局限流检查(通过, 配额-1) → 资源限流检查(拒绝, 无法执行)
  → 全局限流配额已扣减, 但本次操作实际未执行 → 配额浪费
  
  根因：两个限流器周期不一致, 且全局限流器不感知资源限流器的状态
```

**修复方向**（在技术方向文档中记录，具体实现留给 DEV）：
1. **状态感知**：外层检查前先查询内层状态，跳过已受限的资源
2. **统一周期**：将多个策略的解除周期对齐
3. **合并检查**：将多层策略合并为单一的复合判定

---

## 三、自检结果输出

自检结果直接记录在当前需求的技术方向文档中，在"风险提示"章节之前插入：

```markdown
## 自检结果

### 交互点

| 已有功能 | 共享元素 | 交互方式 | 推演结论 |
|----------|----------|----------|----------|
| 资源限流 | 同一请求链路 | 顺序执行(先全局后资源) | ⚠️ 解除周期不一致 → 配额浪费 |

### 发现的问题

1. ⚠️ / 🔴 [问题简述]
   - 冲突点：[两个方案在哪个环节产生冲突]
   - 影响：[后果描述]
   - 建议：[修复方向概述]

### 无问题的交互点（可选）

- 交互点 X：推演无风险，省略
```

**无交互点时**：简写为 `自检结果：本设计与已有功能无明显交互点，跳过推演。`

---

## 四、自检的边界

自检的目的是**在方向确定阶段发现设计缺陷**，不是为了穷举所有可能的运行时问题。以下内容不在此检查范围内：

- 分布式事务的最终一致性细节（属于 DEV 实现阶段的考虑）
- 操作系统/网络层面的极端故障（如进程崩溃、网络分区）
- 需要性能压测才能发现的瓶颈

自检聚焦于**逻辑层面、可在方向层面推演**的一致性问题。

---

## 五、自检结果进入决策点对话

**完整推演**（检查点 ④）发现的问题，在该检查点的决策点对话中向用户主动提出：

> 在方向自检中，发现 [需求 X] 的 [某个决策] 与已有功能 [功能 Y] 存在交互隐患：[简述问题]。建议 [修复方向]。你觉得这个方向可以吗？

用户确认后，更新技术方向文档的风险提示章节。

> 若该问题暴露的是前置检查点 ①②③ 的决策缺口，按 `feature-design.md` 的回退机制执行显式回退，不在此就地打补丁。
