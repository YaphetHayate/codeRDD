# 设计自检指南

本文件提供设计自检的完整方法论。在 Phase 2 每个 L2/L3 需求设计完成后执行（per-design），并在 Phase 2.5 全局评审时交叉验证。

**核心目标**：在设计阶段主动发现新设计与已有功能的交互隐患，避免"每个设计单独看合理、放在一起出问题"的情况流入 DEV 环节。

---

## 一、自检时机与范围

| 时机 | 范围 | 触发条件 |
|------|------|----------|
| **设计完成后**（Phase 2） | 当前需求 vs 已有功能 | L2/L3 需求，每设计完一个立即执行 |
| **全局评审时**（Phase 2.5） | 所有需求 vs 所有需求、所有需求 vs 已有功能 | 存在 2+ L2/L3 需求，或存在 L2/L3 需求与已有功能有明显交互 |

---

## 二、自检三步法

### Step 1：交互点识别

先列出新设计与已有功能的**所有交互点**。不列交互点就开始分析等于猜。

**交互点定义**：新设计中的某个环节与已有功能共享了以下任一元素：
- **同一数据**（同一张表、同一个缓存 key、同一个内存状态）
- **同一执行路径**（同一个请求链路、同一个方法调用链）
- **同一资源**（同一个锁、同一个限流配额、同一个连接池）
- **同一生命周期**（同一个创建/销毁过程、同一个定时任务）
- **同一渲染管线**（两个模块都参与了同一个视觉输出——DOM 更新、Canvas 绘制、SVG 渲染，或各自维护了独立的渲染路径但服务于同一个视觉区域）
- **同一初始化时序**（新设计依赖某个模块在特定时机之前完成注册/初始化）
- **同一 UI 状态同步**（同一逻辑状态被多个组件/模块分别持有，需要保持一致）
- **同一事件流**（同一个动作/变更通过事件机制通知多个订阅者，通知链路的完整性和顺序性需要保证）

**前置检查**：在设计文档中搜索所有引用了已有代码的地方（文件路径、类名、函数签名）。对每个引用点，检查设计文档的"集成点描述"章节是否已覆盖。未覆盖的，要求补全后再执行自检。

**输出格式**：

```
┌─────────────────────────────────────────────────────────────────┐
│  交互点识别                                                       │
├────────────┬──────────┬──────────────────┬──────────────────────┤
│  新设计环节  │ 已有功能  │ 共享元素          │ 交互方式              │
├────────────┼──────────┼──────────────────┼──────────────────────┤
│  全局限流   │ 资源限流  │ 同一请求链路      │ 顺序执行              │
│  检查       │          │ (execute 方法)    │ (先全局后资源)         │
│  ...       │ ...      │ ...              │ ...                  │
└────────────┴──────────┴──────────────────┴──────────────────────┘
```

**触发提示**：以下模式是高交互概率的信号，必须执行 Step 1：

- 新设计是一个"全局"或"统一"的层（全局拦截器、统一过滤器、公共中间件）——它必然与每个经过它的已有功能交互
- 新设计是对已有功能的"补充"或"增强"（在已有限流上加新限流、在已有校验上加新校验）
- 新设计修改了已有功能的触发条件或执行顺序
- 新设计引入了新的异步/并发路径，可能与已有同步路径交叉
- 新设计涉及前端渲染、DOM 操作、Canvas 绘制——可能与已有渲染管线产生冲突或重复
- 新设计的初始化逻辑依赖其他模块先完成注册/创建——时序无法保证时即存在隐患

**反例：渲染管线断裂（codeRDD-plus-mimo 项目）**

```
┌──────────────────────────────────────────────────────────────────┐
│  交互点：Character 类 vs SceneManager/Renderer                   │
├──────────────────────────────────────────────────────────────────┤
│  Character 有自己的 render(ctx) 方法（含 fallback 蓝色矩形）        │
│  SceneManager 通过 _buildCharacterLayer() 提取 sprite/frame 数据  │
│  Renderer.drawCharacter() 在 sprite 为 null 时直接 return         │
│                                                                  │
│  推演：                                                          │
│  Q1: Renderer 收到的 sprite 数据格式是否正确？                      │
│      → ❌ Character.currentAnimation.spriteSheet 为空字符串        │
│      → 空字符串 || null → null → drawCharacter 直接 return        │
│  Q2: Character.render() 是否被调用？                               │
│      → ❌ 从未被调用，SceneManager 绕过了它                        │
│  结论：🔴 两条渲染管线完全断裂，需统一为一条                          │
└──────────────────────────────────────────────────────────────────┘
```

### Step 2：上下文消融推演

对 Step 1 列出的每个交互点，执行上下文消融推演。

**推演方法**：以请求/操作为单位，从入口到出口逐步推演，对每个环节询问以下问题：

```
┌─────────────────────────────────────────────────────────────────┐
│  环节 N：[环节名称]                                                │
├─────────────────────────────────────────────────────────────────┤
│  Q1: 这个环节成功时，下一环节的输入是否仍然有效？                    │
│      → [检查：是否存在时间窗口问题？数据是否已过期？]                │
│                                                                  │
│  Q2: 这个环节失败时，前置环节消耗的资源是否需要回滚？                │
│      → [检查：限流配额是否已扣减但未使用？锁是否已获取？]             │
│                                                                  │
│  Q3: 这个环节的执行结果，是否需要通知上游/下游的其他子系统？          │
│      → [检查：多个限流器之间是否需要状态同步？缓存是否需失效？]       │
│                                                                  │
│  Q4: 如果这个环节被并发执行，结果是否可预测？                       │
│      → [检查：是否有竞态条件？是否有"先到先得"假设？]                │
│                                                                  │
│  Q5: 这个环节假设的前提，在运行时是否一定成立？                      │
│      → [检查：假设"上游已通过检查"、"数据已存在"、"状态未过期"等]    │
└─────────────────────────────────────────────────────────────────┘
```

**推演输出**：对每个交互点，给出结论：

```
  [交互点描述]
  推演结论：
    ✅ / ⚠️ / 🔴  [通过 / 有风险需记录 / 有隐患需修复设计]
    [如非 ✅，说明具体问题和建议]
```

**前端交互点额外推演**：当交互点涉及渲染管线、初始化时序、UI 状态同步或事件流时，额外询问：

- **渲染管线**：管线的每一层是否都收到了它期望格式的数据？不存在 sprite/image 时是否有 fallback？两条渲染路径是否可能同时绘制到同一上下文导致闪烁或覆盖？
- **初始化时序**：被依赖方是否一定在依赖方之前完成初始化？是否存在异步加载导致的时序竞争？
- **UI 状态同步**：多个持有者对同一状态的更新是否会冲突？更新是单向传播还是双向同步？一方更新后另一方是否能感知？
- **事件流**：事件的发布者是否在订阅者完成注册之后才开始发送？是否有事件丢失的场景？事件处理是否可能引起循环触发？

### Step 3：多策略一致性检查（当涉及多个限制/守卫层时必做）

当新设计中存在**多个策略层/守卫层**作用于同一操作路径时（例如：全局限流 + 资源限流、多层校验、多层缓存），必须检查各层之间的一致性。

**检查矩阵**：

```
┌──────────────────────┬──────────────────┬──────────────────┬──────────┐
│  一致性维度            │ 层 A (如全局)    │ 层 B (如资源)    │ 结论      │
├──────────────────────┼──────────────────┼──────────────────┼──────────┤
│  生效/解除周期         │ [周期描述]       │ [周期描述]       │ 一致/不一致│
│  状态传播              │ B 失败时 A 是否  │ A 失败时 B 是否  │ 是否闭环  │
│                      │ 感知并回滚？     │ 感知？           │          │
│  资源消耗              │ 本层消耗的资源   │ 本层消耗的资源   │ 是否存在  │
│                      │                 │                  │ 浪费链    │
│  执行顺序              │ [先/后]         │ [先/后]          │ 是否合理  │
│  错误隔离              │ 本层失败对下游   │ 本层失败对上游   │ 是否分级  │
│                      │ 的影响          │ 的影响           │          │
└──────────────────────┴──────────────────┴──────────────────┴──────────┘
```

**关键判断**：如果"状态传播"不是闭环（即某层失败后，其他层无法感知并回收已消耗的资源），且"生效/解除周期"不一致，则**必然存在资源浪费隐患**。

**典型反例**（你遇到的限流问题）：

```
  请求进入 → 全局限流检查(通过, 配额-1) → 资源限流检查(拒绝, 无法执行)
  → 全局限流配额已扣减, 但本次操作实际未执行 → 配额浪费
  
  根因：两个限流器周期不一致, 且全局限流器不感知资源限流器的状态
```

**修复方向**（在设计文档中记录，具体实现留给 DEV）：
1. **状态感知**：外层检查前先查询内层状态，跳过已受限的资源
2. **事务回滚**：内层拒绝时通知外层回收配额
3. **统一周期**：将两个限流器的解除周期对齐
4. **合并检查**：将多层限流合并为单一的复合限流判定

## 三、自检结果输出

自检结果直接记录在当前需求的设计文档中，在"风险与应对"章节之前插入：

```markdown
## 自检结果

### 交互点

| 已有功能 | 共享元素 | 交互方式 | 推演结论 |
|----------|----------|----------|----------|
| 资源限流 | 同一请求链路 | 顺序执行(先全局后资源) | ⚠️ 解除周期不一致 → 配额浪费 |

### 发现的问题

1. ⚠️ / 🔴 [问题简述]
   - 场景：[触发条件]
   - 影响：[后果描述]
   - 建议：[修复方向概述]

### 无问题的交互点（可选）

- 交互点 X：推演无风险，省略
```

**无交互点时**：简写为 `自检结果：本设计与已有功能无明显交互点，跳过推演。`

---

## 四、自检的边界

自检的目的是**在设计阶段发现设计缺陷**，不是为了穷举所有可能的运行时问题。以下内容不在此检查范围内：

- 分布式事务的最终一致性细节（属于 DEV 实现阶段的考虑）
- 操作系统/网络层面的极端故障（如进程崩溃、网络分区）
- 需要性能压测才能发现的瓶颈

自检聚焦于**单机/单进程内、逻辑层面、可在设计层面推演**的一致性问题。

---

## 五、自检结果进入 Phase 3 反馈

自检发现的问题在 Phase 3（讨论与确认）中向用户主动提出：

> 在设计自检中，发现 [需求 X] 与已有功能 [功能 Y] 存在交互隐患：[简述问题]。建议在方案中增加 [修复方向]。你觉得这个方向可以吗？还是你有其他考虑？

用户确认后，更新设计文档的对应章节（核心流程或风险应对）。
