# 功能设计流程

> **前提**：本流程由 SKILL.md 场景路由触发。适用于 PM 归档为新功能/迭代增强的场景。CTO 角色为**架构师**。
>
> **核心范式**：一次只深耕一条需求。同会话内不再逐条循环处理多条 L2/L3——每会话锁定一条（或一组强相关簇）做透，归档后引导 `/new` 开新会话处理下一条。详见 SKILL.md 核心原则。

---

## 第一步：扫描与准备

### 1.1 理解项目现状

需要理解现有代码时，委托 engine 探索（结果通过全局缓存复用）：
```powershell
$rdd = (Get-ChildItem (git rev-parse --show-toplevel) -Recurse -Directory -Depth 3 -Filter 'rdd-engine' | Select-Object -First 1).FullName; & "$rdd\scripts\explore.cmd" -Type explore -Query "分析当前需求涉及的代码模块和现有架构"
```

深度阅读项目代码，理解现有架构。参照 `code-quality-assessment.md` 评估代码质量问题。需要项目上下文时通过 rdd-engine 获取。

### 1.2 需求分级

逐条阅读 PM 归档的需求文件，按以下标准判定等级：

| 等级 | 判定条件 | 典型场景 |
|------|----------|----------|
| **L1 简单** | 全部满足：≤ 3 个文件改动；无外部依赖引入；无需技术选型；无需数据模型变更（或仅新增表） | Bugfix、单文件改动、配置调整 |
| **L2 标准** | 任一满足：跨 3+ 文件或模块；需接口或数据模型变更；涉及多需求依赖协调 | 新增功能、API 改造、多模块联动 |
| **L3 复杂** | 任一满足：需引入新框架/中间件/库；涉及架构层面重构；多需求强耦合或循环依赖；影响核心业务流程 | 架构重构、引入消息队列、核心流程改造 |

分级结果按 `design-guide.md` 的"分级结果呈现格式"展示。

### 1.3 确定依赖顺序

分析各需求之间的依赖关系，确定处理顺序。被依赖的需求先设计。依赖序用于两处：① L1 分流（行政动作，见 1.4）；② 锁定推荐（见 1.5）。

### 1.4 L1 快速分流（锁定前的一次性行政动作）

将所有 L1 需求**一次性**输出快速结论（按 `design-guide.md` 的"L1 快速结论格式"），在 `task.md` 路由总览中把对应行的 `当前责任人` 直接改为 DEV。

> L1 无需技术设计、不占深耕额度。这一步是开工前的清理动作，不违背"一次一条"原则——深耕只针对 L2/L3。

### 1.5 锁定单条（核心步骤）

分流完 L1 后，剩余的 L2/L3 中锁定**一条**作为本次会话的深耕对象：

**a. 列出剩余 L2/L3**：把所有待设计的 L2/L3 需求列给用户。

**b. 强相关簇识别（可选合并）**：若多条需求构成强相关簇，可作为"一个单元"合并锁定。判定三信号（综合判断，任一显著命中即可建议合并）：
- PM 在 `task.md` 备注栏显式标注的复合需求（如"复合需求，CTO+UX 并行"）
- 需求文件自身的「依赖关系」字段指向彼此
- 预估涉及文件/模块高度重叠（同一批文件被多条需求改动）

**c. 推荐 + 请求确认**（话术模板）：

```
本次待设计的 L2/L3 需求：
  • [标题 A]（L2）— [一句话]
  • [标题 B]（L3）— [一句话]

我推荐先做 [标题 X]，因为 [依赖根 / 优先级高 / 阻塞其他需求]。
[若识别到强相关簇：标题 B 与 标题 C 共享 XX 模块、依赖关系紧密，建议作为一组一起做。]

本次专注这一条（或这一组），其余留到后续会话。
是否确认锁定 [标题 X]？
```

**d. 锁定后的约束**：
- 只读锁定需求的内容，不混入其他需求
- **中途换条规则**：尚未归档草稿 → 可放弃、重新锁定另一条（告知用户即可）；一旦写盘归档 → 本次需求闭环，不换条，想改走驳回流程

---

## 第二步：设计锁定需求

> 以下流程只针对 1.5 锁定的那一条（或强相关簇）。不再循环回其他需求。

### 2.1 读取本条需求

只读当前锁定的需求文件。强相关簇模式下读完整簇，但作为一个整体设计。

### 2.2 前序设计影响扫描（替代旧的交叉校验）

同会话内不再做多条需求的交叉校验。改为**设计前**主动感知同归档内已完成的其他设计是否影响本次：

**a. 找出已完成的设计**：扫描 `task.md` 路由总览，找同归档内 `关联设计文档` 已填真实路径（非 `(待产出)` 占位）、且 `当前责任人` 已越过设计阶段的行。

**b. 三信号判断是否影响**（对每条已完成设计评估）：
- PM 路由备注标注与当前需求复合/关联
- 当前锁定需求文件「依赖关系」字段指向该需求
- 该前序设计的「变更地图」（涉及文件、模块归属、接口契约）与本次预估涉及范围有重叠

**c. 分流处理**：
- 命中任一信号 → **可能有影响**：先读该设计文档，把其方向（技术选型、模块归属、关键接口、配置方案）作为本次设计的**约束输入**
- 全不命中 → 无影响，跳过

**d. 若发现冲突**（前序方向与本次需求存在矛盾）：按 `rdd-engine/references/rejection-protocol.md` 正式反馈，不私下妥协或绕过。

> 这一步确保跨批次、跨会话完成的设计之间保持一致，弥补单条深耕模式下"内存中跨需求校验"的缺失。

### 2.3 深度分析（按需）

- **L2 需求**：加载 `analysis-l2.md`，执行可行性评估 + 依赖分析
- **L3 需求**：先加载 `analysis-l3.md`，执行完整三维分析
- **涉及技术选型**（L2/L3 需引入新框架/中间件/库）→ 加载 `industry-research.md` 执行业界调研

### 2.4 技术方向设计（5 问）

**加载 `design-guide.md`**（获取决策点格式、ASCII 图表库、技术方向文档模板）。

按 5 问框架逐层设计：
1. **技术选型**（用什么？）→ 最大的方向先敲定
2. **模块归属**（放哪里？）→ 放在哪个模块/包，是否新建
3. **关键要素**（叫什么？）→ 要建的类/接口名、文件位置、职责
4. **配置方案**（怎么配？）→ 配置方式、配置项
5. **涉及文件**（改哪些？）→ 新建 + 修改的文件清单

### 2.5 自检

L2/L3 设计完成后 → 加载 `self-check.md` 执行自检三步（交互点识别 → 冲突推演 → 多策略一致性检查）。

> 自检聚焦"当前需求 vs 已有代码库"。跨需求一致性已在 2.2 前序扫描中处理，自检不重复做。

### 2.6 逐决策点对话确认

**一次只抛出一个决策点**，按 `design-guide.md` 的决策点话术格式：

```
"需求 X 需要解决 Y 问题。我建议 [方案]，因为 [理由]。
对于 [不适用场景]，可以 [兜底策略]。你觉得这个方向可以吗？"
```

推荐推进顺序（先方向后细节）：
1. Round 1：技术选型
2. Round 2：模块归属
3. Round 3：关键要素（类/接口名、涉及文件）
4. Round 4：风险与取舍（含 2.5 自检发现的问题）

**用户确认一个 → 填入设计文档 → 推进下一个。**

### 2.7 确认完成 → 立即写设计文档

全部决策点确认后，**立即**写入设计文档和附带产物：
- 主体文档：`design/{需求文件名}-cto.md`（需求文件名从 `task.md` 获取，去掉 `.md` 后缀），按 `design-guide.md` 的"技术方向文档模板"
- 附带产物：`design/{需求文件名}-cto-decisions.md`，按模板写入决策记录和风险提示

---

## 第三步：归档（单条）

本条（或强相关簇）确认并写入完成后：

1. 更新 `task.md` 路由总览：本次完成的需求行，`当前责任人` 改为 DEV（或 UX），`关联设计文档` 追加自身设计文档路径（与单元格已有路径 `+` 连接、去重，移除 `(待产出)` 占位，不覆盖他人路径）
2. 告知用户文件位置（单条收尾，不做"全部需求总览"汇总——自检即闸门）

---

## 第四步：引导下一步（/new 分支）

按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（更新路由 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

**推荐角色分支**（由 `next` 输出决定）：
- **CTO 仍有待办**（`next` 显示 CTO `taskCount > 0`）→ 推荐重入 CTO（新会话）处理下一条 L2/L3。话术补充："本条已闭环，CTO 还有 N 条待设计，建议 `/new` 开新会话继续。"
- **CTO 已清空** → 交下游（UX 并行 / DEV），按 transition-guide 正常推荐

> 完整流程、模式检测、同会话切换规则见 `rdd-engine/references/transition-guide.md`。

---

## 对话风格

- **一次一条需求、一次一个决策点**
- 方案中如果做了假设，明确标注
- 给方案时说清楚理由——不只是"建议用 Redis"，而是"建议用 Redis，因为缓存场景下读写性能是关键瓶颈，而 Redis 在你们当前基础设施里已经有了"
