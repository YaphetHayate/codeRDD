# 功能设计流程

> **前提**：本流程由 SKILL.md 场景路由触发。适用于 PM 归档为新功能/迭代增强的场景。CTO 角色为**架构师**。
>
> **核心范式**：一次只深耕一条需求。同会话内不再逐条循环处理多条 L2/L3——每会话锁定一条（或一组强相关簇）做透，归档后引导 `/new` 开新会话处理下一条。详见 SKILL.md 核心原则。

---

## 第一步：扫描与准备

> **入口适配**：TaskId / Handoff 单条模式（A0，"一需求一会话"）下，本会话只处理指针指向的任务——分级照常内做（命中 L1 → 按快速结论发开发，本会话即收尾），但**不做全量 L1 分流与锁定推荐**（1.4 / 1.5 面向多任务会话：A/D 模式下 `show` 列出多条 CTO 待处理时的场景）。

### 1.1 理解项目现状

需要理解现有代码时，委托 engine 检索缓存（结果通过全局缓存复用，热区优先）：
```powershell
$rdd = $null; $t = $null; try { $t = git rev-parse --show-toplevel } catch { }; foreach ($c in @($env:RDD_ENGINE_HOME; if ($t) { (Get-ChildItem $t -Recurse -Directory -Depth 3 -Filter 'rdd-engine').FullName }; "$HOME\.rdd\engine\current")) { if ($c -and (Test-Path "$c\scripts\rdd-flow.cmd")) { $rdd = $c; break } }; if (-not $rdd) { throw "rdd-engine 未定位（三级定位链：RDD_ENGINE_HOME → 项目内 rdd-engine → ~\.rdd\engine\current 全 miss）。安装/排障：GitHub Release 下载 rdd-engine.tgz 后运行 scripts/install-rdd-engine.ps1；协议详见 rdd-engine/references/engine-location.md" }; & "$rdd\scripts\explore.cmd" -Type search -Query "分析当前需求涉及的代码模块和现有架构"
```

深度阅读项目代码，理解现有架构。参照 `code-quality-assessment.md` 评估代码质量问题。需要项目上下文时通过 rdd-engine 获取。

### 1.2 需求分级（内部分工判断）

逐条阅读 PM 归档的需求文件，按以下标准判定等级：

| 等级 | 判定条件 | 典型场景 |
|------|----------|----------|
| **L1 简单** | 全部满足：≤ 3 个文件改动；无外部依赖引入；无需技术选型；无需数据模型变更（或仅新增表） | Bugfix、单文件改动、配置调整 |
| **L2 标准** | 任一满足：跨 3+ 文件或模块；需接口或数据模型变更；涉及多需求依赖协调 | 新增功能、API 改造、多模块联动 |
| **L3 复杂** | 任一满足：需引入新框架/中间件/库；涉及架构层面重构；多需求强耦合或循环依赖；影响核心业务流程 | 架构重构、引入消息队列、核心流程改造 |

分级是**内部分工判断**，不是对用户的呈现产物——它只回答"哪些需求不值得开完整设计"。用户看到的是分级的**后果**：1.4 的分流清单（每条一句"为什么不用设计"）与 1.5 的锁定推荐，而不是一张 L1/L2/L3 标签表。用户追问分级依据时，按 `design-guide.md` 的"分级标准（内部判据）"解释。

### 1.3 确定依赖顺序

分析各需求之间的依赖关系，确定处理顺序。被依赖的需求先设计。依赖序用于两处：① L1 分流（行政动作，见 1.4）；② 锁定推荐（见 1.5）。

### 1.4 L1 快速分流（锁定前的一次性行政动作）

将所有 L1 需求**一次性**输出快速结论（按 `design-guide.md` 的"L1 快速结论格式"——面向用户讲清每条"为什么不用设计、直接发开发"的理由），逐条调用 rdd-flow `set-route -To DEV -Phase IMPL` 直接发开发（无设计文档则跳过 add-design）。

> L1 无需技术设计、不占深耕额度。这一步是开工前的清理动作，不违背"一次一条"原则——深耕只针对 L2/L3。

### 1.5 锁定单条（核心步骤）

分流完 L1 后，剩余的 L2/L3 中锁定**一条**作为本次会话的深耕对象：

**a. 列出剩余 L2/L3**：把所有待设计的 L2/L3 需求列给用户。

**b. 强相关簇识别（可选合并）**：若多条需求构成强相关簇，可作为"一个单元"合并锁定。判定三信号（综合判断，任一显著命中即可建议合并）：
- PM 在 `task.json` remark 字段标注的复合需求（如"复合需求，CTO+UX 并行"）
- 需求文件自身的「依赖关系」字段指向彼此
- 预估涉及文件/模块高度重叠（同一批文件被多条需求改动）

**c. 推荐 + 请求确认**（话术模板）：

```
本次待设计的需求：
  • [标题 A] — [一句话]
  • [标题 B] — [一句话]

我推荐先做 [标题 X]，因为 [依赖根 / 优先级高 / 阻塞其他需求]。
[若识别到强相关簇：标题 B 与 标题 C 共享 XX 模块、依赖关系紧密，建议作为一组一起做。]

本次专注这一条（或这一组），其余留到后续会话。
是否确认锁定 [标题 X]？
```

**d. 锁定后的约束**：
- 只读锁定需求的内容，不混入其他需求
- **中途换条规则**：尚未归档草稿 → 可放弃、重新锁定另一条（告知用户即可）；一旦写盘归档 → 本次需求闭环，不换条，想改走驳回流程

## 第二步：设计锁定需求

> 以下流程只针对 1.5 锁定的那一条（或强相关簇）。不再循环回其他需求。

### 2.1 读取本条需求

只读当前锁定的需求文件。强相关簇模式下读完整簇，但作为一个整体设计。

### 2.2 前序设计影响扫描（替代旧的交叉校验）

同会话内不再做多条需求的交叉校验。改为**设计前**主动感知同归档内已完成的其他设计是否影响本次：

**a. 找出已完成的设计**：调用 rdd-flow show 查看同归档内 designDocs 条目 `status=ready`（非 `pending` 占位）、且任务路由已越过设计阶段的行。

**b. 四信号判断是否影响**（对每条已完成设计评估）：
- **信号 0（强制约束输入，优先于以下三信号）**：桥接 run 注入的「架构约定」——DESIGN 链头 node.task 中「架构约定：<path>」指向的 `report/architecture-conventions.md`（多 CTO/UX 并行设计的共同基线，promulgate `-ConventionsFile` 注入）：本次设计**必须遵循**该套架构/风格约定；无此注入（单设计/串行设计/非桥接 run）则跳过本信号
- PM 路由备注标注与当前需求复合/关联
- 当前锁定需求文件「依赖关系」字段指向该需求
- 该前序设计的「变更地图」（涉及文件、模块归属、接口契约）与本次预估涉及范围有重叠（注意变更地图文件行的机读契约：`` `仓库根相对完整路径` [op] 说明 ``，见 design-guide「变更地图」）——本信号在现状分析（2.3b）之前只能粗判，拿不准的**先挂起、待 2.3b 现状摘要完成后复核一次**再定，不在信息不足时硬判

**c. 分流处理**：
- 命中任一信号 → **可能有影响**：先读该设计文档，把其方向（技术选型、模块归属、关键接口、配置方案）作为本次设计的**约束输入**
- 全不命中 → 无影响，跳过

**d. 若发现冲突**（前序方向与本次需求存在矛盾）：按 `rdd-engine/references/rejection-protocol.md` 正式反馈，不私下妥协或绕过。设计互斥**不得默默二选一**：调和出一致结论（更新设计产物并同步前序侧）或上报用户裁决——编排层冲突治理协议见 `rdd-engine/references/planner-scenarios.md`「并行协作冲突治理细则」。

> 这一步确保跨批次、跨会话完成的设计之间保持一致，弥补单条深耕模式下"内存中跨需求校验"的缺失。

### 2.3 需求解读与现状分析（功能点清单）

> L2/L3 的差异只体现在本节分析的**深度**与 2.4 评估的维度数，不再有独立的"可行性评估"前置步骤——可行性评估的对象是**方案**，发生在候选方案形成之后（2.4c）。连方案都没有就做"可行性分析"是流程违规。

**a. 需求解读**：用自己的话复述这条需求要解决什么、验收标准是什么——1~3 句白话，不堆术语。发现需求本身有歧义、矛盾或缺失验收标准时，先向用户提**针对性澄清问题**（白话、具体），不带方案；无疑义则不打断，继续 b。

**b. 现状分析**：围绕**本条需求**检索并阅读相关代码（检索方式同 1.1 的 explore 命令，Query 聚焦锁定需求涉及的模块/数据流），产出「现状摘要」：相关模块与数据流、项目里已有的类似实现/既有模式、可直接复用的部分——**每条附文件证据（路径）**。现状摘要向用户展示：它既是方案的事实底座，也是"CTO 真的看过代码"的置信度来源。

**c. 功能点清单**：把需求翻译成「为实现该需求必须建立/改动的功能点」清单——白话描述、不引入实现技术名词，每条可追溯到验收标准。这份清单是需求与方案之间的桥：2.4 的方案必须逐点覆盖它，用户也靠它判断方案是否跑偏。

**d. 合成呈现**：a+b+c 不单独打断用户，作为 2.4e 方案呈现的开头部分（需求解读 → 现状摘要 → 功能点清单）一并给出，构成一条线性叙事。

### 2.4 方案设计与评估（先方案、后评估）

**加载 `design-guide.md`**（决策点纪律、ASCII 图表库、技术方向文档模板）。

**a. 方案调研（每次必做，分两级）**：加载 `industry-research.md`。第一级**知识内核对**每次必做：识别本需求对应的经典设计模式与业界通用做法（缓存旁路、发布订阅、重试退避、Repository……），点名模式 + 说明在本项目的适配理由——空口方案没有置信度，用户无法决策。第二级**检索式调研**按触发条件执行（引入新技术 / 已有知识不足高置信 / 多个成熟候选且影响显著，任一命中即搜）。

**b. 候选形成**：基于功能点清单 + 调研依据形成候选方向。**无真实分叉时只形成一个候选**——禁止为"显得客观"凑陪跑候选（陪跑检验见 `design-guide.md` 决策点纪律）。

**c. 方案级评估（可行性评估在这一步，不在方案之前）**：
- **L2 需求**：加载 `analysis-l2.md`，对**每个候选**执行可行性/影响/风险评估
- **L3 需求**：加载 `analysis-l3.md`，对每个候选执行完整维度评估（多需求依赖图服务于第一步排序，已绘制且仍准确则沿用，不重画）

**d. 推荐方向 + 5 问展开**：胜出候选按 5 问框架逐层落定：
1. **技术选型**（用什么？）→ 最大的方向先敲定
2. **模块归属**（放哪里？）→ 放在哪个模块/包，是否新建
3. **关键要素**（叫什么？）→ 要建的类/接口名、文件位置、职责
4. **配置方案**（怎么配？）→ 配置方式、配置项
5. **涉及文件**（改哪些？）→ 新建 + 修改的文件清单

**e. 方案呈现（一次讲完）**：把 2.3 的 digest（需求解读 → 现状摘要 → 功能点清单）与方案（调研依据 → 推荐/候选对比 → 5 问结论 → 风险）合成**一条线性叙事**呈现。存在真实分叉时，分叉点按 `design-guide.md` 多方案决策点格式单独抛出（一次一个）；无分叉时按单方案推荐格式做一次方向确认。

### 2.5 自检机制（增量预扫 + 末尾完整）

自检不再在"设计完成后一次性执行"。改为**两段式**，与下方四检查点推进模型耦合。两段都发生在 **2.4e 方案呈现之前**（内部分析环节，不是呈现后的补查）——完整推演的产物（冲突判定、风险点）直接进入同一次呈现的「风险」部分，不在呈现后再向用户补报：

- **轻量预扫**（检查点 ①②③ 各自达标后）：只做交互点识别的快速版——标记本次设计可能与已有代码产生交互的模块/数据/路径，**不展开推演**。产物是一份逐步累积的"交互点清单"。
- **完整推演**（检查点 ④）：执行自检三步法（交互点识别 → 冲突推演 → 多策略一致性检查），把前面预扫标记的所有交互点逐一推演，输出冲突判定与修复方向。

> 预扫不能替代完整推演。检查点 ④ 跳过完整推演属于流程违规。方法论与边界见 `self-check.md` 第一节。
>
> 自检聚焦"当前需求 vs 已有代码库"。跨需求一致性已在 2.2 前序扫描中处理，自检不重复做。

### 2.6 四检查点推进模型

> **核心心智**：四个检查点是**内部分析完备性门槛**，不是四个用户打断点。主流程线性走完（2.3 解读/现状 → 2.4 方案/评估 → 2.5 自检），检查点在内部逐一达标；**用户决策只出现在"真实分叉"与"该用户兜底的风险取舍"两类时刻**——其余环节属专业判断，CTO 自主定、留痕即可，不制造决策点。为了决策而决策是流程违规。

#### 四个检查点

| 检查点 | 内容 | 内部门槛（全勾齐才达标） | 谁拍板 |
|--------|------|--------------------------|--------|
| **① 技术选型** | 用什么框架/库/中间件 | □ 依据链完整（业界依据：设计模式/成熟方案/调研来源 + 项目依据：现状文件/已有模式）<br>□ 三维理由（架构优劣 / 业务匹配 / 框架兼容性）<br>□ 兜底策略（不适用场景如何降级）<br>□ 有真实分叉：候选全量对比（每个候选通过陪跑检验）；无分叉：写明为何单一可行 | **真实分叉**（多条路线都成立、选择改变后续走向）或引入新依赖/成本影响 → 用户拍板；单一可行 → CTO 定，随 2.4e 方向确认一次带过 |
| **② 模块归属** | 放在哪个模块/包 | □ 归属理由（为何放在此模块而非别处）<br>□ 职责单一（与现有模块职责无重叠）<br>□ 无循环依赖 | **CTO 专业判断**：自主定 + `*-decisions.md` 留痕（用户异议随时推翻） |
| **③ 关键要素** | 类/接口名、文件位置、职责 | □ 命名 + 位置 + 职责（单一职责）<br>□ 文件清单完整（新建 + 修改全覆盖）<br>□ 配置项已识别 | **CTO 专业判断**：自主定 + 留痕（同上） |
| **④ 风险取舍** | 改哪些 + 风险与回退判定 | □ 完整自检三步法已执行（含前面所有预扫交互点）<br>□ 风险分级（P1/P2/P3）+ 应对方向<br>□ 前置 ①②③ 无残留缺口 | **P1 / 不可逆 / 成本类风险 → 用户确认**；P2/P3 → 记入风险提示即可 |

（自检两段式与检查点的耦合不变：①②③ 各自达标后轻量预扫，④ 完整推演——见 2.5 与 `self-check.md` 第一节。）

#### 推进规则

**推进条件 = 内部门槛全勾齐 + 属用户拍板域的项已拍板**，两者缺一不可：

- 默认交互形态：**线性分析一次走完，最后一次性呈现**「推荐方案 + 依据链 + 风险清单」向用户做方向确认，中间不打断。分叉/高风险项才拆出独立决策点，且**一次只抛一个**。
- **决策点排序**：叙事呈现后，按「分叉 → 高风险取舍」顺序逐个抛出决策点（抛一个、收一个）；全部拍板后做一次**收束的方向确认**。若最后一个决策点本身已等价于方向确认（如"选 A 还是 B"直接决定方案走向），两者合并，不再重复确认。
- 抛给用户的决策点必须符合 `design-guide.md`「决策点纪律」：讲清**决策目的**（为什么需要你定、定错了影响什么）、**白话表达**（术语跟一句解释）、**选项后果具体**（选了会发生什么，用改动范围/依赖/风险描述，不用空泛形容词）。
- "用户拍板"只是闸门的一部分，**不是闸门本身**。门槛未达标时，即使用户催促推进，也要先补齐——向用户说明还差哪一项。
- 纯自动模式（planner-auto-mode）下，"用户拍板"按 SKILL.md「完成前置硬检查」的分级表代答/升级执行，本节拍板域划分不变。

#### 回退机制（显式回退，禁止私下补丁硬推）

后续检查点发现前置决策有缺口时（典型场景：④ 完整推演暴露出 ① 选型未考虑某交互、或 ③ 文件清单漏掉了某个被波及的文件），**禁止**为保持流程"线性"而就地打补丁、掩盖缺口硬推下去。

回退按**是否触及已拍板决策**分两类：

- **内部回退**（缺口涉及的决策尚未经用户拍板——默认单次呈现模型下，呈现之前发现的缺口都属此类）：直接补强 + 记入回退记录区，**不打断用户**，补强结果随 2.4e 呈现自然体现
- **推翻已拍板决策**（该决策已经用户确认，或纯自动模式下已代答入账）：必须**显式回到用户**——在对话中声明回退并请求重新裁定（纯自动模式按 SKILL.md「完成前置硬检查」调用 `escalate` 升级等待）；同样记入回退记录区

两类回退都记入 `*-decisions.md` 的"回退记录"区（格式见 `design-guide.md`）：

```
回退声明：
  当前检查点：④（风险推演）
  发现前置缺口：检查点 ①（技术选型）未考虑 [X 交互]
  回退到：检查点 ①
  原因：[缺口简述，为何波及后续]
  后续动作：补强 [X] → 重新沿链推进
```

**回退后重新推进的连带校验**：补强缺口后，**已达标的后置检查点也需重新校验**是否被本次补强波及。例如 ① 选型改动后，② 的模块归属、③ 的文件清单都要复核——不能假设"之前达标就永远达标"。复核结果一并记入回退记录。

### 2.7 确认完成 → 立即写设计文档

全部决策点确认后，**立即**写入设计文档和附带产物：
- 主体文档：`design/{需求文件名}-cto.md`（需求文件名从 `task.json` 获取，去掉 `.md` 后缀；`design/` 目录不存在则创建），按模板文件 `../design-template.md` 落盘——该文件是变更地图机读契约真源（引擎 delivery-bridge / planner-scenarios 均以它为准），格式说明见 `design-guide.md`
- 附带产物：`design/{需求文件名}-cto-decisions.md`，按模板文件 `../design-decisions-template.md` 写入决策记录、回退记录和风险提示

## 第三步：归档（单条）

本条（或强相关簇）确认并写入完成后：

1. 本条经用户确认的检查点决策（选型/取舍/方案定稿）入统一决策账本留痕：`delivery-bridge.cmd -Command decide -Kind checkpoint -Archive <归档> -Checkpoint <名> -Decision <结论> [-Reason] [-Options <A|B>] [-Background] [-Role CTO]`
2. 调用 rdd-flow add-design 追加设计文档路径，然后 `set-route` 推进路由（见 rdd-engine/references/task-routing.md）——**收窄/汇聚语义**：本任务还有其他设计阶段角色（并行的 UX，或串行计划中的 UX/QA 测试先行）→ `set-route -To "<剩余角色集>"` 阶段内收窄（不带 `-Phase`）；自己是最后一个 → `set-route -To "DEV" -Phase IMPL` 汇聚切换
3. 告知用户文件位置（单条收尾，不做"全部需求总览"汇总——自检即闸门）

## 第四步：引导下一步（/new 分支）

按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（更新路由 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

**推荐角色分支**（由 `next` 输出决定）：
- **CTO 仍有待办**（`next` 显示 CTO `taskCount > 0`）→ 推荐重入 CTO（新会话）处理下一条 L2/L3。话术补充："本条已闭环，CTO 还有 N 条待设计，建议 `/new` 开新会话继续。"
- **CTO 已清空** → 交下游（UX 并行 / DEV），按 transition-guide 正常推荐

> 完整流程、模式检测、同会话切换规则见 `rdd-engine/references/transition-guide.md`。

## 对话风格

- **一次一条需求、一次一个决策点**（决策点只在该抛的时候抛，见 2.6）
- **说人话**：面向用户的输出里，首次出现的术语必须跟一句白话解释，或直接换成白话说法（判定标准与示例见 `design-guide.md` 术语纪律）
- **优缺点必须有证据**：写不出具体出处（项目文件 / 依赖行为 / 调研来源）的优缺点不许列——空泛形容词堆砌等于没有，用户无法据此决策
- 方案中如果做了假设，明确标注
- 给方案时说清楚理由——不只是"建议用 Redis"，而是"建议用 Redis，因为缓存场景下读写性能是关键瓶颈，而 Redis 在你们当前基础设施里已经有了"
