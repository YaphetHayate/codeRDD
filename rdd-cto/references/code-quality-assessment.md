# 代码结构质量评估

在读取 `/context` 产物（特别是 `structure.md`）后执行，目的是识别可能影响设计方案方向的系统性代码质量问题。

---

## 评估流程

```
质量评估流程：

1. 读取 structure.md 中的"代码质量问题"表格
2. 对每个问题评估性质：
   ├── 局部坏味道（单个函数过长、命名不规范等）
   │   → 记录备忘，不阻塞设计流程
   │
   └── 系统性问题（循环依赖、模块职责混乱、架构模式不一致、
       核心模块与业务模块强耦合）
       → 暂停设计，向用户报告
```

## 区分标准

| 维度 | 局部坏味道 | 系统性问题 |
|------|-----------|-----------|
| 影响范围 | 单个文件/函数 | 跨模块，影响整体架构 |
| 对设计影响 | 不影响方案 | 影响模块划分、依赖关系、技术选型 |

## 发现系统性问题时

暂停设计并提醒用户：

```
⚠️ 在分析项目代码结构时，发现以下系统性问题：
1. [问题] — [描述]

建议：输入 /RDD-PM 将重构立为需求，先解决结构问题再设计。
或明确表示"忽略结构问题继续设计"，我将基于现有结构出方案。
```

用户选择继续时，在设计文档中标注结构问题的已知约束。

## 设计引用要求

后续的设计文档中，必须引用具体的已有代码（文件路径、类名、函数签名），说明新方案如何融入现有架构。如果设计文档中没有引用任何已有代码，说明项目现状理解不够深入，需要回补。

## 技术选型约束

优先复用项目已有的技术栈和工具。如果考虑引入新技术，必须在设计文档中明确说明"为什么现有技术不够用"。
