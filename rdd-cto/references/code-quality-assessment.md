# 代码与设计质量评估

在读取 `/context` 产物（特别是 `structure.md`）后执行，同时结合 PM 需求文档和用户提出的实现设想，识别可能影响设计方案方向的系统性代码质量问题与设计坏味道。

---

## 评估流程

```
质量评估流程：

1. 读取 structure.md 中的"代码质量问题"表格
2. 阅读 PM 需求中的"技术相关信息/用户实现设想/设计约束"（如有）
3. 对每个问题评估性质：
   ├── 局部坏味道（单个函数过长、命名不规范等）
   │   → 记录备忘，不阻塞设计流程
   │
   └── 系统性问题（循环依赖、模块职责混乱、架构模式不一致、
       核心模块与业务模块强耦合）
       → 暂停设计，向用户报告
4. 对需求或实现设想中的设计坏味道做一次筛查：
   ├── 只是可替代的实现偏好
   │   → 标注为"用户设想"，不作为强制方案
   │
   └── 会导致架构风险或维护风险
       → 主动提出，并给出更稳妥的设计方向
```

## 区分标准

| 维度 | 局部坏味道 | 系统性问题 |
|------|-----------|-----------|
| 影响范围 | 单个文件/函数 | 跨模块，影响整体架构 |
| 对设计影响 | 不影响方案 | 影响模块划分、依赖关系、技术选型 |

## 需求/方案中的设计坏味道

以下情况需要 CTO 主动指出，不应直接照单设计：

- **方案先行**：需求把具体实现方案写成目标，但没有说明要解决的问题。
- **重复造轮子**：项目已有框架、工具或模块能覆盖，却要求新建平行能力。
- **职责错位**：把业务逻辑塞进 UI、把基础设施逻辑塞进业务模块、或让某个模块承担不属于它的职责。
- **过早复杂化**：为简单需求引入中间件、服务拆分、复杂状态机或抽象层。
- **强耦合扩散**：方案要求多个无关模块互相感知内部细节。
- **绕过既有约束**：为了快速实现而破坏现有权限、安全、数据一致性、部署或可观测性机制。
- **局部修补掩盖系统问题**：需求只要求修一个表象，但代码现状显示根因是结构性问题。

发现这些问题时，不要只说"不建议"。需要说明：

1. 坏味道是什么；
2. 它会带来的具体后果；
3. 哪些需求目标仍然成立；
4. 推荐的替代设计方向；
5. 是否需要回到 PM 澄清需求，或由用户确认接受该风险继续设计。

## 发现系统性问题时

暂停设计并提醒用户：

```
⚠️ 在分析项目代码结构时，发现以下系统性问题：
1. [问题] — [描述]

建议：输入 /RDD-PM 将重构立为需求，先解决结构问题再设计。
或明确表示"忽略结构问题继续设计"，我将基于现有结构出方案。
```

用户选择继续时，在设计文档中标注结构问题的已知约束。

## 发现需求中的设计坏味道时

先把问题从"实现方案"拉回"需求目标"：

```
我注意到这个需求里有一个可能的不良设计倾向：

- 坏味道：[例如：为单一页面状态引入全局状态管理]
- 影响：[会让状态来源变多，后续调试和回归成本上升]
- 需求目标仍然是：[例如：让页面 A 和页面 B 共享筛选条件]
- 建议方向：[优先复用现有路由参数/页面状态同步机制]

你可以选择：
1. 按建议方向调整设计；
2. 保留原设想，但把相关维护风险写入设计文档。
```

## 设计引用要求

后续的设计文档中，必须引用具体的已有代码（文件路径、类名、函数签名），说明新方案如何融入现有架构。如果设计文档中没有引用任何已有代码，说明项目现状理解不够深入，需要回补。

## 技术选型约束

优先复用项目已有的技术栈和工具。如果考虑引入新技术，必须在设计文档中明确说明"为什么现有技术不够用"。
