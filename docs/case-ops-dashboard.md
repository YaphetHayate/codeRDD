# 实战案例：一天造出运营看板

> 本页记录一个真实大需求如何经 PM 拆解 → PLANNER 树编排 → 多角色协作交付。
> 数据来源：`.rdd/changes/archive/2026-10-08-rdd-ops-dashboard/` 与对应目标树
> `deliver-2026-10-08-rdd-ops-dashboard` 的结案报告。
> 演示视频：**待补充**

## 需求

做一个能看到"RDD 全流程跑得怎么样"的运营看板——把需求归档、探索缓存、命中率、tips、交付树等散落数据聚合到一个本地页面。

PM 完成需求全貌确认后拆解为两个有依赖关系的任务：

| # | 任务 | 依赖 |
|---|------|------|
| #1 | rdd_explore 查询流水记录（hit/miss 落盘，看板的数据源） | 无 |
| #2 | RDD 运营看板（零依赖 node:http 服务 + 单页前端） | #1 |

因涉及引擎改造 + 本地服务 + 前端页面，PM 判定为大任务，转交 **PLANNER** 编排。

## 编排过程

1. **建树**：PLANNER 生成 13 节点目标树，单阶段两批次——#2 命中率模块消费 #1 的流水契约，故 #1 先行、#2 在 #1 settle 后解锁；其余 5 个数据域不依赖 #1。
2. **#1 流水线**：CTO（裁定双入口覆盖 + 六字段 JSONL 契约）→ DEV（引擎检索链路 + DSH 插件双入口实现）→ QA（hit/miss 两态落盘、append-only、失败隔离验收）。
3. **#2 流水线**：CTO + UX 并行（服务架构 / 页面信息架构）→ DEV（零依赖服务 + SSR 六数据域 + 8 个 API）→ QA。
4. **事前把关**：AUDITOR 在建树前审需求集（两任务均 pass，双向映射无空洞、验收标准全为可观察输出），在设计汇聚后审跨设计一致性。
5. **集成联调**：末阶段挂集成节点，DEV 真实启动服务、做一命中一未命中两次查询、刷新看板验证命中率从 27→28→29 行真实变化。
6. **整体验收**：QA 对照 `requirements/overview.md#整体验收判据` 逐条核验真链路（判据 #1 8/8、#2 11/11），结论落盘后才结案。

## 结果

- 终局 **achieved**：单轮编排、13 节点（预算上限 17 节点 / 12 轮）
- 12 次回写回调全部 valid，引用越界 **0**，质量扫描违规 **0**
- 交付物：查询流水（双入口六字段 JSONL）+ 零依赖看板服务（6 数据域 + 8 API）
- 全程产物落盘：设计变更地图、质量凭据、验收报告、结案报告均可回溯
