# 测试设计工作流

> **前提**：本流程由 SKILL.md 执行委托触发。QA 始终基于 `requirements/` 目录的需求文档工作，**禁止读取 `design/` 目录**。

本文件描述从需求分析到测试归档的 6 个阶段。测试用例设计的方法论和模板见 `test-case-guide.md`。

**核心产物**：本流程产出两处用例资产，职责不同、必须双写：
- `.rdd/tests/{feature}/cases.md` — 功能级用例规约，**跨迭代的长期资产**（这个功能现在该测什么）
- `archive/.../tests/cases.md` — 本次变更增量，**极简时点快照**（本次动过哪些 TC）

---

## 第〇步：识别功能与读取历史用例

> 需求是按需求组织的（一次变更一个需求文件），但测试用例是按功能组织的（跨迭代长期活着）。本步建立两者的映射，避免重复设计、保留演进线索。

### 读取功能清单

读取 `.rdd/tests/index.md`（首次工作则不存在，跳过）。它列出项目已有的功能及其用例库位置。

### 为每条需求识别功能归属

逐条阅读需求，判断它属于哪个功能。判定原则：

- 需求描述的核心行为落在哪个已有功能上 → 归属该功能，**复用已有功能名**（如需求"搜索结果加分页"归属 `search`）
- 需求是全新能力，已有功能都不匹配 → **新建功能**，用 QA 淘汰式命名：先拟一个功能名，向用户确认是否合适；命名遵循 kebab-case，语义化、与被测能力对齐
- 一条需求跨多个功能 → 归到**主触发功能**（需求核心行为落在哪），其余功能用 `cross-feature` 标签关联（详见 `test-case-guide.md#功能用例库`）

将识别结果呈现给用户确认：

```
功能归属识别：

| 需求 | 功能 | 类型 | 说明 |
|------|------|------|------|
| 需求1：搜索分页 | search | 复用 | 已有 .rdd/tests/search/cases.md（5 个 active 用例） |
| 需求2：导出 Excel | export | 新建 | 全新功能，建议命名 export |
```

### 读取已有用例规约

对每个**复用型**功能，读取 `.rdd/tests/{feature}/cases.md`，重点关注：
- 已有哪些 active 用例 → 新需求可能扩展或修改它们
- 哪些 deprecated → 避免重新设计已被取代的场景
- TC 编号规则 → 新用例接着已有编号续编，保持连续

**新建型**功能没有历史，直接进入第一步。

---

## 第一步：需求分析与测试范围确定

### 提取测试要素

逐个阅读需求，从每个需求中提取以下测试要素：

1. **验收标准** — 每条直接对应至少一个测试用例
2. **用户场景** — "谁在什么情况下做什么操作、期望什么结果"就是一个测试场景
3. **边界与异常** — 需求文档中标注的空数据、极端情况、已知限制
4. **隐含约束** — 从需求描述中推断出的约束（如性能要求、并发限制）

将提取结果呈现给用户：

```
测试要素提取：

┌──────────────┬──────────────────────────────────────────────────┬─────────┐
│  需求          │ 测试要素                                          │ 数量     │
├──────────────┼──────────────────────────────────────────────────┼─────────┤
│  需求 1：XXX   │ 验收标准 3 条，用户场景 2 个，边界条件 1 个          │ 6+      │
│  需求 2：YYY   │ 验收标准 2 条，用户场景 1 个，异常场景 2 个          │ 5+      │
│  需求 3：ZZZ   │ 验收标准 1 条，边界条件 3 个                        │ 4+      │
└──────────────┴──────────────────────────────────────────────────┴─────────┘
```

### 确定测试层级

根据需求特点确定需要哪些测试层级：

| 测试层级 | 适用场景 | 依赖 |
|----------|---------|------|
| **单元测试** | 验证独立函数/模块的行为是否正确 | 需要了解代码结构 |
| **集成测试** | 验证模块间协作是否正确 | 需要了解模块边界 |
| **接口测试** | 验证 API 的输入输出是否符合预期 | 需要了解接口定义 |

告诉用户你计划写哪些层级的测试以及为什么。如果项目已有测试文件，先看现有测试层级和风格，保持一致。

## 第二步：探索项目代码结构

从"怎么测"的角度看代码，不是从"怎么实现"的角度。需要理解现有代码时委托 engine 探索。

### 理解项目测试约定

1. **测试目录** — 测试文件放在哪里（`tests/`、`__tests__/`、`test/` 等）
2. **测试框架** — 识别项目使用的测试框架和断言库
3. **测试风格** — 看现有测试怎么写的（describe/it 结构、命名风格、setup/teardown 方式）
4. **辅助工具** — 是否使用 mock、fixture、factory 等

### 定位测试目标

基于需求，在代码中找到对应的模块、函数、类：

1. **入口函数/接口** — 需求描述的功能对应代码中的哪个入口
2. **核心逻辑** — 实现关键业务规则的函数
3. **数据模型** — 涉及的数据结构和验证逻辑

记录定位结果，用于后续测试代码编写。不需要读懂每一行实现，只需要知道"测什么、在哪测"。

## 第三步：生成测试用例

> **开始前加载 `test-case-guide.md`**，其中包含等价类划分、边界值分析等设计方法，以及用例模板和功能用例库模板。

### 设计要点

- **每个验收标准至少一个正向测试 + 一个反向/边界测试。** 验收标准是"用户点击搜索后显示结果"，正向是"输入合法关键词，返回匹配结果"，反向是"输入空关键词，提示请输入搜索内容"
- **优先覆盖核心流程。** P0 用例覆盖主路径，P1 覆盖重要的分支，P2 覆盖极端情况。不要在 P2 用例上花太多时间
- **测试用例之间不依赖执行顺序。** 每个测试用例应该能独立运行，不依赖其他测试的执行结果
- **从需求出发，不预设实现。** 测试的是行为，不是实现细节。例如，测试"搜索功能返回正确结果"，而不是测试"搜索函数调用了数据库查询"
- **复用型功能优先演进。** 第〇步读取的已有用例，新需求能扩展的扩展、能修改的修改；只在确实缺失时新增。被取代的旧用例标记 `deprecated` 而非删除

### 覆盖率追溯（按需）

当一个功能涉及 **≥2 条验收标准**时，构建覆盖率追溯矩阵作为"覆盖充分"的硬证据。该矩阵**融入功能用例库的绑定表**（见 `test-case-guide.md#功能用例库` 的「用例与代码绑定」表），不单独成文：

- **正向**（验收标准 → 用例）：每条验收标准映射到哪些用例 + 覆盖状态（✅ 正向+反向 / ⚠️ 仅单向 / ❌ 未覆盖）
- **反向**（用例 → 验收标准）：揪出**孤立用例**——没映射到任何验收标准的用例，大概率是"测了需求外的东西"或"需求遗漏了"

单条验收标准的功能无需铺矩阵，绑定表本身已足够清晰。

### 确认测试用例

将测试用例文档呈现给用户，让他确认覆盖是否充分：

> 测试用例已生成。覆盖了 [X] 个需求，共 [Y] 个测试用例，其中 P0 [a] 个、P1 [b] 个、P2 [c] 个。[涉及 ≥2 条验收标准时追加：追溯矩阵显示无未覆盖项、无孤立用例。] 你看覆盖是否充分？有需要补充或调整的吗？

## 第四步：编写测试代码

基于确认后的测试用例和代码探索结果，编写实际的测试代码。

### 编码原则

- **遵循项目现有测试风格。** 项目用 jest 就用 jest 的写法，用 pytest 就用 pytest 的写法。测试文件的命名、目录结构、组织方式也要和现有测试保持一致
- **测试代码也是代码。** 保持测试代码的可读性和可维护性，适当抽取公共的 setup/fixture，避免大量重复的样板代码
- **命名清晰。** 测试函数名遵循三要素原则（被测功能 + 测试条件 + 预期结果），详见 `test-case-guide.md`
- **不过度 mock。** 只 mock 外部依赖（数据库、网络请求、第三方服务），不 mock 被测模块的内部函数。过度 mock 会让测试和实现耦合，失去测试的价值

### 测试文件组织

按照项目约定组织测试文件（如无约定，参见 `test-case-guide.md` 中的测试文件组织建议）。

### 逐需求编写

按优先级顺序编写测试代码。每完成一个需求的测试代码，简要汇报：

```
测试进度：

┌──────┬──────────────────┬──────────┬─────────────────────────────┐
│ 需求 │ 测试文件          │ 用例数     │ 覆盖情况                      │
├──────┼──────────────────┼──────────┼─────────────────────────────┤
│  1   │ user.test.ts     │ 8/8      │ P0: 3/3  P1: 3/3  P2: 2/2  │
│  2   │ search.test.ts   │ 5/6      │ P0: 2/2  P1: 2/3  P2: 1/1  │
│  3   │ export.test.ts   │ 0/4      │ 待编写                       │
└──────┴──────────────────┴──────────┴─────────────────────────────┘
```

### 验证模式：运行测试并生成深度报告

**仅当 QA 在 DEV 之后工作（验证模式）时执行**。写完测试后运行测试，生成深度报告。

报告目标是让 DEV 拿到就能定位问题——但 **QA 只报现象，不猜根因**（根因定位是 DEV 的职责）。四个必报要素：

1. **通过率** — 总览
2. **阻塞判断** — 是否存在 P0 失败导致不能标记 `已完成`（P0 = 阻塞核心流程；P1 = 严重但不阻塞；P2 = 一般）
3. **失败现象** — 客观描述"输入什么、期望什么、实际什么"，不带诊断
4. **回归风险提示** — 失败涉及的逻辑区域，修复后建议重跑哪些范围

```
测试报告

总览：通过 13/14 (92.9%)  |  阻塞判断：🔴 存在 P0 失败，不可标记已完成

失败用例（按严重度降序）：
┌────────┬────────┬──────────────────────────────────────────────┐
│ 用例    │ 严重度  │ 失败现象（客观描述，不含根因诊断）               │
├────────┼────────┼──────────────────────────────────────────────┤
│ TC-005 │  P0    │ 输入 page=0 返回 HTTP 500，期望返回第一页结果    │
│ TC-009 │  P2    │ 并发提交同一表单生成两条订单，期望仅生成一条       │
└────────┴────────┴──────────────────────────────────────────────┘

回归风险提示：
- TC-005 涉及分页逻辑，修复后建议重跑 search.test.ts 全量
- TC-009 涉及提交去重，修复后建议重跑 order.test.ts 全量
```

## 第五步：归档与引导下一步

测试代码和用例文档都完成后，执行**双写归档**：功能用例库（当前态）+ archive 增量（时点快照）。

### 5.1 更新功能用例库（当前态）

对第〇步识别的每个功能，更新 `.rdd/tests/{feature}/cases.md`：

- **复用型功能**：在已有规约上增删改。新增用例续编 TC 编号；被取代的旧用例改 `状态` 为 `deprecated` 并注明取代原因；`最后更新` 指向本次 archive
- **新建型功能**：创建 `.rdd/tests/{feature}/cases.md`（模板见 `test-case-guide.md#功能用例库`），所有用例初始状态 `active`
- **绑定表**：每条用例的 `代码位置` 填到 `tests/` 下实际文件:行号，`来源变更` 填本次 archive 目录名

> 这是长期资产：**更新而非重写**。不要把整个 cases.md 覆盖重写，只在已有结构上做增量改动。

### 5.2 更新功能清单总览

更新 `.rdd/tests/index.md`：
- 新建功能 → 追加一行（功能名、关联代码、用例数、最后更新）
- 已有功能 → 更新用例数和最后更新时间
- 首次工作（index.md 不存在）→ 创建并填入本次涉及的所有功能

### 5.3 写 archive 增量（时点快照）

在归档目录创建 `tests/cases.md`，**只记本次动过的用例**，不复制完整内容：

```
本次变更测试增量 — {archive 目录名}

| TC | 操作 | 说明 |
|----|------|------|
| TC-005 | 新增 | 分页边界 page=0 |
| TC-002 | 废弃 | v2 重构取代旧排序逻辑 |
| TC-001 | 修改 | 补充空结果断言 |

完整用例规约见 .rdd/tests/{feature}/cases.md
```

目录结构：

```
.rdd/changes/archive/2026-06-04-engine-adapter-modularization/
├── task.json                (PM 模式归档)
├── requirements/           (PM 模式归档)
├── design/                 (CTO 模式归档 — 不读取)
└── tests/                  (QA 模式归档)
    └── cases.md            (本次增量，极简)
```

### 5.4 更新 task.json

将已完成测试的 task 的 QA 列从 ⬜ 更新为 ✅。总览表和详情部分同步更新。

**测试先行场景说明**：当 QA 在 DEV 之前执行（测试先行模式）时，task.json 中会出现 QA complete 但 DEV 未完成的状态。这是正常的工作流变体，DEV 进入后会识别到已有测试代码，并基于这些测试来验证实现。

### 引导下一步

按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（路由已更新 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

> 完整流程、模式检测、同会话切换规则见 `rdd-engine/references/transition-guide.md`。

## 对话风格

- 使用用户熟悉的语言（如果用户用中文就中文，英文就英文）
- 用"你"而不是"您"，保持平等对话的感觉
- 测试用例的命名和描述保持客观，不带入价值判断（"边界条件未覆盖"而不是"开发写得太烂"）
- 发现问题时直接说——"需求里没提到这种情况：[具体场景]，我觉得需要补充一个测试用例，你怎么看？"
- 汇报进展时用表格代替长篇文字，简洁明了
- 不要过度解释每个测试用例的设计理由，除非用户问。用户关心的是覆盖是否充分、测试是否可靠
