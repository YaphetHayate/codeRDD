# 测试设计工作流

> **前提**：本流程由 SKILL.md 执行委托触发。QA 始终基于 `requirements/` 目录的需求文档工作，**禁止读取 `design/` 目录**。

> **模式判定（先于第〇步）**：两个时机由任务 `phase` 机械决定，不靠主观判断——`DESIGN` → 时机一（测试先行：走第〇~四步 + 第七步，第四步按「测试先行形态」执行，跳过其中「运行测试并生成深度报告」小节与第五、六步）；`VERIFY` → 时机二（验证模式：**先查本归档是否已有 `tests/cases.json` 先行基线**——有 → 走「基线复跑快速道」，无 → 完整走第〇~七步）。判定细则见 SKILL.md「触发时机 · 模式判定」。

本文件描述从需求分析到测试归档（验证模式含代码质量检查与提交门禁）的完整流程。测试用例设计的方法论和模板见 `test-case-guide.md`。

**核心产物**：本流程产出两处用例资产，职责不同、必须双写：
- `.rdd/tests/{feature}/cases.json` — 功能级用例规约，**跨迭代的长期资产**（这个功能现在该测什么），JSON 格式，Schema 见 `test-case-guide.md#功能用例库`
- `archive/.../tests/cases.json` — 本次变更增量，**极简时点快照**（本次动过哪些 TC）

---

## 第〇步：识别功能与读取历史用例

> 需求是按需求组织的（一次变更一个需求文件），但测试用例是按功能组织的（跨迭代长期活着）。本步建立两者的映射，避免重复设计、保留演进线索。

### 读取功能清单

读取 `.rdd/tests/index.json`（首次工作则不存在，跳过）。它列出项目已有的功能及其用例库位置。

### 为每条需求识别功能归属

逐条阅读需求，判断它属于哪个功能。判定原则：

- 需求描述的核心行为落在哪个已有功能上 → 归属该功能，**复用已有功能名**（如需求"搜索结果加分页"归属 `search`）
- 需求是全新能力，已有功能都不匹配 → **新建功能**，用 QA 淘汰式命名：先拟一个功能名，向用户确认是否合适；命名遵循 kebab-case，语义化、与被测能力对齐
- 一条需求跨多个功能 → 归到**主触发功能**（需求核心行为落在哪），其余功能用 `cross-feature` 标签关联（详见 `test-case-guide.md#功能用例库`）

将识别结果呈现给用户确认：

```
功能归属识别：

| 需求 | 功能 | 类型 | 说明 |
|------|------|------|------|
| 需求1：搜索分页 | search | 复用 | 已有 .rdd/tests/search/cases.json（5 个 active 用例） |
| 需求2：导出 Excel | export | 新建 | 全新功能，建议命名 export |
```

### 读取已有用例规约

对每个**复用型**功能，读取 `.rdd/tests/{feature}/cases.json`，重点关注：
- 已有哪些 active 用例 → 新需求可能扩展或修改它们
- 哪些 deprecated → 避免重新设计已被取代的场景
- TC 编号规则 → 新用例接着已有编号续编，保持连续

**新建型**功能没有历史，直接进入第一步。

## 第一步：需求分析与测试范围确定

### 提取测试要素

逐个阅读需求，从每个需求中提取以下测试要素：

1. **验收标准** — 每条直接对应至少一个测试用例
2. **用户场景** — "谁在什么情况下做什么操作、期望什么结果"就是一个测试场景
3. **边界与异常** — 需求文档中标注的空数据、极端情况、已知限制
4. **隐含约束** — 从需求描述中推断出的约束（如性能要求、并发限制）

将提取结果呈现给用户：

```
测试要素提取：

┌──────────────┬──────────────────────────────────────────────────┬─────────┐
│  需求          │ 测试要素                                          │ 数量     │
├──────────────┼──────────────────────────────────────────────────┼─────────┤
│  需求 1：XXX   │ 验收标准 3 条，用户场景 2 个，边界条件 1 个          │ 6+      │
│  需求 2：YYY   │ 验收标准 2 条，用户场景 1 个，异常场景 2 个          │ 5+      │
│  需求 3：ZZZ   │ 验收标准 1 条，边界条件 3 个                        │ 4+      │
└──────────────┴──────────────────────────────────────────────────┴─────────┘
```

### 确定测试层级

根据需求特点确定需要哪些测试层级：

| 测试层级 | 适用场景 | 依赖 |
|----------|---------|------|
| **单元测试** | 验证独立函数/模块的行为是否正确 | 需要了解代码结构 |
| **集成测试** | 验证模块间协作是否正确 | 需要了解模块边界 |
| **接口测试** | 验证 API 的输入输出是否符合预期 | 需要了解接口定义 |

告诉用户你计划写哪些层级的测试以及为什么。如果项目已有测试文件，先看现有测试层级和风格，保持一致。

## 第二步：探索项目代码结构

从"怎么测"的角度看代码，不是从"怎么实现"的角度。需要理解现有代码时委托 engine 探索。

### 理解项目测试约定

1. **测试目录** — 测试文件放在哪里（`tests/`、`__tests__/`、`test/` 等）
2. **测试框架** — 识别项目使用的测试框架和断言库
3. **测试风格** — 看现有测试怎么写的（describe/it 结构、命名风格、setup/teardown 方式）
4. **辅助工具** — 是否使用 mock、fixture、factory 等

### 定位测试目标

基于需求，在代码中找到对应的模块、函数、类：

1. **入口函数/接口** — 需求描述的功能对应代码中的哪个入口
2. **核心逻辑** — 实现关键业务规则的函数
3. **数据模型** — 涉及的数据结构和验证逻辑

记录定位结果，用于后续测试代码编写。不需要读懂每一行实现，只需要知道"测什么、在哪测"。

> **时机一（测试先行）**：实现尚不存在，定位不到入口属正常——转向需求级行为契约面（UI 接线 / CLI·API 契约 / 数据可观测面）设计探针，形态约束见第四步「测试先行形态」。

## 第三步：生成测试用例

> **开始前加载 `test-case-guide.md`**，其中包含等价类划分、边界值分析等设计方法，以及用例模板和功能用例库模板。

### 设计要点

- **每个验收标准至少一个正向测试 + 一个反向/边界测试。** 验收标准是"用户点击搜索后显示结果"，正向是"输入合法关键词，返回匹配结果"，反向是"输入空关键词，提示请输入搜索内容"
- **优先覆盖核心流程。** P0 用例覆盖主路径，P1 覆盖重要的分支，P2 覆盖极端情况。不要在 P2 用例上花太多时间
- **测试用例之间不依赖执行顺序。** 每个测试用例应该能独立运行，不依赖其他测试的执行结果
- **从需求出发，不预设实现。** 测试的是行为，不是实现细节。例如，测试"搜索功能返回正确结果"，而不是测试"搜索函数调用了数据库查询"
- **复用型功能优先演进。** 第〇步读取的已有用例，新需求能扩展的扩展、能修改的修改；只在确实缺失时新增。被取代的旧用例标记 `deprecated` 而非删除

### 覆盖率追溯（按需）

当一个功能涉及 **≥2 条验收标准**时，构建覆盖率追溯矩阵作为"覆盖充分"的硬证据。该矩阵**融入功能用例库的 cases 数组**（见 `test-case-guide.md#功能用例库` 的 cases.json Schema），不单独成文：

- **正向**（验收标准 → 用例）：每条验收标准映射到哪些用例 + 覆盖状态（✅ 正向+反向 / ⚠️ 仅单向 / ❌ 未覆盖）
- **反向**（用例 → 验收标准）：揪出**孤立用例**——没映射到任何验收标准的用例，大概率是"测了需求外的东西"或"需求遗漏了"

单条验收标准的功能无需铺矩阵，绑定表本身已足够清晰。

### 确认测试用例

将测试用例文档呈现给用户，让他确认覆盖是否充分：

> 测试用例已生成。覆盖了 [X] 个需求，共 [Y] 个测试用例，其中 P0 [a] 个、P1 [b] 个、P2 [c] 个。[涉及 ≥2 条验收标准时追加：追溯矩阵显示无未覆盖项、无孤立用例。] 你看覆盖是否充分？有需要补充或调整的吗？

## 时机二进入分支：基线复跑快速道（验证模式）

验证模式进入时**先查基线**：本归档 `tests/cases.json` 已存在（测试先行留下的冻结基线）→ **不重做第〇~三步的设计流程**。先行用例是本任务已确认过的验收契约，不是待重新设计的新需求：

1. **零改动复跑先行套件**：同命令直接跑，skip 守卫用例随实现落地自动激活。失败按第四步报告要素处理（只报现象，不猜根因）
2. **适配层绑定真实入口**：先行形态留下的适配层（若有）此时绑定实现入口，测试主体零改动
3. **基线缺口增量补充（只增不弱）**：实现揭示的未覆盖行为 → 续编 TC 补充；先行用例与实际不符 → 修正**预期**必须引用需求依据（哪条验收标准/边界变了），不得按实现倒推弱化基线；确属需求空洞 → 整理清单报 PM（见 SKILL.md「向上游反馈」）
4. 增量落盘并复跑全绿后，照常进第五步（代码质量检查）、第六步（提交门禁）、第七步（归档，archive 增量记录本轮 added/modified）

> 无基线（QA 未先行、DEV 后直接进入验证模式）→ 完整走第〇~七步，本分支不适用。

## 第四步：编写测试代码

基于确认后的测试用例和代码探索结果，编写实际的测试代码。

### 编码原则

- **遵循项目现有测试风格。** 项目用 jest 就用 jest 的写法，用 pytest 就用 pytest 的写法。测试文件的命名、目录结构、组织方式也要和现有测试保持一致
- **测试代码也是代码。** 保持测试代码的可读性和可维护性，适当抽取公共的 setup/fixture，避免大量重复的样板代码
- **命名清晰。** 测试函数名遵循三要素原则（被测功能 + 测试条件 + 预期结果），详见 `test-case-guide.md`
- **不过度 mock。** 只 mock 外部依赖（数据库、网络请求、第三方服务），不 mock 被测模块的内部函数。过度 mock 会让测试和实现耦合，失去测试的价值

### 测试文件组织

按照项目约定组织测试文件（如无约定，参见 `test-case-guide.md` 中的测试文件组织建议）。

### 逐需求编写

按优先级顺序编写测试代码。每完成一个需求的测试代码，简要汇报：

```
测试进度：

┌──────┬──────────────────┬──────────┬─────────────────────────────┐
│ 需求 │ 测试文件          │ 用例数     │ 覆盖情况                      │
├──────┼──────────────────┼──────────┼─────────────────────────────┤
│  1   │ user.test.ts     │ 8/8      │ P0: 3/3  P1: 3/3  P2: 2/2  │
│  2   │ search.test.ts   │ 5/6      │ P0: 2/2  P1: 2/3  P2: 1/1  │
│  3   │ export.test.ts   │ 0/4      │ 待编写                       │
└──────┴──────────────────┴──────────┴─────────────────────────────┘
```

### 测试先行形态（时机一写测试代码的形态约束）

时机一写测试代码时实现尚不存在，测试以「先行形态」落盘，三条硬约束：

- **绑行为契约，不绑实现形态。** 断言锚定需求可观测的行为面（UI 接线 / CLI·API 契约 / 数据可观测面），不预设 CTO 尚未裁定的实现细节（接口签名、模块划分、存储选型）。确需触达实现侧入口时用**适配层隔离**：先行会话里适配层指向占位/stub，验证会话绑定真实入口，测试主体零改动
- **实现缺席时套件可跑。** 未交付的行为加 skip 守卫（探测不到实现 → skip 并注明「待 DEV 交付」），实现落地后**同命令复跑自动激活**。先行形态跑一遍并记录 total / failed / skipped 进测试设计报告——failed 必须为 0，skipped 数与待交付面一致
- **出厂自检（归档前硬检查）。** ①语法级可解析（按项目语言选：解释器 AST 解析 / `node --check` / BOM 检查）；②噪声源归一化——不断言毫秒级时间戳等不稳值，先取基线再对比或归一化后断言，防假红；③先行形态干跑一遍留证

> 实证教训（2026-10-08 / 10-09 run）：先行探针带语法缺陷出厂、毫秒时间戳断言假红，都到验证期才暴露，一轮取证/驳回回退的成本远高于出厂自检。

### 验证模式：运行测试并生成深度报告

**仅当 QA 在 DEV 之后工作（验证模式）时执行**。写完测试后运行测试，生成深度报告。

报告目标是让 DEV 拿到就能定位问题——但 **QA 只报现象，不猜根因**（根因定位是 DEV 的职责）。四个必报要素：

1. **通过率** — 总览
2. **阻塞判断** — 是否存在 P0 失败导致不能标记 `已完成`（P0 = 阻塞核心流程；P1 = 严重但不阻塞；P2 = 一般）
3. **失败现象** — 客观描述"输入什么、期望什么、实际什么"，不带诊断
4. **回归风险提示** — 失败涉及的逻辑区域，修复后建议重跑哪些范围

```
测试报告

总览：通过 13/14 (92.9%)  |  阻塞判断：🔴 存在 P0 失败，不可标记已完成

失败用例（按严重度降序）：
┌────────┬────────┬──────────────────────────────────────────────┐
│ 用例    │ 严重度  │ 失败现象（客观描述，不含根因诊断）               │
├────────┼────────┼──────────────────────────────────────────────┤
│ TC-005 │  P0    │ 输入 page=0 返回 HTTP 500，期望返回第一页结果    │
│ TC-009 │  P2    │ 并发提交同一表单生成两条订单，期望仅生成一条       │
└────────┴────────┴──────────────────────────────────────────────┘

回归风险提示：
- TC-005 涉及分页逻辑，修复后建议重跑 search.test.ts 全量
- TC-009 涉及提交去重，修复后建议重跑 order.test.ts 全量
```

> 验证模式下，第五步（代码质量检查）的结果会追加到本报告末尾，构成完整的"功能+质量"双维度报告，格式见 `code-quality-check.md#报告格式`。

## 第五步：代码质量检查（验证模式）

> **仅验证模式执行**（DEV 之后进入）。测试先行模式跳过本步——此时无业务代码可查。

加载 `code-quality-check.md` 获取完整规则。本步只说明在流程中的位置与关键动作。

### 检查范围

只看本次 DEV 变更触及的业务代码：

```powershell
git diff --name-only <merge-base> HEAD
```

排除测试文件、配置、文档、lock 文件。审查的是 DEV 的代码，不审查 QA 写的测试代码。

### 执行顺序

1. **客观检查先行**（构建 / lint / typecheck）——任一失败直接进驳回流程，无需继续人工审查
2. **人工审查 diff**（函数长度、嵌套深度、重复逻辑、命名规范、新引入循环依赖）——逐项核对 `docs/code-quality.md` 的量化规则
3. **主观坏味道扫描**（上帝类、过度设计等）——记录备忘，不阻塞

### 驳回 vs 备忘

- **硬性项不通过** → reopen 回 DEV（见 `code-quality-check.md#驳回流程`）
- **软性项发现问题** → 写入测试报告备忘栏，不阻塞，不驳回

### 汇总到测试报告

代码质量检查结果融入第四步的测试报告，在末尾追加"代码质量检查"表和"代码质量备忘"栏。格式见 `code-quality-check.md#报告格式`。

## 第六步：执行提交（验证模式门禁）

> **仅验证模式执行**。功能测试通过 + 代码质量硬性项通过后，QA 执行 git 提交。这是提交门禁——任何硬性项未通过都不提交，直接 reopen。

### 提交前提（全部满足才提交）

| 前提 | 判定 |
|------|------|
| 功能测试通过 | 第四步测试报告中无 P0 失败 |
| 代码质量硬性项通过 | 第五步检查中 #1~#8 全部合规 |
| 用户确认提交 | 向用户汇报双通过结果，请求提交确认 |

### 提交规范

- **分支**：在 DEV 已创建的分支上提交，不创建/切换分支、不 push
- **Commit message**：基于 `git diff` 自拟（DEV 不再提供草稿），遵循项目已有的 commit message 风格；无明确规范时用简洁中文描述（`feat: 添加用户搜索功能`、`fix: 修复订单状态判断逻辑`）
- **提交范围**：本次变更涉及的业务代码 + QA 编写的测试代码，一并提交；每个 commit 聚焦一个逻辑改动

### 提交动作

```powershell
git add <本次变更涉及的文件>
git commit -m "<基于 diff 自拟的 commit message>"
```

提交后汇报：

```
已提交到分支 [分支名]，commit: [commit message]
改动文件：X 个（业务 Y + 测试 Z）
```

### 不提交的情况

任一硬性项未通过时，**不执行提交**，直接按驳回流程 reopen 回 DEV：

```
⚠️ 代码质量检查未通过，已驳回回 DEV，未执行提交

驳回理由：
- [具体文件:行号] [违反规则] [期望状态]

DEV 修复后重新进入 QA 验证。
```

> 测试先行模式（QA 在 DEV 之前）不执行本步。归档后交 DEV 实现，后续 DEV 完成再以验证模式进入 QA 时才走提交门禁。

## 第七步：归档与引导下一步

测试代码和用例文档都完成后（验证模式还需提交完成），执行**双写归档**：功能用例库（当前态）+ archive 增量（时点快照）。

### 7.1 更新功能用例库（当前态）

对第〇步识别的每个功能，更新 `.rdd/tests/{feature}/cases.json`：

- **复用型功能**：在已有规约上增删改。新增用例续编 TC 编号；被取代的旧用例改 `status: "deprecated"` 并填 `deprecatedReason`；`lastChange` 指向本次 archive
- **新建型功能**：创建 `.rdd/tests/{feature}/cases.json`（Schema 见 `test-case-guide.md#功能用例库`），所有用例初始 `status: "active"`
- **绑定代码**：每条用例的 `codeRef` 填到 `tests/` 下实际文件:行号，`sourceChange` 填本次 archive 目录名
- **写后自检**：JSON 可解析、枚举值合法、TC 编号无重复

> 这是长期资产：**更新而非重写**。不要把整个 cases.json 重建，只在已有结构上做增量改动。

### 7.2 更新功能清单总览

更新 `.rdd/tests/index.json`：
- 新建功能 → `features` 数组追加一项（feature、relatedCode、testCode、activeCount、lastUpdated、lastChange）
- 已有功能 → 更新 activeCount 和 lastUpdated
- 首次工作（index.json 不存在）→ 创建并填入本次涉及的所有功能

### 7.3 写 archive 增量（时点快照）

本会话经用户确认的检查点决策（验收口径改定、放行取舍等）先入统一决策账本留痕：`delivery-bridge.cmd -Command decide -Kind checkpoint -Archive <归档> -Checkpoint <名> -Decision <结论> [-Reason] [-Options <A|B>] [-Background] [-Role QA]`——条目落归档级 `decisions.jsonl`（四要素 + decider=user）。

在归档目录创建 `tests/cases.json`，**只记本次动过的用例**，不复制完整内容：

```json
{
  "archive": "2026-06-04-engine-adapter-modularization",
  "changes": [
    { "feature": "search", "id": "TC-005", "op": "added", "title": "分页边界 page=0" },
    { "feature": "search", "id": "TC-002", "op": "deprecated", "reason": "v2 重构取代旧排序逻辑" },
    { "feature": "search", "id": "TC-001", "op": "modified", "note": "补充空结果断言" }
  ]
}
```

`op` 枚举：`added` / `modified` / `deprecated`。完整用例规约见 `.rdd/tests/{feature}/cases.json`。

目录结构：

```
.rdd/changes/archive/2026-06-04-engine-adapter-modularization/
├── task.json                (PM 模式归档)
├── requirements/           (PM 模式归档)
├── design/                 (CTO 模式归档 — 不读取)
└── tests/                  (QA 模式归档)
    └── cases.json          (本次增量，极简)
```

### 7.4 任务路由状态（只经 CLI，不手改 task.json）

路由状态的唯一写通道是 `rdd-flow` 命令（phase-model 语义），按所处时机推进：

- **时机一（测试先行）**：DESIGN 阶段还有其他 owner（CTO/UX）→ `set-route -To "<阶段内剩余角色集>"` 阶段内收窄；自己是最后一个设计角色 → `set-route -To "DEV" -Phase "IMPL"` 交给实现，随后按「引导下一步」交接。**禁止调用 `complete`**——时机一的完成只是设计面完成，`complete` 会把任务整条闭环（lifecycle=completed），DEV 与后续验证会话都无法再认领（`TASK_NOT_CLAIMABLE`）。桥接 run 下本步不适用：`goal-tree-leaf report` 回调规划者即终局，路由推进由规划者驱动
- **时机二（验证模式）**：功能+质量双通过并完成提交后 → `rdd-flow complete` 标记任务闭环（currentOwners → 已完成）。**这是 `complete` 的唯一使用时机**

### 引导下一步

按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**执行角色交接（路由已更新 → 运行 next → 推荐角色请求确认 → 生成 packet 按模式分支）。

> 完整流程、模式检测、同会话切换规则见 `rdd-engine/references/transition-guide.md`。

## 对话风格

- 使用用户熟悉的语言（如果用户用中文就中文，英文就英文）
- 用"你"而不是"您"，保持平等对话的感觉
- 测试用例的命名和描述保持客观，不带入价值判断（"边界条件未覆盖"而不是"开发写得太烂"）
- 发现问题时直接说——"需求里没提到这种情况：[具体场景]，我觉得需要补充一个测试用例，你怎么看？"
- 汇报进展时用表格代替长篇文字，简洁明了
- 不要过度解释每个测试用例的设计理由，除非用户问。用户关心的是覆盖是否充分、测试是否可靠
