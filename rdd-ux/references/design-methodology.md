# 独立设计方法论 — 七步设计法

本文件定义创作者模式下，从业务需求生成完整设计方案的系统化流程。目标是在没有视觉参考的情况下，产出与有参考图时同等质量的设计规格。

## 核心原则

- **需求驱动设计。** 每个设计决策都追溯到具体的用户场景或需求约束，不存在"因为好看所以这样设计"。
- **先结构后视觉。** 先确定信息架构和布局骨架，再填充视觉细节。避免"配色好看但信息层级混乱"的情况。
- **建立系统而非逐个设计。** 先建立设计 Token 系统（色彩、字体、间距），再基于系统设计组件。不是每个组件单独设计，而是所有组件共享同一套视觉系统。
- **一致性优先于独特性。** 如果项目已有部分前端代码，新设计必须融入现有风格，而非另起炉灶。

## Step 1: 需求理解与场景定义

### 目标

从 requirement.md 中提取设计所需的信息，明确要设计什么。

### 提取内容

| 项目 | 来源 | 说明 |
|------|------|------|
| 核心用户场景 | requirement.md 的用户场景章节 | "谁在什么情况下做什么操作、期望什么结果" |
| 必须展示的信息 | 需求描述 + 验收标准 | 页面上必须出现的数据和内容 |
| 必须支持的操作 | 验收标准 | 用户可以执行的动作 |
| 页面/组件列表 | 需求描述 + 影响范围 | 需要设计哪些页面或组件 |
| 约束条件 | 关键约束章节 | 技术限制、设备要求、用户群体特征 |

### 场景清单输出

```
设计场景清单：

场景 1：[场景名称]
  用户：[谁]
  目标：[想做什么]
  页面：[在哪个页面]
  操作流程：[步骤1] → [步骤2] → [步骤3]
  必须看到：[信息列表]
  必须能做：[操作列表]

场景 2：...
```

### 关键问题检查

在设计开始前，确认以下问题有明确答案：

- [ ] 用户首次看到这个页面时，最关注的信息是什么？
- [ ] 用户最常执行的操作是什么？
- [ ] 有哪些异常状态需要展示（空数据、错误、加载中）？
- [ ] 是否有数据量级上的预期（列表 10 条 vs 1000 条会影响布局决策）？
- [ ] 用户群体有什么特征（年龄、技术水平、使用设备）？

**无法从 requirement.md 中获取答案的问题，向用户提问。**

此产出直接归档到设计规格文档第 3.2 节。

```
用户流程图（场景：[场景名]）：

[入口页面]
  │
  ├─ 用户看到：[初始状态描述]
  │
  ├─ 操作：[动作]
  │  ├─ 前置条件：[什么情况下可操作]

  │  └─ 跳转/状态：[结果]
  │
  ├─ 操作：[动作]
  │  ├─ 异常分支：[异常情况]
```

- 网络失败、权限不足、数据为空、数据超长、并发冲突

## Step 3: 布局设计

### 目标

基于信息架构，确定具体的布局实现方式。

### 布局模式选择

| 布局模式 | 适用场景 | 不适用场景 |
|----------|----------|-----------|
| 单栏居中 | 内容型页面、表单、文章 | 数据密集的管理界面 |
| 侧边栏+主内容 | 管理后台、设置页、有导航需求的页面 | 移动端优先的页面 |
| 双栏并排 | 对比视图、主从关系 | 信息量大需集中展示 |
| 网格 | 卡片列表、图片墙、产品展示 | 线性流程页面 |
| 标签页 | 同层级内容切换、减少页面跳转 | 内容之间有强关联需同时展示 |

### 布局关键参数

```
布局参数：

容器最大宽度：[值]px
页面内边距：[值]px（桌面）/ [值]px（平板）/ [值]px（手机）
内容区间距：[值]px
网格列数：[值]（桌面）/ [值]（平板）/ [值]（手机）
网格间距：[值]px
```

### 响应式策略

```
响应式断点：

断点定义：
- 手机：< 640px
- 平板：640px - 1024px
- 桌面：> 1024px
- 大屏：> 1280px

各断点布局变化：
┌──────────┬──────────────────────────────────────────┐
│ 断点      │ 布局变化                                  │
├──────────┼──────────────────────────────────────────┤
│ 桌面      │ 侧边栏展开（240px）+ 主内容区              │
│ 平板      │ 侧边栏收缩为图标栏（64px）+ 主内容区       │
│ 手机      │ 侧边栏隐藏，通过汉堡菜单唤出              │
└──────────┴──────────────────────────────────────────┘
```

**关键决策点：布局模式的选择需要与用户讨论。**

## Step 4: 视觉系统建立

### 目标

建立完整的三层设计 Token 系统——Primitive（原始值）→ Semantic（语义化）→ Component（组件级）。

### 为什么用三层结构

扁平 Token（`--color-primary: #3B82F6`）在项目初期够用，但会随规模增长产生维护噩梦：品牌重塑时要逐个查找替换，不同组件用不同色值导致不一致。

三层结构解决了这个问题：

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Primitive       │     │  Semantic        │     │  Component       │
│  原始值，无语境    │ ──→ │  角色命名，可复用  │ ──→ │  绑定具体组件     │
│  blue-500        │     │  action-primary  │     │  button-primary  │
└─────────────────┘     └─────────────────┘     └─────────────────┘
  改这里 = 全局生效        改这里 = 调整一类用途     改这里 = 微调单个组件
```

### 配色方向（关键决策点）

**1. 确定主色方向**——根据产品气质选择色系
- 专业/工具 → 蓝色系、灰色系
- 活力/社交 → 橙色系、绿色系
- 高端/商务 → 深色系、金色点缀
- 信任/安全 → 蓝色系、绿色系

**2. 如果项目已有品牌色**——以品牌色为主色，推导完整色板
**3. 如果项目无品牌色**——基于产品气质推荐 2-3 个方向供用户选择

**关键决策点：配色方向需要与用户讨论。**

### Token 建立流程

#### 第一层：Primitive Tokens（原始值）

罗列所有原始值，命名只描述值本身（`blue-500`），不描述用途。按类型分组：

- **色彩调色板**：主色系（100-700 色阶）、中性色系（50-900 色阶）、功能色（success/warning/error/info）
- **字体尺寸**：font-size-* 和 font-weight-* 的原始值
- **间距刻度**：以 4px 或 8px 为基准的 space-* 值
- **圆角 / 阴影**：radius-* 和 shadow-* 的原始值

> 如果 `.rdd/design-system/tokens.md` 已有 Primitive 层，直接复用，只补充缺失的值。

#### 第二层：Semantic Tokens（语义化）

按角色命名，指向 Primitive。命名规则：`[类别]-[角色]`，如 `color-action-primary`、`text-body`、`spacing-md`。

**命名原则：**
- **按角色命名，而非外观**：`text-secondary` 能熬过品牌重塑，`gray-text` 不能
- **只指向 Primitive，不互相指向**：避免链式别名难维护
- **先覆盖核心角色**：text / bg / border / action 四类优先

```
Semantic 层示例：

color-action-primary    → blue-500
color-action-primary-hover → blue-600
color-text-primary      → gray-900
color-text-secondary    → gray-500
color-bg-page           → gray-50
color-border            → gray-200
```

#### 第三层：Component Tokens（组件级）

为每个组件定义 Token，指向 Semantic 层。格式：`[组件]-[属性]`。

```
Component 层示例：

button-primary-bg       → color-action-primary
button-primary-bg-hover → color-action-primary-hover
button-primary-text     → color-text-on-action
card-bg                 → color-bg-card
card-border             → border-default
```

> 不是所有组件都需要 Component Token。只有需要偏离 Semantic 默认值的组件才单独定义。大多数组件直接引用 Semantic 层即可。

### 对比度要求

正文文字与背景的对比度不低于 4.5:1（WCAG AA 标准）。建立 Semantic 层后必须验证每对"文字色 + 背景色"的对比度。

## Step 5: 组件设计

### 目标

基于视觉系统，设计每个组件的完整规格。

### 组件设计模板

对 Step 1 中识别的每个组件，按以下模板设计：

```
组件：[组件名]
用途：[一句话说明这个组件做什么]

结构：
  <容器>
    <子元素A />
    <子元素B />
    <子元素C />
  </容器>

样式规则：
  容器：
    - 尺寸：宽 [值] 高 [值]（或自适应）
    - 内间距：[值]
    - 背景：[色值]
    - 圆角：[值]
    - 边框：[值]
    - 阴影：[值]
  子元素A：
    - 字体：[层级]
    - 颜色：[色值]
    - 间距：[值]

变体：
┌──────────┬──────────────────────────────────────────┐
│ 变体      │ 差异                                      │
├──────────┼──────────────────────────────────────────┤
│ 默认      │ [基础样式]                                 │
│ 主要      │ 背景 primary-500，文字白色                  │
│ 次要      │ 背景 transparent，边框 primary-500          │
│ 文字      │ 背景 transparent，文字 primary-500          │
│ 危险      │ 背景 error 色，文字白色                     │
└──────────┴──────────────────────────────────────────┘

状态变化：
┌──────────┬──────────────────────────────────────────┐
│ 状态      │ 视觉变化                                  │
├──────────┼──────────────────────────────────────────┤
│ hover    │ [具体变化]                                 │
│ focus    │ [具体变化]                                 │
│ active   │ [具体变化]                                 │
│ disabled │ [具体变化]                                 │
└──────────┴──────────────────────────────────────────┘

状态组合矩阵（多状态共存时的视觉规则）：
┌─────────────────┬──────────┬──────────┬──────────┐
│ 基础 \ 叠加      │ hover    │ focus    │ disabled │
├─────────────────┼──────────┼──────────┼──────────┤
│ default         │ [变化]    │ [变化]    │ [变化]    │
│ disabled        │ 无反馈    │ 无反馈    │ —        │
│ loading         │ [变化]    │ [变化]    │ 不并存    │
└─────────────────┴──────────┴──────────┴──────────┘
  · 单状态规格只定义状态独立的样子
  · 实际运行中状态会组合（disabled+hover、loading+focus）
  · 没有组合矩阵 → DEV 凭感觉实现 → 组合态视觉冲突
  · 填法：「无反馈」=不触发变化；「不并存」=逻辑不可能；「—」=自身对自身
```

### 组件组合规则

定义组件如何嵌套和组合：

```
组合规则：

PageLayout（页面布局）
  └── Header
  └── Main
      ├── SectionTitle
      └── CardGrid
          └── ContentCard × N
              ├── CardHeader（Avatar + Title + Meta）
              ├── CardBody（Content）
              └── CardFooter（Actions）
```

## Step 6: 交互设计

### 目标

定义用户操作路径、状态流转和反馈机制。

### 用户操作路径

对 Step 1 中的每个场景，绘制完整的操作路径：

```
操作路径（场景：[场景名]）：

[入口页面]
  │
  ├── 用户看到：[页面初始状态描述]
  │
  ├── 操作 1：[点击搜索]
  │   ├── 反馈：输入框获得焦点，显示下拉建议
  │   └── 结果：显示搜索结果列表
  │
  ├── 操作 2：[点击结果项]
  │   ├── 反馈：页面切换过渡（淡入 300ms）
  │   └── 结果：进入详情页
  │
  └── 操作 3：[点击返回]
      ├── 反馈：页面切换过渡（淡入 300ms）
      └── 结果：回到列表页，滚动位置恢复
```

### 状态流转

对有复杂状态的组件，绘制状态机：

```
组件状态流转（[组件名]）：

┌─────────┐
│  空状态   │ ← 初始加载
└────┬────┘
     │ 数据到达
┌────▼────┐     用户操作
│  已加载   │──────────────▶┌─────────┐
│  (默认)   │              │  编辑中  │
└────┬────┘              └────┬────┘
     │ 操作确认                 │ 保存成功
     ▼                         ▼
┌─────────┐              ┌─────────┐
│  处理中  │              │  成功    │─────▶ 已加载(默认)
│ (loading)│              │(success)│
└────┬────┘              └─────────┘
     │ 操作失败
     ▼
┌─────────┐
│  错误    │─────▶ 重试 ──▶ 处理中
│ (error)  │
└─────────┘
```

### 过渡动画参数

```
动画规格：

┌──────────────────┬──────────┬──────────┬──────────────────┐
│ 动画场景          │ 时长      │ 缓动函数  │ 属性              │
├──────────────────┼──────────┼──────────┼──────────────────┤
│ 按钮 hover       │ 150ms    │ ease     │ background-color  │

│ 通知弹出         │ 300ms    │ ease-out │ opacity, translateY(-20px) │
│ 骨架屏闪烁       │ 1.5s     │ ease-in-out │ opacity (0.4↔1) │

```

**关键决策点：交互模式（弹窗 vs 抽屉、分步 vs 单页等）需要与用户讨论。**

## Step 7: 一致性检查

### 目标

确保设计方案内部一致，且与项目已有风格一致。

### 检查清单

| 检查项 | 检查内容 | 通过标准 |
|--------|----------|----------|
| 视觉一致性 | 相同功能的组件在不同位置是否用相同样式 | 按钮在任何地方都长一样（除了变体差异） |
| 交互一致性 | 相似的操作是否用相似的反馈方式 | 所有删除操作都用确认弹窗，所有成功操作都用 toast |
| 间距一致性 | 相同层级的内容间距是否一致 | 所有卡片之间的间距相同 |
| 字体一致性 | 相同层级的信息用相同的字体规格 | 所有卡片标题都用 H3 规格 |
| 色彩一致性 | 相同语义的颜色使用是否一致 | 所有错误提示都用 Error 色 |
| 与项目已有风格 | 新设计是否与已有页面风格冲突 | 不引入与项目已有风格截然不同的设计语言 |

### 发现不一致时的处理

- **内部不一致** → 调整设计方案，统一处理
- **与已有风格不一致** → 优先遵循已有风格，除非有明确理由需要不同（向用户说明）

### 输出

```
一致性检查结果：

✅ 视觉一致性：通过
✅ 交互一致性：通过
⚠️ 间距一致性：发现 1 处不一致 → [具体说明 + 修复方案]
✅ 字体一致性：通过
✅ 色彩一致性：通过
✅ 与项目已有风格：通过（/ 首个项目，无已有风格）
```
