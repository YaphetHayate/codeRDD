## 各节编写要点

### 项目名称与描述

- **名称**：用代码中的实际项目名（`package.json` 的 `name` 字段）
- **描述**：一句话，不要超过 30 字。聚焦"解决什么问题"
- 反面示例："一个功能强大的企业级微服务架构解决方案"（太空泛）
- 正面示例："基于 RDD 工作流的 AI 辅助开发 skill 集合"（具体）

### 快速开始

- **必须能在 3 步内跑起来**：clone → install → run
- 如有环境变量，给出 `.env.example` 路径和必填项
- 如有 Docker，优先给 Docker Compose 命令

### 项目结构

- 只列顶层目录和关键子目录，不要枚举到第 3 层
- 每个目录后面写 2-5 字的说明
- 如果项目复杂，可以按"前端" / "后端" / "公共"分组

### 使用方式

- 优先用表格列常用命令
- 如果功能较多，按场景分组（开发 / 构建 / 部署 / 测试）
- 如果有 CLI 工具，给出常用参数示例

### 技术栈

- 用表格分类（语言 / 框架 / 构建 / 测试 / 数据库 等）
- 标注版本号（如在配置文件中已有）或只写名称

### 贡献指南

- 如果项目有 `.github/CONTRIBUTING.md`，在此链接过去
- PSE 不自动创建贡献指南，除非用户明确要求

## 更新已有 README 的流程

1. 完整读取现有 `README.md`，逐节记下内容
2. 执行项目分析流程（`project-analysis.md`），对比现状
3. 标注差异：

   ```
   待更新内容：
   ┌──────────────────┬──────────────────────────────────────┐
   │ 节               │ 变化                                  │
   ├──────────────────┼──────────────────────────────────────┤
   │ 快速开始          │ 新增 Docker 部署方式                  │
   │ 项目结构          │ 新增 rdd-pse/ 目录                   │
   │ 技术栈            │ 测试框架从 Jest 迁移到 Vitest         │
   └──────────────────┴──────────────────────────────────────┘
   ```

4. 用户确认哪些差异需要更新后，逐节修改
5. 保留已有的有效内容，不过度重写

## 风格要求

- **用中文写**（除非项目本身是全英文的）
- **终端友好**：代码块标注语言，路径用反引号
- **用 ASCII 而不是 emoji**，保持 README 在任何终端都能正常渲染
- **避免空话**：不要写"高性能"、"易扩展"这类没有具体证据的形容词
- **链接优先**：如已有详细文档，用链接引用而不是重复内容
- **先功能后原理**：让读者先知道怎么用，再了解为什么这样设计
