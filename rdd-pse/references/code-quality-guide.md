# 代码质量指南编写规范

> 本文档定义 `docs/code-quality.md` 的编写标准和模板。该文件是 opencode.json 中 `instructions` 字段指向的文件，会被注入到所有 Agent 的系统提示词中。

---

## 设计目标

`docs/code-quality.md` 是所有 Agent（primary + subagent）在生成代码时的通用约束。这份文件应确保：

1. **任何 Agent 写出的代码都符合项目统一的质量标准**
2. **新增或更换 Agent/skill 时不需要重复配置代码规范**
3. **规范内容具体可操作，不是空洞的口号**

---

## 标准结构

```markdown
# 代码质量规范

> 本文档由 RDD-PSE 根据项目实际代码风格生成，随项目演进持续维护。

---

## 1. 可读性优先

[函数长度、嵌套层级、注释原则等具体约束]

## 2. 命名规范

[按文件、类、函数、变量、常量等分类的具体命名规则]

## 3. 单一职责

[函数拆分原则、模块职责边界、副作用管理等]

## 4. 高内聚低耦合

[模块内聚原则、接口解耦方式、循环依赖防范等]

### 检查清单

[提交前的自查问题列表]
```

---

## 各节编写要点

### 可读性优先

- 从项目实际代码中提取**现有团队在用的编写习惯**，不是凭空制定
- 给出**量化约束**：函数行数上限、嵌套层级上限、重复代码容忍度
- 注释原则要明确：写"为什么"不写"做什么"

### 命名规范

- 必须从项目实际代码中**推断**命名风格，不要强行引入不符合项目习惯的规则
- 用表格列出每种类型（文件/类/函数/变量/常量等）的命名规则
- 给出**具体的反面示例**比正面示例更有说服力
- 特殊命名模式（如 React Hook 的 `use` 前缀、事件处理器的 `handle` 前缀）需要单独列出

### 单一职责

- 定义"一件事"的判断标准：函数名描述的事 = 函数实际做的事
- 列出项目中常见的**职责边界**（组件/服务/工具/数据访问层各自的职责）
- 给出拆分信号：什么情况下必须拆分函数/模块

### 高内聚低耦合

- 基于项目的**实际目录结构**定义模块边界
- 给出具体的解耦手段：接口抽象、依赖注入、事件总线、共享类型模块
- 列出项目中常见的**耦合陷阱**（如跨模块直接 import 内部实现）

### 检查清单

- 设计为 Agent 在生成代码后可自查的问题列表
- 每条问题应能用 **是/否** 回答
- 问题聚焦于最可能出问题的点

## 生成流程

### 1. 项目代码分析

在动笔之前，必须从代码中提取信息：

- **命名风格**：阅读 5-10 个源文件，提取共性命名规则
- **目录边界**：分析顶层目录结构，理解模块间的依赖关系
- **lint 配置**：读取 `.eslintrc`、`.prettierrc`、`.editorconfig` 等配置文件
- **编码模式**：识别项目中常用的设计模式和代码组织方式
- **技术栈**：确定语言/框架，以便给出语言特定的规范（如 React 的 Hook 命名、TypeScript 的类型导出规范）

### 2. 生成初稿

- 按标准结构逐节填充
- 所有规则必须**有依据**——从哪段代码看到的？为什么这样做？
- 不确定的规则标注 `[待确认]`，不编造

### 3. 与用户确认

- 逐节呈现给用户确认，重点确认：
  - "这些命名规则和你团队的实际习惯一致吗？"
  - "有没有遗漏你们团队特别在意的事项？"
- 用户可能希望增删或修改某些规则——最终决定权在用户

### 4. 写入文件

- 写入 `docs/code-quality.md`
- 提醒用户：修改本文档后需要**重启 opencode** 才能生效

### 5. 关联配置

- 检查 `opencode.json` 是否存在且是否包含 `"instructions": ["docs/code-quality.md"]`
- 如果 `opencode.json` 不存在，询问用户是否创建
- 如果 `opencode.json` 存在但未引用本文档，建议添加

---

## 更新流程

当项目代码风格、技术栈或团队约定发生变化时，PSE 应主动建议更新：

1. 重新执行项目代码分析
2. 对比现有 `docs/code-quality.md`
3. 标注差异，用户确认后更新
4. 提醒用户重启 opencode

---

## 风格要求

- **面向 Agent 编写**：用指令口吻，如"你必须..."而不是"开发者应该..."
- **具体 > 笼统**：写"函数不超过 40 行"而不是"函数不要太长"
- **可验证**：每条规则应能通过自动化工具（lint）或人工审查快速验证
- **适度克制**：规范不在多而在精，控制在 80 行以内（不含示例），避免给 Agent 造成上下文负担
