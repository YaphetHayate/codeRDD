# UX 角色重新定位 — 设计文档

## 一、需求概述

将 RDD-UX skill 的职责从"输出代码级设计规格文档（颜色 hex、字号 px、间距 px 等）"改为"视觉决策 + 输出参考效果图"。UX 不再教 DEV 怎么写代码，而是产出 DEV 能直观理解和参考的视觉方向。

## 需求覆盖映射

| 需求 ID | 本文档负责范围 | 对应章节 | 关联文档 |
|---------|--------------|---------|---------|
| uxRoleReposition | SKILL.md 职责改写、产出模板重定义、红线调整 | 二、三 | design/uxRoleReposition-ux.md |

> 本需求的前端视觉/交互设计由 UX skill 负责（→ design/uxRoleReposition-ux.md）。
> CTO 设计文档聚焦：文件改动范围、模块归属、集成点、实现步骤。

### 2.3 核心流程

```
UX 模式新旧对比：

旧流程：
  需求文档 → 读代码了解技术栈 → 五步/七步法分析 → 输出代码级规格
                                            ↓
                              spec-template.md 格式
                              ├── 色彩系统（hex 精确值）
                              ├── 字体系统（px 精确值）
                              ├── 间距系统（px 精确值）
                              ├── 组件规格（结构+精确样式）
                              └── 交互规格（精确动画参数）
                              ↓
                          DEV 逐条翻译为代码
                          （问题：不直观，翻译成本高，错误放大）


新流程：
  需求文档 → 读代码了解技术栈 → 五步/七步法分析 → 输出视觉方向
                                            ↓
                              新 visual-direction-template.md 格式
                              ├── 参考效果图（AI 生成/工具输出）
                              ├── 风格定调描述（定性而非定量）
                              ├── 布局结构图（ASCII 保留）
                              ├── 资源决策清单（代码 vs 图片素材）
                              ├── 组件结构建议（结构层次，非像素级样式）
                              └── 交互行为描述（行为，非精确动画参数）
                              ↓
                          前端 DEV 理解视觉意图 → 自主实现代码
                                                ↓
                          后端 DEV 不接触视觉输出（只收文本需求/接口）
```

## 四、自检结果

### 交互点

| 新设计环节 | 已有功能 | 共享元素 | 交互方式 | 推演结论 |
|-----------|----------|----------|----------|---------|
| UX 新产出物 | 前端 DEV（需求 2 创建） | 设计文档交接 | UX 写 design/ → 前端 DEV 读取 | ⚠️ 见下方问题 1 |

| UX 新红线 | rdd-engine 委托 | UX 调用 engine 的 /context | 原有流程不变 | ✅ 无影响 |

### 发现的问题

1. ⚠️ 前端 DEV 对 UX 视觉方向的解读不确定性
   - 场景：UX 输出"蓝灰色系，偏专业/工具感"，前端 DEV 自主选择具体 hex 值
   - 影响：前端 DEV 选的色值可能与 UX 意图有偏差，导致视觉分歧
   - 建议：这本质上是"灵活性的代价"，不是设计缺陷。当 UX 和前端 DEV 跑通 1-2 个需求后（即需求 3 的反馈闭环启用），可根据实际效果调优解读精度。第一期不做过度设计。
