# 需求清单：RDD-UX Skill

## 背景

RDD 工作流（PM → CTO → DEV）在处理前端开发时存在结构性缺口：没有环节负责视觉设计和交互设计。CTO 专注于技术架构（数据模型、接口、模块划分），DEV 拿不到视觉规格和交互定义，只能凭"感觉"写前端代码。无论用户提供文字描述还是参考图片，视觉期望都在传递过程中被稀释，最终产出质量不可控。需要新建一个独立的 UX skill 填补这个缺口。

## 需求列表

### 需求 1：视觉参考分析能力

- **描述**：当用户提供参考图（PNG/JPG）或现有界面截图时，UX 能系统性分解视觉设计，输出结构化的实现规格，而非模糊的"参考这张图"。
- **验收标准**：
  - 给定一张参考图，能提取出设计 token（配色方案、字体层级、间距系统、阴影/圆角定义）
  - 能识别并记录布局结构（grid/flex 模式、响应式断点、定位关系）
  - 能识别组件层级（存在哪些组件、如何组合、嵌套关系）
  - 能识别可见的交互状态（hover、active、disabled、loading 等视觉差异）
  - 提取结果结构化输出，DEV 可直接用于编码
- **优先级**：高

### 需求 2：独立设计能力

- **描述**：当用户只提供业务需求（如"做一个登录页"）而无视觉参考时，UX 能自主完成设计决策，涵盖布局、配色、组件选型、交互方案。
- **验收标准**：
  - 给定业务需求，能产出完整的设计方案（信息层级、布局策略、组件组合、配色方案）
  - 设计决策有明确理由（"为什么用侧边栏而非顶部导航"这类问题能回答）
  - 方案包含响应式策略（不同屏幕尺寸的适配方案）
  - 方案包含交互流程定义（用户操作路径、状态变化、反馈方式）
- **优先级**：高

### 需求 3：结构化设计规格产出

- **描述**：UX 的最终交付物是一份结构化的设计规格文档，DEV 拿到后可以直接开始编码，不需要再猜设计意图。
- **验收标准**：
  - 产出包含设计 token 定义（具体的颜色值、字号、间距数值，而非"蓝色"、"大字"）
  - 产出包含每个组件的规格（结构、变体、状态、布局规则）
  - 产出包含交互规格（过渡效果、动画参数、操作反馈方式及时长）
  - 产出包含响应式规则（断点定义、各断点下的布局变化）
  - 规格文档格式统一、DEV 可作为实现依据逐条对照
- **优先级**：高
- **影响范围**：DEV 执行阶段——DEV 的工作流需要适配读取 UX 的产出物
- **依赖关系**：与需求 1、2 为同一 skill 的不同工作模式，不可分割

### 需求 4：灵活的流水线定位

- **描述**：UX 在 RDD 流水线中的位置不固定，可按项目性质灵活调整，且在前后端设计不耦合时可与 CTO 并行。
- **验收标准**：
  - UX 可以在 CTO 之后运行（基于技术架构做设计）
  - UX 可以在 CTO 之前运行（设计驱动架构）
  - UX 可以与 CTO 并行运行（前后端独立时）
  - skill 本身不强制位置，由用户或 PM 根据项目性质决定调用时机
  - 并行场景下，UX 和 CTO 的产出物最终在 DEV 阶段汇合
- **优先级**：中
- **影响范围**：PM 引导分流逻辑、task.md 格式（需支持 UX 列）

### 需求 5：与现有 RDD 流程的集成

- **描述**：UX skill 需要注册到 skill-registry，PM/CTO/DEV 需要知道何时应该调用 UX。
- **验收标准**：
  - skill-registry.md 中有 UX 的条目，包含合适的领域标签
  - PM 分流逻辑中包含"涉及前端/视觉需求时建议启动 UX"的引导
  - CTO 的领域识别流程中能匹配到 UX（涉及前端视觉/交互时）
  - DEV 的任务分析阶段能识别并引用 UX 的产出物
  - task.md 模板支持 UX 列（与 CTO 并列，状态标记规则一致）
- **优先级**：中
- **影响范围**：skill-registry.md、PM 分流逻辑、CTO 领域识别、DEV 任务分析、task.md 模板

## 关键约束

- UX **不写业务代码**，只产出设计规格文档（类似 CTO 的"只设计不动手"原则）
- UX 的产出物归档在 `RDD/changes/archive/.../design/` 下，与 CTO 的设计文档同目录
- UX 不替代 CTO——技术架构（接口、数据模型、后端逻辑）仍是 CTO 的职责
- UX 的设计规格是 DEV 的实现输入，DEV 对最终代码质量负责

## 讨论记录

- 用户最初考虑"新建 skill"vs"补强 CTO/DEV"两个方向，经讨论确认新建独立 UX skill
- 用户确认 UX 需要同时具备"翻译者"（分析参考图）和"创作者"（从需求生成设计）两种能力
- 用户提出 UX 与 CTO 在不耦合时可并行，采纳为灵活定位方案
- 用户反馈文字描述和参考图两种输入方式在过去都效果不佳，根因是流程缺失而非输入方式问题
- 命名采用 UX（User Experience Designer），与 PM/CTO/DEV/QA 保持一致的缩写风格
