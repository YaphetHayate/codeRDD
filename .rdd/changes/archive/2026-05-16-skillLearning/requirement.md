# 需求清单：Skill 学习能力与项目上下文系统

## 背景

当前 RDD 各角色（CTO/DEV/UX）每次进入项目都需要重新理解代码风格、结构和术语，效率低且结果不一致。现有的 code-compass 提供了一次性全量分析能力，但实际使用中成本过高——生成洞察的 token 消耗甚至超过了它能节省的量，且产物更新困难。

同时，UX/CTO 在面对超出自身领域知识范围的设计需求时（如不同风格的页面设计需要不同方法论），缺乏自我评估和知识补齐的机制。

本需求通过"懒加载式项目上下文系统"和"角色能力自评机制"两个方向，让 RDD 角色具备项目自适应能力。

## 需求列表

### 需求 1：项目上下文懒加载系统

- **描述**：建立一套按需生成的项目理解产物体系。定义三类产物——代码风格（命名规范、编码模式）、代码结构（目录组织、模块关系）、项目术语（模块含义、对应工程和能力）。CTO/DEV 启动工作时先检查产物是否已存在，存在则直接读取，不存在则调用 code-compass 按需生成并缓存。
- **验收标准**：
  - CTO 启动设计工作时，自动检查项目理解产物是否存在；若不存在，触发 code-compass 生成并缓存，然后读取产物进入设计
  - DEV 启动开发工作时，自动检查项目理解产物是否存在；若不存在，触发 code-compass 生成并缓存，然后读取产物进入开发
  - code-compass 能够产出三类结构化产物：代码风格、代码结构、项目术语
  - 产物生成后可被后续所有角色会话复用，无需重复生成
  - code-compass 在生成产物时可识别代码坏味道，识别到则提醒用户
- **优先级**：高
- **影响范围**：code-compass（生产者）、rdd-cto/SKILL.md、rdd-dev/SKILL.md
- **用户场景**：
  - 场景 A：用户首次在一个项目中使用 CTO 设计功能，CTO 发现无项目理解产物，自动调用 code-compass 生成，基于产物完成设计
  - 场景 B：用户在同一项目中再次使用 DEV 开发功能，DEV 发现产物已存在，直接读取并遵循其中定义的代码风格进行开发
  - 场景 C：code-compass 生成产物时检测到代码坏味道，提醒用户；用户决定是否将重构立为 PM 需求
- **边界与异常**：
  - 产物可能过时（代码已变更但产物未更新）：角色应能识别产物生成时间，在明显过时时提醒用户重新生成
  - 代码风格不一致的项目：产物应如实记录主流风格，同时标注不一致之处
- **依赖关系**：依赖 code-compass 现有分析能力，需扩展产物类型

### 需求 2：角色能力自评与 Skill 补齐

- **描述**：UX 和 CTO 在开始工作前增加能力自评步骤——评估自身是否有能力完成当前类型的设计/分析任务。若评估为能力不足，使用 `find-skill` 发现可补充的领域 skill，找到后集成该 skill 的能力辅助完成工作。
- **验收标准**：
  - UX 接到设计任务时，先评估自身是否具备完成该类设计（如特定风格、特定领域）的能力
  - 若评估为能力不足，UX 自动调用 `find-skill` 搜索相关领域 skill
  - 找到匹配 skill 后，UX 集成该 skill 的能力辅助设计，产出符合要求的设计规格
  - 若未找到匹配 skill，UX 明确告知用户能力缺口，建议由用户补充相关 skill
  - CTO 在设计方案时，若涉及自身不熟悉的领域，同样可执行能力自评和 skill 补齐流程
- **优先级**：中
- **影响范围**：rdd-ux/SKILL.md、rdd-cto/SKILL.md
- **用户场景**：
  - 场景 A：用户要求 UX 设计一个像素风格的游戏界面，UX 评估后发现自己缺乏像素风格设计的领域知识，调用 `find-skill` 发现 `pixel-art-sprites` skill，集成其能力完成设计
  - 场景 B：CTO 需要设计一个涉及特定图形算法的技术方案，评估后发现领域知识不足，调用 `find-skill` 搜索相关 skill
- **边界与异常**：
  - 能力自评不应过度谨慎，避免每个任务都触发 find-skill 搜索造成不必要开销
  - find-skill 未找到匹配项时，应清晰说明缺口而非静默跳过
- **依赖关系**：依赖 skill-registry.md 中已注册的领域 skill 和 find-skill 能力

### 需求 3：CTO 代码结构质量把关

- **描述**：CTO 读取项目理解产物后，若判断现有代码结构存在系统性问题（而非局部坏味道），应提醒用户并建议先通过 PM 立为重构需求，不应基于有问题的结构继续推进设计方案。
- **验收标准**：
  - CTO 在读取项目理解产物后，对代码结构进行质量评估
  - 若发现系统性结构问题（如循环依赖、模块职责混乱、架构模式不一致），CTO 暂停设计流程，向用户说明问题并建议先处理
  - CTO 不应基于有问题的结构继续设计，除非用户明确表示接受当前结构并继续
- **优先级**：高
- **影响范围**：rdd-cto/SKILL.md
- **用户场景**：
  - 场景 A：CTO 读取产物后发现项目存在严重的模块耦合问题，暂停设计，向用户说明问题，建议先将重构作为 PM 需求处理
  - 场景 B：CTO 发现产物中只有局部坏味道（如单个函数过长），但整体结构合理，正常推进设计，仅在涉及该部分时提醒
- **边界与异常**：
  - "系统性问题"与"局部坏味道"的区分需要 CTO 具备合理的判断标准，避免过度敏感
  - 用户明确要求"忽略结构问题继续设计"时，CTO 应尊重用户决策
- **依赖关系**：依赖需求 1 的项目理解产物作为判断输入

## 关键约束

- 项目理解产物的生成必须是**按需触发**，不能在角色启动时无条件执行全量分析（避免 code-compass 现有的成本问题）
- 产物存储位置应在项目中（可跨会话持久化），而非仅存在于单次对话上下文
- 角色能力自评应轻量高效，不应引入显著延迟
- find-skill 搜索仅在角色自评判断为"能力不足"时触发，不应成为常规流程的必经步骤

## 讨论记录

- 用户最初期望 code-compass 一次性完成所有代码洞察，但实际使用发现成本过高（token 消耗 > 节省量），因此转向懒加载方案
- 代码重构能力经过讨论后拆出本次需求范围——重构通过标准 RDD 流程（PM → CTO → DEV）自然流转，本次聚焦在"发现问题"而非"解决问题"
- 代码坏味道的检测职责归属于 code-compass（客观观察），重构决策归属于用户和 PM
