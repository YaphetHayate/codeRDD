# 需求清单

## 背景

当前 RDD skill 体系（PM/CTO/DEV/QA）在实际使用中暴露三个核心问题：PM 缺乏对已有工具能力的探测意识、CTO 缺少全局架构评审和业界方案调研、DEV 依赖执行不严格且缺少自测环节。本次优化目标是针对这三个环节分别增强能力。

## 需求列表

### 需求 1：PM 增加平台能力探测环节

- **描述**：在 PM 的"深入挖掘"阶段增加平台能力探测步骤。当用户提出的需求涉及某个已有工具/平台/框架的能力时，PM 应主动阅读相关代码或文档，确认该工具是否已提供相关能力，引导用户优先复用而非自建
- **验收标准**：
  1. PM 的 SKILL.md 中"第二步：深入挖掘"包含明确的"平台能力探测"子步骤
  2. 探测范围界定为当前项目已使用的技术栈和工具能力（业界方案调研留给 CTO）
  3. 当发现已有能力可覆盖需求时，PM 主动向用户提出复用建议，并说明理由
  4. 若用户确认已有能力不适用，PM 记录"为什么不用"的原因，避免后续重复讨论
- **优先级**：高
- **影响范围**：rdd-pm/SKILL.md
- **用户场景**：用户提出"为员工单独配置模型" → PM 读取项目代码发现 opencode 已有 provider API → 引导用户直接调用 opencode 接口而非自建供应商管理
- **边界与异常**：探测可能增加 PM 阶段的耗时；部分工具的 API 文档不在项目内，需要 PM 主动请求用户提供信息

### 需求 2：CTO 增加全局架构评审（Phase 2.5）

- **描述**：在 CTO 的"逐需求设计方案"（Phase 2）和"逐个讨论确认"（Phase 3）之间插入全局架构评审环节。逐条设计完后，整体审视需求间的关联、冲突、合并机会，输出全局架构图，确保方案之间不矛盾
- **验收标准**：
  1. CTO 的 SKILL.md 中 Phase 2 和 Phase 3 之间存在明确的"Phase 2.5：全局架构评审"步骤
  2. 全局评审至少包含：需求间依赖关系图、架构一致性检查、重复/冲突/合并机会识别
  3. 全局评审结果以 ASCII 架构图 + 文字说明呈现给用户确认
  4. 评审发现的问题需同步更新到相关设计文档中
- **优先级**：高
- **影响范围**：rdd-cto/SKILL.md、rdd-cto/references/design-guide.md
- **用户场景**：需求 A 设计了认证方案 X，需求 B 设计了认证方案 Y → 全局评审发现冲突 → 合并为统一方案
- **边界与异常**：单需求场景下全局评审可简化为一致性检查；L1 需求不需要纳入全局评审

### 需求 3：CTO 强化结合项目现状

- **描述**：强化 CTO"理解项目现状"步骤的深度要求，确保设计方案充分引用项目已有代码和架构模式，而非脱离项目现状做理想化设计
- **验收标准**：
  1. 设计文档中必须引用具体的已有代码（文件路径、类名、函数签名），说明新方案如何融入现有架构
  2. 技术选型时优先复用项目已有的技术栈和工具，引入新技术需说明"为什么现有技术不够用"
  3. 设计方案的代码风格、目录结构、命名规范与项目已有代码保持一致
- **优先级**：中
- **影响范围**：rdd-cto/SKILL.md
- **用户场景**：项目已用 FastAPI + SQLAlchemy 做数据层 → CTO 设计新功能时复用同样的模式，而非引入 Prisma
- **边界与异常**：新项目无已有代码时不适用此要求

### 需求 4：CTO 增加业界方案调研能力

- **描述**：CTO 在处理 L2/L3 需求时，涉及技术选型应主动调用 web 搜索工具调研业界成熟方案，优先推荐复用成熟工具而非自建。调研方法论单独放在 reference 文件中，便于后续独立优化
- **验收标准**：
  1. 新增 `rdd-cto/references/industry-research.md`，包含调研方法论（搜索策略、评估维度、对比呈现格式）
  2. L2/L3 需求的分析流程中包含"业界方案调研"步骤，涉及技术选型时必须先调研
  3. 调研结果用对比表呈现，至少包含：方案名、成熟度、社区活跃度、与项目技术栈兼容性、推荐理由
  4. CTO 优先推荐业界成熟方案，自建方案需要给出"为什么不用成熟工具"的理由
- **优先级**：高
- **影响范围**：rdd-cto/SKILL.md、rdd-cto/references/industry-research.md（新增）
- **用户场景**：需求涉及 RAG 能力 → CTO 搜索 LangChain/LlamaIndex 等工具 → 对比后推荐最适合项目的方案
- **边界与异常**：L1 需求不需要调研；调研可能受 web 搜索结果质量影响

### 需求 5：DEV 严格遵循任务依赖关系

- **描述**：强化 DEV 任务分析阶段对依赖关系的识别和执行控制，确保并行组之间严格串行——下一并行组必须等前一组所有任务全部完成并通过审查后才能启动
- **验收标准**：
  1. 并行组规则中显式声明：下一并行组必须等前一组所有任务全部完成并通过审查
  2. 拆分计划中增加依赖链可视化（如 `T1 → T2 → [T3, T4]`）
  3. 执行阶段启动任务前校验前置依赖任务状态是否全部为 ✅
  4. 模板和 SKILL.md 中明确依赖违反时的处理方式（拒绝启动、提示等待）
- **优先级**：高
- **影响范围**：rdd-dev/SKILL.md、rdd-dev/references/templates.md
- **用户场景**：依赖关系为 1→2→3/4 → T1 完成但 T2 未完成 → 尝试启动 T3 时被阻止 → 提示"T3 依赖 T2 完成"
- **边界与异常**：无依赖的并行任务不受影响；用户明确要求跳过依赖等待时可豁免

### 需求 6：DEV 增加单任务自测环节

- **描述**：每个任务（DEV 直接执行或子 agent 执行）完成后，必须通过 lint + typecheck + 该任务涉及模块的测试才算通过，避免代码写完但实际不可用
- **验收标准**：
  1. 任务完成的标准从"代码写完"变为"代码写完 + lint 通过 + typecheck 通过 + 相关测试通过"
  2. 子 agent prompt 模板中增加自测要求，要求子 agent 返回结果前先执行 lint + typecheck + 相关测试
  3. DEV 审查阶段增加"可运行性"检查维度
  4. 自测不通过的任务不能标记为完成，需修复后重新自测
- **优先级**：高
- **影响范围**：rdd-dev/SKILL.md、rdd-dev/references/prompt-template.md、rdd-dev/references/review-guide.md
- **用户场景**：子 agent 完成 T2（搜索接口）→ 自测发现 typecheck 失败 → 子 agent 自行修复 → 修复后通过 → 返回结果给 DEV
- **边界与异常**：项目没有配置 lint/typecheck 时跳过对应检查；项目没有测试框架时只做 lint + typecheck

## 关键约束

- PM 的平台能力探测范围限定为当前项目已使用的技术栈，不扩展到通用业界调研
- CTO 的业界调研方法论放在独立 reference 文件中，便于后续单独优化
- DEV 自测只跑 lint + typecheck + 相关模块测试，不跑全量测试
- 所有优化不改变现有 RDD 工作流的整体结构（PM → CTO → DEV → QA）

## 讨论记录

- 用户基于实际使用反馈提出三个优化方向
- PM 探测范围讨论后确定为项目已有技术栈，业界调研留给 CTO
- CTO 业界调研能力要求主动调用 web 搜索工具，方法论单独放 reference
- DEV 自测范围讨论后确定为 lint + typecheck + 相关模块测试，不跑全量
