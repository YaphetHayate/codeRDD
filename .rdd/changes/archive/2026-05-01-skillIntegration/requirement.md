# RDD Skills 联动性增强

## 背景

当前的五个 skill（PM、CTO、DEV、QA、code-compass）各自独立运行，模式间切换完全依赖用户手动输入命令。本次改动旨在：在保持各 skill 解耦的前提下，建立模式间的自动流转机制，并将 DEV 升级为开发主管角色以支持任务并行。

## 需求列表

### 需求 1：PM 归档后自动流转到下一模式

- **描述**：PM 完成需求归档后，基于需求复杂度判断建议路径（CTO 或 DEV），询问用户确认。确认后通过 `skill` 工具在当前对话中加载目标模式的指令，实现无缝切换，用户无需手动输入命令。当 QA 并行条件满足时，QA 通过 Task 子 agent 在后台启动。
- **验收标准**：
  - PM 归档完成后，主动向用户建议下一步路径（CTO 或 DEV）并附理由，等待用户确认
  - 用户确认后，PM 通过 `skill` 工具加载目标模式（RDD-CTO 或 RDD-DEV），当前对话切换到新模式继续工作
  - 切换时，PM 将归档路径、task.md 状态等关键信息以文字形式呈现给用户，确保新模式能立即获取上下文
  - 当 QA 并行条件满足时，PM 询问是否同时启动 QA；用户确认后通过 Task 子 agent 后台启动 QA
  - 用户拒绝流转时，回退到手动引导（显示可用的模式命令）
- **优先级**：高
- **影响范围**：rdd-pm/SKILL.md（修改第五步 4b/4e 的引导流程）
- **边界与异常**：
  - 模式切换时，PM 的红线约束（不写代码等）应被目标模式的规则取代
  - 若用户在 PM 阶段还有未讨论完的内容，不触发流转

### 需求 2：CTO 归档后自动流转到 DEV

- **描述**：CTO 完成设计方案归档后，询问用户是否进入开发模式。确认后通过 `skill` 工具在当前对话中加载 RDD-DEV，携带设计文档路径和 task.md 状态。
- **验收标准**：
  - CTO 归档设计文档后，主动询问用户是否进入开发模式
  - 用户确认后，CTO 通过 `skill` 工具加载 RDD-DEV，当前对话切换到开发模式
  - 切换时，CTO 将归档路径、设计文档目录、task.md 状态、建议开发顺序等关键信息呈现给用户
  - 用户拒绝时，显示手动切换提示
- **优先级**：高
- **影响范围**：rdd-cto/SKILL.md（修改 Phase 4 的引导流程）

### 需求 3：DEV 完成后自动流转到 QA

- **描述**：DEV 完成所有开发任务并验证通过后，询问用户是否启动 QA 进行测试验证。确认后通过 Task 子 agent 后台启动 QA，QA 自主运行测试并返回结果。
- **验收标准**：
  - DEV 完成所有 task 的开发和验证后，主动询问用户是否启动 QA
  - 用户确认后，DEV 通过 Task 工具启动 QA 子 agent，传递归档路径和 task.md 信息
  - QA 子 agent 完成后，DEV 收到结果并汇总呈现给用户（通过率、失败用例等）
  - 用户拒绝时，显示手动切换提示
- **优先级**：高
- **影响范围**：rdd-dev/SKILL.md（修改提交后的引导流程）

### 需求 4：DEV 升级为开发主管角色

- **描述**：DEV 模式从"纯执行者"升级为"开发主管"，负责阅读需求和设计文档、拆分独立任务、协调子 agent 并行开发。简单任务或强关联任务由 DEV 直接执行，复杂且可并行的任务分配给子 agent。
- **验收标准**：
  - DEV 进入后，通读需求和设计文档，分析任务间的依赖关系和可并行性
  - 将任务拆分为可独立执行的子任务，呈现拆分计划给用户确认：
    ```
    任务拆分计划：

    ┌──────┬──────────────────┬──────────┬──────────┬─────────────────────┐
    │ 编号 │ 任务              │ 依赖      │ 执行方式  │ 说明                 │
    ├──────┼──────────────────┼──────────┼──────────┤                     │
    │ T1   │ 用户模型扩展      │ 无        │ 子 agent │ 独立模块              │
    │ T2   │ 搜索接口实现      │ T1        │ 子 agent │ 依赖模型定义          │
    │ T3   │ 配置项调整        │ 无        │ DEV 直接 │ 单文件改动            │
    └──────┴──────────────────┴──────────┴──────────┴─────────────────────┘

    并行组 1: [T1, T3] → 并行组 2: [T2]
    ```
  - 简单任务（≤2 文件、目标明确）或强关联任务（拆分开会引入一致性风险），由 DEV 直接执行
  - 独立且复杂度足够的任务，DEV 构造包含充分上下文的 prompt，通过 Task 子 agent 执行
  - 子 agent 完成后，DEV 汇总结果，检查是否有问题需要用户决策
  - 遇到问题时，DEV 将决策信息整理后呈现给用户，获得回答后发起下一轮任务
  - 所有任务完成后，DEV 做整体验证（lint、测试、构建），汇报最终结果
- **优先级**：高
- **影响范围**：rdd-dev/SKILL.md（重构核心工作流）
- **用户场景**：
  - 用户确认 CTO 设计方案后进入 DEV，DEV 读取设计文档，识别出 5 个实现任务，其中 3 个可以并行。DEV 展示拆分计划，用户确认后同时启动 3 个子 agent 并行开发。子 agent 完成后 DEV 汇总检查，发现其中 1 个有问题需要用户确认，DEV 整理问题后询问用户。
- **边界与异常**：
  - 子 agent 是无状态 worker，不保留对话历史，所有必要信息由 DEV 在 prompt 中传递
  - 子 agent 无法中途提问，遇到不确定的问题应在结果中报告，由 DEV 决定处理方式
  - DEV 对子 agent 产出的代码质量负责，需做 code review 级别的检查
  - 若项目没有设计文档（需求引导模式或直接开发模式），DEV 按原有逻辑工作

## 关键约束

- **保持解耦**：各 skill 间通过"skill 工具加载"和"Task 子 agent"实现流转，不引入 skill 间的直接代码依赖
- **用户确认节点**：所有自动流转必须在关键节点获得用户确认
- **向后兼容**：修改后的 skill 在无子 agent 场景下仍能直接开发
- **不改变核心职责边界**：PM 不写代码、CTO 不写业务代码、QA 不读设计文档等红线约束不变

## 讨论记录

- PM→CTO、CTO→DEV 使用 `skill` 工具在当前对话内切换（需要交互）；→QA 使用 Task 子 agent（自主执行）
- DEV 升级为开发主管：简单/强关联任务直接做，独立复杂任务分给子 agent 并行
- 子 agent 是无状态 worker，通过 DEV 构造的 prompt 获取上下文，不需要独立的 skill 定义
- code-compass 集成（原需求 5、6）暂不纳入本次迭代，后续按需补充
