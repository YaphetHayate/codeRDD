## 背景

基于 codeRDD-plus-mimo 项目"办公室场景不渲染"bug 的修复复盘，发现该 bug 实际由 4 层独立问题叠加而成（场景未注册、背景类型不匹配、Canvas 0x0 像素、API 路径错误），但 RDD 流程将其当作 4 个独立的 L1 bug 逐次修复，经历了 4 轮 PM→DEV 才最终解决。而直接让 AI 修复同类问题时，AI 能一次性读完整个渲染管线并诊断出所有层级。

核心矛盾：RDD 流程的"分析→拆分→执行"模式适合计划型开发，但 bug 修复的节奏是"诊断→修复→验证"，现有三种 DEV 模式都不支持。

## 需求列表

### 需求 1：DEV 新增 Bug 修复专用工作流

- **描述**：DEV 当前三种工作模式均以"先计划、后执行"为底层逻辑，不支持"先全链路诊断、再统一修复"的 bug 修复节奏。需为 DEV 新增专门面向 bug 修复的工作流，核心特征是诊断优先——修复前先沿用户场景完整 trace 代码执行路径，识别所有问题层，再统一修复。
- **验收标准**：
  1. DEV SKILL.md 新增"模式四：Bug 修复模式"，包含完整的诊断→修复→验证工作流
  2. 诊断环节要求沿用户报告的场景从入口到终点完整 trace 代码路径，列出所有问题点（而非只看报错信息）
  3. 修复环节要求基于诊断结果统一修复所有层级，而非逐层逐次
  4. 验证环节要求确认用户可见的最终行为正确，而非仅确认特定报错消失
  5. 明确触发条件：用户报告 bug / 修复后发现仍有问题 / QA 测试失败时自动切换
- **优先级**：高
- **影响范围**：`rdd-dev/SKILL.md`

### 需求 2：PM Bug 验收标准锚定用户可见结果

- **描述**：PM 的 bug 修复策略要求定义"修复后应该表现为什么样"，但归档记录显示验收标准经常停留在代码层面（如"不报 Scene not found"），而非用户可见行为（如"办公室场景正常显示角色和背景"）。需强化 PM 对 bug 验收标准的引导。
- **验收标准**：
  1. `execution-strategy.md` Bug 修复章节新增验收标准规则：必须描述用户可见的最终行为，禁止"不报错"、"不再出现 X"等否定式描述
  2. 提供正反示例（反面："不再报 Scene not found" → 正面："办公室场景正常渲染，包含背景、地板、角色"）
  3. PM 确认 bug 验收标准时，需追问"修好后用户看到的最终画面/行为是什么？"
- **优先级**：高
- **影响范围**：`rdd-pm/references/execution-strategy.md`

### 需求 3：DEV Bug 修复后全链路验证

- **描述**：当前 DEV 的冒烟验证检查的是"应用能启动、核心路径可走通"，但不检查"被修复的用户场景现在是否正常"。需在 bug 修复场景下增加针对性验证：沿用户报告的完整场景走一遍，确认最终行为符合预期。
- **验收标准**：
  1. DEV 冒烟验证环节新增 bug 修复专项：修复完成后，沿用户报告的完整操作路径验证最终行为
  2. 验证不通过时，回到诊断环节重新排查（与需求 1 的诊断流程衔接形成闭环）
- **优先级**：中
- **影响范围**：`rdd-dev/SKILL.md`

## 关键约束

- 所有改动仅限于 SKILL.md 和 references 目录下的 markdown 文件
- Bug 修复模式应比走 PM→CTO→DEV 流程更轻量，不是加流程而是换节奏
- 需求 1 和需求 3 存在衔接关系：诊断→修复→验证在 bug 修复场景下是闭环
