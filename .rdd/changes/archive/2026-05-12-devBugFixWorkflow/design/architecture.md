# DEV Bug 修复模式 + PM 验收标准强化 — 设计文档

## 一、需求概述

**需求 1+3**：为 DEV 新增"Bug 修复模式"（模式四），以全链路诊断为核心工作流，诊断→修复→验证形成闭环。同时引入 bug register 机制处理非阻塞 bug。

**需求 2**：强化 PM Bug 修复的验收标准编写规则，锚定用户可见结果而非代码层面症状。

三个需求共同解决一个问题：RDD 流程对 bug 的处理效率——多层 bug 被逐层拆分修复，验收标准停留在代码层面，修完不验证用户可见结果。

## 二、需求 1+3：DEV Bug 修复模式

### 2.1 模式定位

与现有三种模式并列的"模式四"，同时具备"侧任务"属性——可从 Mode 1/2/3 中直接切入，完成后回到原模式断点继续。

```
独立触发：用户报告 bug ──▶ Mode 4 ──▶ 完成 ──▶ 等待用户指令

侧任务触发：Mode 1/2/3 执行中
  │
  ├── 发现阻塞 bug ──▶ 切入 Bug 修复流程（记录断点）
  │                     │
  │                     ├── 诊断 → 修复 → 验证
  │                     │
  │                     └── 完成 ──▶ 回归检查 ──▶ 恢复原模式断点
  │
  └── 发现非阻塞 bug ──▶ 记录到 bug register ──▶ 继续当前任务
```

### 2.2 触发条件

| 触发场景 | 进入方式 | 完成后 |
|----------|---------|--------|
| 用户直接报告 bug（"XX 不工作"、"修一下这个"） | 输入处理直接路由到 Mode 4 | 等待用户下一步指令 |
| Mode 1/2/3 中发现阻塞当前任务的 bug | 从当前模式切入（侧任务） | 回到原模式断点继续 |
| Mode 1/2/3 中发现不阻塞当前任务的 bug | 记录到 bug register，不切换模式 | 不中断 |
| 修复后验证未通过（用户说"还是不行"） | 自动回到诊断环节 | 迭代 |
| QA 测试失败 | DEV 收到结果后进入 Mode 4 | 修复后重新流转 QA |

### 2.3 核心工作流

```
触发 Bug 修复模式
  │
  ├── Step 1: 理解问题（≤3 分钟，问清楚就过）
  │   - 用户在做什么操作？期望看到什么？实际看到什么？
  │   - 有报错信息吗？能稳定复现吗？
  │   - PM 定义的验收标准是什么？（如有需求文档）
  │
  ├── Step 2: 全链路诊断
  │   │
  │   ├── 2.1 定位入口代码
  │   │   从用户操作 → 找到代码入口点（事件处理/路由/API 调用链起点）
  │   │
  │   ├── 2.2 逐层 trace
  │   │   从入口沿执行路径逐层深入，每一层检查：
  │   │   - 输入数据格式是否匹配上一层输出？
  │   │   - 处理逻辑是否覆盖了当前场景？
  │   │   - 输出数据格式是否符合下一层期望？
  │   │   - 是否有未处理的边界/异常情况？
  │   │   → 记录所有发现的问题点（不只看报错信息）
  │   │
  │   └── 2.3 汇总诊断结果
  │       - 列出所有问题点，按执行路径顺序排列
  │       - 标注问题间的依赖（"A 不修，B 修了也没用"）
  │
  ├── Step 3: 呈现诊断结果（多层 bug 时必做）
  │       单层简单 bug（原因明确、≤2 文件）可跳过，直接进入 Step 4
  │
  │       向用户报告：
  │       "诊断发现 [N] 个问题层：
  │        1. [问题 A] — 位置：[文件:行] — 影响：[...]
  │        2. [问题 B] — 位置：[文件:行] — 影响：[...]
  │        建议一次性修复所有层级。确认？"
  │
  ├── Step 4: 统一修复
  │       基于诊断结果，一次性修复所有问题。不逐层逐次，不留给下一轮。
  │
  ├── Step 5: 场景验证
  │       沿用户报告的完整操作路径验证最终行为。
  │       验证标准：用户可见的最终结果是否符合预期（不是检查报错是否消失）。
  │       如果有 PM 定义的验收标准，逐条对照。
  │       │
  │       ├── 验证通过 → Step 6
  │       │
  │       └── 验证未通过 → 回到 Step 2 重新诊断（迭代，最多 3 轮）
  │           3 轮后仍未通过 → 向用户报告全部诊断发现，请求协助
  │
  └── Step 6: 汇报
      - 诊断发现了什么（问题层数、根因）
      - 修了什么（文件、改动摘要）
      - 验证结果（用户可见行为确认）
      - 如有仍在关注的风险点，主动说明
```

### 2.4 快速通道

当 bug 原因一目了然时（typo、缺 import、简单逻辑反转），可以跳过 Step 2-3 直接修复。

**硬性规则**：快速修复后 Step 5 验证未通过时，**必须**回到 Step 2 执行完整诊断——不允许再走快速通道。

### 2.5 侧任务执行规则

从 Mode 1/2/3 切入 Bug 修复时：

1. **记录断点**：简短说明当前做到哪了（一句话）
2. **执行 Bug 修复流程**（Step 1-6）
3. **回归检查**：修复完成后，检查修复是否影响了当前任务的实现计划（如修复改动了设计文档引用的接口）
4. **恢复原模式**：从断点继续。如果修复影响了实现计划，向用户说明调整

### 2.6 退出边界

Bug 修复模式不应处理的场景——遇到以下情况应引导用户到对应模式：

| 场景 | 处理方式 |
|------|---------|
| Bug 修复需要新增功能才能解决 | 建议用户 `/RDD-PM` |
| Bug 修复涉及架构变更 | 建议用户 `/RDD-CTO` |
| Bug register 中累积 3+ 待处理 bug | 建议用户安排批量修复 |

## 三、Bug Register 机制

**位置**：`RDD/changes/bug-register.md`（项目级，与 archive 同级）

**格式模板**（新增 `rdd-dev/references/bug-register-template.md`）：

```markdown
# Bug Register

> 开发过程中发现的非阻塞 bug。PM 可定期审视排优先级，DEV 可批量处理。

| ID | 发现日期 | 描述 | 发现上下文 | 状态 | 优先级 |
|----|---------|------|-----------|------|--------|
| B001 | YYYY-MM-DD | [简述] | [在哪个 Task/模式下发现] | ⬜ 待处理 / ✅ 已修复 | 高/中/低 |
```

**写入时机**：Mode 1/2/3 中发现不阻塞当前任务的 bug 时，DEV 追加一行，继续当前工作。

**处理时机**：
- 当前任务全部完成后，DEV 检查 register 中是否有待处理的 bug，向用户确认是否继续修复
- PM 审视归档时可以扫描 register，将有价值的 bug 纳入下一轮需求
- 用户随时可以指定"修一下 B001"触发 Mode 4

## 四、需求 2：PM Bug 验收标准强化

在 `rdd-pm/references/execution-strategy.md` 的 **Bug 修复 → 定义修复标准** 步骤中补充以下内容：

### 4.1 新增验收标准编写规则

**规则 1**：验收标准必须描述用户可见的最终行为，而非代码层面的中间状态。

- ❌ 禁止："不再报 Scene not found 错误"
- ✅ 正确："办公室场景正常渲染，显示背景、地板、墙壁，无白屏或空白区域"

**规则 2**：禁止否定式描述。用"修复后应该是什么样"替代"修复后不再出现什么"。

- ❌ 禁止："不再白屏"、"不再崩溃"、"不再返回 500"
- ✅ 正确："页面正常显示完整的办公室场景"、"接口返回 200 和预期的数据结构"

**规则 3**：验收标准应覆盖用户操作的完整路径，而非只覆盖报错点。

- ❌ 不足："控制台不再报错"
- ✅ 完整："用户选择项目后，进入办公室页面，场景渲染完成（背景、角色可见），可点击角色触发对话"

### 4.2 PM 追问话术

在"定义修复标准"步骤中，PM 必须追问：

> "修好后用户看到的最终画面/行为是什么？请描述一个完整的用户操作路径和期望结果。"
