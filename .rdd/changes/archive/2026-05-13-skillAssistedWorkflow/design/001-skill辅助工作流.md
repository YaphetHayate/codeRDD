# Skill 辅助工作流 — 设计文档

## 一、需求概述

在 CTO 的 Phase 1 需求分级阶段和 DEV 的任务分析阶段，各增加一个 Skill 匹配步骤。当需求涉及超出通用软件工程的领域（像素美术、UX、动画等）时，CTO/DEV 自动从统一 skill 索引中查找匹配的 skill，读取其 SKILL.md 获取领域知识，融入设计文档或实现过程。索引无匹配时降级到 find-skill 搜索。

三个需求强关联（共享同一套匹配机制和索引文件），合并为一份设计文档。

## 二、技术方案

### 2.1 技术选型

不引入新技术。Skill 索引使用 Markdown 格式，CTO/DEV 通过 Read 工具读取。Skill 知识获取同样通过 Read 工具读取对应 SKILL.md。Find-skill 通过 Skill 工具调用。

### 2.2 模块归属

| 改动 | 文件 | 类型 |
|------|------|------|
| Skill 索引文件 | `skill-registry.md`（项目根目录） | 新建 |
| CTO Skill 匹配步骤 | `rdd-cto/SKILL.md` | 修改（Phase 1 流程扩展） |
| DEV Skill 匹配步骤 | `rdd-dev/SKILL.md` | 修改（任务分析阶段扩展） |

### 2.3 Skill 索引文件设计

#### 路径

`skill-registry.md`，放在项目根目录。CTO 和 DEV 都读取同一份文件。

#### 格式

```markdown
# Skill 索引

> 本文件列出所有可作为领域顾问使用的 skill。CTO 和 DEV 在工作流程中会读取此文件匹配相关 skill。
> 新增 skill 时，在此文件中追加条目即可。每个 skill 一个三级标题。

### pixel-art-sprites

- **领域标签**：像素美术, pixel art, sprite, 精灵图, 调色板, 像素画, 角色绘制, 动画帧, tile, 8-bit, 16-bit
- **能力概述**：像素画创作、精灵图动画、有限调色板设计
- **使用方式**：读取 SKILL.md 获取像素画技法指导（调色板策略、像素密度、阴影技法、sprite sheet 设计）

### code-compass

- **领域标签**：代码分析, 项目结构, 代码索引, 调用关系, 入口点, 代码导航, 理解项目, 定位代码
- **能力概述**：项目代码理解加速器，构建结构化代码索引
- **使用方式**：读取 SKILL.md 了解索引查询方式；如项目未构建索引，可调用 /map 生成

### find-skill

- **领域标签**：技能发现, skill 搜索, 寻找技能
- **能力概述**：当索引中无匹配 skill 时，搜索发现可用的技能
- **使用方式**：CTO/DEV 在索引中无匹配项时调用此 skill
```

#### 设计要点

- **领域标签是匹配键**：CTO/DEV 从需求文本中提取领域特征词，与每个 skill 的领域标签做关键词匹配。匹配成功即关联该 skill。
- **条目按需扩展**：新增 skill 只需在文件末尾追加一个 `### skill-name` 条目，按格式填写三行即可。
- **排除工作流 skill**：rdd-pm、rdd-cto、rdd-dev、rdd-qa 这四个是 RDD 工作流角色，不是领域顾问 skill，不纳入索引。

#### 1.1 需求分级 — 改动

原有分级结果表增加"领域标签"列：

```
┌──────────────────┬──────┬──────────────────┬──────────────────────────────┐
│  需求              │ 等级  │ 理由              │ 领域标签                      │
├──────────────────┼──────┼──────────────────┼──────────────────────────────┤
│  需求 1：XXX       │  L1  │ ...              │ 通用工程（无）                 │
│  需求 2：YYY       │  L2  │ ...              │ 像素美术, Canvas 渲染          │

└──────────────────┴──────┴──────────────────┴──────────────────────────────┘
```

领域标签提取规则：阅读需求描述和验收标准，判断是否涉及以下方向（不限于）：
- 视觉设计（UI/UX、像素画、图标、动画、配色）
- 特定渲染技术（Canvas、WebGL、SVG）
- 数据可视化
- 特定算法（路径规划、物理模拟）
- 其他需要专业领域知识的方向

不涉及特定领域的标为"通用工程（无）"，跳过后续 skill 匹配。

#### 1.2 领域识别与 Skill 匹配 — 新增章节

```markdown
### 1.2 领域识别与 Skill 匹配

对 1.1 中标注了领域标签（非"通用工程"）的需求，执行 skill 匹配。

**匹配流程**：

对每个有领域标签的需求：
  │
  ├── 读取项目根目录 skill-registry.md
  │
  ├── 将需求的领域标签与 registry 中每个 skill 的领域标签做关键词匹配
  │   （标签之间有交集即视为匹配）
  │
  ├── 匹配到 skill
  │   │
  │   ├── 读取该 skill 的 SKILL.md
  │   ├── 提取与当前需求相关的领域知识
  │   └── 将领域知识作为设计参考，融入后续 1.4 的分析过程和 Phase 2 的设计文档
  │
  └── 未匹配到 skill
      │
      ├── 调用 find-skill skill，描述当前需求的领域特征
      │   │
      │   ├── find-skill 找到可用 skill → 按上述流程读取并融入
      │   └── find-skill 未找到 → 在该需求的设计文档中标注：
      │       "⚠️ 领域知识缺口：本需求涉及 [领域] 但无对应 skill 辅助。
      │        DEV 实现时需注意此领域下的专业要求。"
      │       并在 1.5 分析汇总中向用户主动说明
```

**匹配结果汇总**（在分级结果表后追加）：

```
Skill 匹配结果：
```

```markdown
2. **[指导要点 2]**：[具体内容，如"角色精灵高度建议 32px，头身比约 1:3"]
3. **[指导要点 3]**：[具体内容]

以上指导将在后续技术方案中体现为 [具体的设计约束/实现建议]。
```

### 2.5 DEV Skill 匹配步骤设计

#### 插入位置

在 `rdd-dev/SKILL.md` 的"任务分析阶段 > 分析流程"中，**"列出所有实现任务"之后、"检查文件冲突"之前**，插入 Skill 匹配步骤。

#### 分析流程改动

原有流程图增加两个环节：

```
通读文档（设计文档/需求文档）
  │
  ├── 列出所有实现任务，标注：
  │   - 涉及文件范围
  │   - 依赖关系（哪些任务必须在哪些之后）
  │   - 职责类型（数据层/业务层/接口层/工具函数/配置）
  │   - 领域标签（新增：是否涉及特定领域知识）
  │
  ├── Skill 匹配（新增）
  │   对有领域标签的任务：
  │     1. 读取 skill-registry.md 匹配 skill
  │     2. 匹配到 → 读取 SKILL.md，实现时参考其领域指导
  │     3. 未匹配 → 调用 find-skill
  │     4. find-skill 也未找到 → 在拆分计划中标注"领域知识缺口"，
  │        向用户说明后继续
  │
  ├── 检查文件冲突
  ├── 前置条件核对
  ├── 分类每个任务
  ├── 集成点识别
  └── 呈现拆分计划给用户确认
```

#### 领域标签提取规则

与 CTO 一致。阅读任务描述，判断实现过程是否涉及特定领域知识。标准代码实现任务（CRUD、API、数据处理等）标为"通用工程"，不触发 skill 匹配。

#### 拆分计划呈现格式改动

在拆分计划的每个任务描述中，增加 skill 关联信息：

```
Task 2: [任务标题]
  涉及文件：xxx.js, yyy.js
  关联 Skill：pixel-art-sprites（领域指导：调色板策略、像素绘制技法）
  / ⚠️ 领域知识缺口（无匹配 skill，实现时需自行判断）
```

#### 对实现阶段的影响

当任务匹配到 skill 后，DEV 在编码过程中应参考该 skill 的领域指导。具体行为：

1. **任务启动前**：读取匹配 skill 的 SKILL.md，理解领域要点
2. **编码过程中**：遇到领域相关的实现决策时，遵循 skill 提供的指导
3. **任务完成后汇报**：在汇报中提及"参考了 [skill-name] 的领域指导"

### 2.6 find-skill 降级机制

两个阶段（CTO/DEV）的降级路径一致：

```
skill-registry.md 有匹配
  → 读取 SKILL.md，融入工作
  → 结束

skill-registry.md 无匹配
  → 调用 find-skill，描述需求的领域特征
  → find-skill 找到
      → 按上述流程使用
      → 建议用户将新发现的 skill 补充到 skill-registry.md
      → 结束
  → find-skill 未找到
      → CTO：在设计文档中标注"⚠️ 领域知识缺口"
      → DEV：向用户报告，协商处理方式
      → 结束
```

**补充索引建议**：当 find-skill 找到了新 skill 时，CTO/DEV 应主动建议用户将该 skill 的条目补充到 `skill-registry.md`，避免下次再走 find-skill 降级路径。

## 三、决策点记录

| 决策点 | 选项 | 最终选择 | 选择理由 |
|--------|------|----------|----------|
| 索引文件格式 | A: JSON  B: Markdown | B: Markdown | 与项目其他文件风格一致，CTO/DEV 直接可读，无需解析 |
| 匹配方式 | A: 精确匹配  B: 关键词交集 | B: 关键词交集 | 需求描述和领域标签之间往往不是精确对应，交集匹配更实用 |
| Skill 知识获取方式 | A: Read SKILL.md  B: Invoke Skill 工具 | A: Read SKILL.md | 咨询模式下 CTO/DEV 吸收知识自行工作，不需要 skill 接管对话 |
| 降级时是否阻塞流程 | A: 阻塞等用户确认  B: 标注后继续 | B: 标注后继续 | find-skill 找不到不代表不能做，只是缺少领域专业指导，不应阻塞 |

## 四、风险与应对

| 风险 | 影响 | 应对措施 | 优先级 |
|------|------|----------|--------|
| 索引过时 | 新 skill 未被收录，CTO/DEV 走 find-skill 降级 | 每次通过 find-skill 发现新 skill 后，主动建议用户补充索引 | P1 |
| 匹配不准 | 领域标签词不对导致漏匹配 | 领域标签使用常见同义词（中英文），提高召回率；CTO/DEV 可自行判断是否跳过匹配 | P2 |
| skill 知识过载 | 读取大量 SKILL.md 内容占用上下文 | 只读取与当前需求相关的部分，不要全文无差别加载 | P2 |

## 五、实现优先级建议
