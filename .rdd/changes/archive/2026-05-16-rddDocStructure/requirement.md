# RDD 文档产出结构优化

## 背景

当前 RDD 工作流的归档结构是：每个归档文件夹下放一个 `requirement.md`（包含所有需求）、一个 `task.md`（任务跟踪）、`design/` 目录下放 CTO/UX 设计文档（通常为 `architecture.md` 或编号文件如 `001-xxx.md`）。

这种结构在需求较少时没有问题，但随着需求数量增多，单文件信息密度高、定位困难，且 CTO/UX 无法针对单个需求独立出设计文档——必须共享一个文件或在编号文件间协调，增加了并行工作的摩擦。

## 需求列表

### 需求 1：需求文件拆分为独立文件
- **描述**：将 PM 产出的 `requirement.md` 从单文件多需求，拆分为一个 `overview.md`（放背景、关键约束、需求索引）+ 每个需求独立一个文件（以简短主题名词命名，如 `fixbug.md`、`optimizeCache.md`）
- **验收标准**：
  - 归档目录下不再有 `requirement.md`，改为 `overview.md` + 多个 `{name}.md`
  - `overview.md` 包含背景、关键约束、需求列表索引（含文件名链接）
  - 每个独立需求文件包含完整的描述、验收标准、优先级及可选字段（影响范围、用户场景、边界与异常、依赖关系）
- **优先级**：高
- **影响范围**：PM skill 的归档输出逻辑、requirement 模板

### 需求 2：task.md 增加文件关联记录
- **描述**：task.md 的每个 task 条目中，明确记录该需求对应的 requirement 文件和 design 文件路径，方便各角色快速定位相关文件
- **验收标准**：
  - 每个 task 条目包含 `需求文件` 字段（如 `fixbug.md`）
  - 每个 task 条目包含 `设计文件` 字段（如 `design/fixbug-cto.md, design/fixbug-ux.md`），无设计文件则标注"无"
- **优先级**：高
- **影响范围**：PM skill 的 task 模板、DEV skill 的任务解析逻辑

### 需求 3：设计文件按需求独立命名
- **描述**：CTO 和 UX 的设计文档从共享/编号命名，改为按需求独立命名，格式为 `{需求名}-cto.md` 和 `{需求名}-ux.md`，放在 `design/` 目录下
- **验收标准**：
  - 每个需求有独立的 CTO 设计文件 `design/{name}-cto.md`
  - 每个需求有独立的 UX 设计文件 `design/{name}-ux.md`（如需要 UX 参与）
  - `design/` 目录下不再出现 `architecture.md` 或纯编号文件
- **优先级**：高
- **影响范围**：CTO skill 的设计文档产出逻辑、UX skill 的设计规格产出逻辑、设计文档模板

## 关键约束
- 三项改动影响 PM、CTO、UX 三个 skill 的模板和行为定义
- 已有归档保持不变，新结构从下一个归档开始生效
- 需求文件命名由 PM 在归档时确定，控制在简短名词范围内
