# 协同链路分析

> 本文档定义跨角色协同效率的评价方法。EVAL 通过追溯信息在各角色间的传递链路，识别协同问题。

---

## 分析方法

### 信息传递链追溯

从需求出发，沿 RDD 工作流逐层追溯信息在各角色产出物中的传递情况：

```
requirements/              ← PM 产出
    ↓
design/architecture.md  ← CTO 产出（需求如何被转化为技术方案）
    ↓
design/{name}-ux.md    ← UX 产出（视觉/交互需求如何被规格化）
    ↓
实际代码                 ← DEV 产出（设计方案如何被实现）
    ↓
tests/cases.md           ← QA 产出（本次变更的测试增量；完整规约在 .rdd/tests/{feature}/cases.md）
    ↓
测试代码                 ← QA 产出（测试用例如何被执行）
```

### 追溯检查点

对每一层传递，检查以下内容：

| 检查维度 | 说明 |
|---------|------|
| **完整性** | 上游的关键信息是否在下游产出物中出现 |
| **准确性** | 上游信息在下游是否被正确理解，有无误解或偏差 |
| **增值性** | 下游产出物是否在上游基础上增加了有价值的细化 |
| **冗余性** | 是否存在不必要的重复工作或信息冗余 |

### 常见协同问题模式

```
问题模式                    表现                              严重程度
──────────────────────────────────────────────────────────────────────
信息蒸发                    上游提到但在下游完全消失的需求点     高
理解偏差                    下游对上游信息的理解与原意不同       高
过度设计                    CTO 为简单需求设计了复杂方案        中
不足设计                    CTO 对复杂需求的设计过于简略        高
规格与实现脱节              UX 规格写了但 DEV 没有遵循          中
测试与需求脱节              QA 测试未覆盖 requirement.md 中     高
                            明确要求的验收标准
共享盲点                    DEV 和 QA 在同一处遗漏了需求点      高
                            （说明两者可能都参考了同一个文档）
反向增值                    下游发现了上游未考虑到的场景         正面发现
```

## 元反馈提炼规则

协同分析中发现的问题，按以下规则提炼为 RDD 流程层面的改进建议：

1. **单次问题 → 不提流程建议。** 仅影响本次需求的偶然问题，记录在评价报告中但不作为流程改进建议。

2. **模式化问题 → 提流程建议。** 如果同类问题在多次评价中反复出现，或问题本身反映了流程设计缺陷（如 QA 与 DEV 共享盲点），则提炼为流程改进建议。

3. **建议格式：**
   ```
   ### 流程改进建议

   1. **[建议标题]**
      - 问题根源：[哪个流程环节的设计导致了这个问题]
      - 建议：[具体改进方案]
      - 预期效果：[改进后应避免什么问题]
   ```

4. **建议范围限定：** 只提 RDD 工作流和角色技能层面的改进，不涉及具体项目的技术架构或业务逻辑。
