# 任务分析

> 本文档是 [SKILL.md](../SKILL.md) 的补充材料，包含任务分析阶段的详细流程和规则。

> **⚡ rdd-engine 集成**：必须先执行 `/context` 获取项目理解产物，再继续后续步骤。

执行方式：
```
首先执行 /context 获取项目上下文。
[加载 rdd-engine skill，执行 /context 指令]

基于产物中的代码风格和项目术语，开始任务拆分...
代码定位通过 Grep/Glob 工具完成。
```

## 分析流程

```
通读文档（设计文档/需求文档）
  │
├── 【统一文档解读】（cto/ 或 ux/ 目录存在时执行）
  │   1. 读取所有设计文档 frontmatter，确认 role 和 status
  │   2. 读取各文档的"需求覆盖映射"章节，定位每个需求对应的章节
  │   3. 按角色分别进入正文：
  │      CTO → 技术架构 / 接口 / 数据模型
  │      UX → 视觉 Token / 组件规格 / 交互规范
  │
  │   仅存在 UX 规格而无 CTO 设计时：
  │   - 视觉/交互层面严格遵循 UX 规格
│   - 技术实现方式由 DEV 基于 pm/ 下的需求文件自行决定
  │   - 按需求引导模式的自主决策范围执行
  │
├── 检查 ux/ 目录下是否存在 UX 设计文件（{name}.md）
  │   ├── 存在 → 读取 UX 设计规格，视觉/交互层面以 UX 规格为准
  │   └── 不存在 → 检查 task.md 中 UX 状态
  │       ├── UX = ⬜ 且"UX 设计文件"不是 `无` → 暂停任务分析，提醒用户先走 /RDD-UX 或明确跳过 UX
  │       └── UX = ⏭️ 或"UX 设计文件"为 `无` → 不影响，按原流程
  │
  ├── 列出所有实现任务，标注：
  │   - 涉及文件范围
  │   - 依赖关系（哪些任务必须在哪些之后）
  │   - 职责类型（数据层/业务层/接口层/工具函数/配置）
  │   - 领域标签（是否涉及特定领域知识，如像素美术、UX、动画等）
  │
  ├── Skill 匹配
  │   对有领域标签（非"通用工程"）的任务：
  │     1. 调用 rdd-engine `/skill-manager query`
  │     2. 推荐 skill → 读取该 skill 的 SKILL.md，实现时参考其领域指导
  │     3. 无匹配 → 在拆分计划中标注"⚠️ 领域知识缺口"
  │     4. 任务完成后调用 rdd-engine `/skill-manager record-use` 记录使用情况
  │
  ├── 检查文件冲突
  │   同一并行组内不能有两个任务改同一文件
  │   冲突时：合并任务 / 改为串行 / 其中一个 DEV 直接做
  │
  ├── 前置条件核对
  │   有设计文档时：读取"前置条件清单"，状态为 ❌ 的项在拆分计划中标注
  │   无设计文档时：DEV 自行识别关键外部依赖，确认项目中是否已满足
  │   未满足的依赖 → 在拆分计划中向用户确认处理方式
  │
  ├── 分类每个任务
  │   - DEV 直接执行：≤2 文件、目标明确、或与其他任务强关联
  │   - 子 agent 执行：3+ 文件、独立模块、与其他任务无文件交叉
  │
  ├── 集成点识别
  │   列出本次改动涉及的所有已有模块交互点
  │   对照设计文档确认每个交互点是否已描述集成方式
  │   未描述的 → 标记为风险点，在拆分计划中向用户标注
  │
  └── 呈现拆分计划给用户确认
```

## 任务拆分原则：按职责拆分

每个文件/模块只承担一个明确的职责。拆分维度：

- **数据层**：数据库模型、Repository、ORM 定义
- **业务层**：Service、核心业务逻辑
- **接口层**：Controller、API 路由、请求处理
- **工具函数**：Utils、Helpers、通用工具
- **配置**：Config、常量定义、环境变量

## 任务分类标准

| DEV 直接执行 | 子 agent 执行 |
|---|---|
| ≤2 个文件 | 3+ 个文件 |
| 目标明确无歧义 | 独立模块，边界清晰 |
| 与其他任务强关联（拆开会引入一致性风险） | 与其他任务无文件交叉 |

## 文件冲突防护

- DEV 为每个子 agent 任务标注"涉及文件"列表
- 同一并行组内的任务，"涉及文件"列表不能有交集
- 发现交集时三种处理：
  - **合并**：将冲突任务合并为一个更大的任务
  - **串行**：将冲突任务放入不同并行组
  - **接管**：其中一个改为 DEV 直接执行

## 依赖执行规则（严格串行）

并行组之间是**严格串行**关系，这是强制约束，不是建议：

1. **下一并行组必须等前一组所有任务全部完成并通过审查后才能启动。** 不是"前一组大部分完成"，而是"全部完成"。
2. **启动任务前必须校验前置依赖。** 每个任务启动前，检查其所有前置依赖任务的状态是否全部为 ✅。如果有任何一个前置依赖未完成，拒绝启动该任务。
3. **用户豁免。** 用户明确要求跳过依赖等待时可以豁免，但必须在进度表中标注"用户豁免依赖检查"。

依赖违反时的处理：

```
⚠️ 任务 [T3] 无法启动：
- 前置依赖 T2 状态为 🔄（进行中），尚未完成
- 需要等待 T2 完成并通过审查后才能启动 T3

如果你确认要跳过依赖等待，请告知。
```

## 拆分计划呈现格式

> 拆分计划呈现格式模板详见 [templates.md](templates.md)

拆分计划中必须包含**依赖链可视化**，清晰展示任务间的先后顺序：

```
依赖链：T1 → T2 → [T3, T4]（T3/T4 可并行，但必须等 T1 和 T2 都完成）
```

**Skill 关联信息**：每个任务在拆分计划中应展示匹配的 skill 或领域知识缺口标注：

```
Task 2: [任务标题]
  涉及文件：xxx.js, yyy.js
设计参考：CTO cto/{name}.md + UX ux/{name}.md
  关联 Skill：pixel-art-sprites（领域指导：调色板策略、像素绘制技法）
  / ⚠️ 领域知识缺口（无匹配 skill，实现时需自行判断）
  / ⚠️ UX 已明确跳过：无 UX 设计规格，视觉层面按项目现有风格判断
  / ⛔ UX 仍待处理：暂停 DEV，先进入 /RDD-UX 或由用户明确跳过
```
