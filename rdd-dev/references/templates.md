```
│ 编号 │ 任务              │ 职责类型  │ 依赖      │ 执行方式  │ 涉及文件             │
├──────┼──────────────────┼──────────┼──────────┼──────────┼─────────────────────┤
│ T1   │ 用户模型扩展      │ 数据层    │ 无        │ 子 agent │ models/user.py       │
│ T2   │ 搜索接口实现      │ 接口层    │ T1        │ 子 agent │ api/search.py        │
│ T3   │ 配置项调整        │ 配置      │ 无        │ DEV 直接 │ config/settings.py   │
│ T4   │ 搜索逻辑实现      │ 业务层    │ T1        │ 子 agent │ services/search.py   │
└──────┴──────────────────┴──────────┴──────────┴──────────┴─────────────────────┘

依赖链：T1 → [T2, T4]（T2/T4 可并行，但必须等 T1 完成）
独立任务：T3（无依赖，可与 T1 并行）

并行组 1: [T1, T3] → 并行组 2: [T2, T4]
预计改动 X 个文件
```

## 提交汇报格式

```
已提交到分支 [分支名]，commit: [commit message]
改动文件：X 个，新增：Y 个
task.md 已更新：Task N DEV → ✅
```

## 提交规范

**仅在用户明确要求时才提交代码。**

**分支管理：**
- 为每个独立的需求/功能创建新分支
- 分支命名遵循项目约定，没有约定时用 `feature/需求简称` 或 `fix/问题描述`
- 如果用户已经在某个分支上工作，继续使用该分支

**Commit 规范：**
- 遵循项目已有的 commit message 风格
- 如果项目没有明确规范，使用简洁的中文描述：`feat: 添加用户搜索功能`、`fix: 修复订单状态判断逻辑`
- 每个 commit 聚焦一个逻辑改动，不要把不相关的修改混在一起

**更新流转状态：** 开发完成的 task，在新格式路由总览中将对应行 `当前责任人` 从 `DEV` 改为 `QA`（或在用户明确跳过 QA 时标注完成/跳过原因），并在备注中写明验证结果。若存在关联设计文档，同步将设计文档 `## 流转控制 > 当前责任人` 改为 `QA`；若无设计文档，同步更新需求文档。旧格式归档才回退为将 DEV 列从 ⬜ 更新为 ✅。
