# 工作模式策略

> 本文档是 [SKILL.md](../SKILL.md) 的补充材料，包含四种工作模式的详细执行流程。

## 模式一：设计引导模式（Design-guided）

当有 CTO 的设计文档时使用。按设计文档确定的方向实现，并在实现层补足必要细节。

**特点：**
- 设计文档是实现方向的最高依据，按其中的技术选型、模块归属、关键要素、配置方案和涉及文件逐条落地
- 代码结构、接口定义、数据模型应符合设计意图，同时允许按项目实际约定补足实现细节
- 如果历史设计文档中包含代码片段或函数签名，先判断其是否与项目现状一致；一致则参考实现，不一致则按偏差处理原则反馈

**执行流程：**

1. **通读所有设计文档与视觉稿**，理解全局方案
   - 设计文档（CTO/UX 的 `.md`）是权威参数源
   - UX 规格「视觉稿参考」章节登记的 HTML mockup（如 `design/mockups/final.html`）必须读取，作为视觉参考理解布局/配色/层次
   - 视觉稿与规格文档参数冲突时以规格文档为准（详见下方「UX 视觉稿处理原则」）
2. **核对实现前检查清单**（集成点识别、前置条件、职责拆分），见下方「实现前检查清单」
3. **实现设计文档的实现步骤**，遵循项目约定
3. **按拆分计划执行**，每个任务完成后向用户汇报进展
4. **遇到问题及时反馈**：

   ```
   ⚠️ 设计文档中的 [具体内容] 在实现时发现了问题：
   - 实际情况：[代码中发现了什么]
   - 影响：[对方案的影响]
   - 建议处理方式：[你的建议]

   请确认是否按建议调整，或者回到 CTO 模式重新设计这部分。
   ```

**实现偏差处理原则：**

以下偏差可以直接处理，在代码注释和 commit message 中说明即可：

- 变量命名、代码风格的微调
- 边界条件的补充处理
- 错误处理的具体实现方式
- 设计文档中标注为"可选"的部分的决定

以下偏差必须与用户确认：

- 改变了接口的输入输出结构
- 修改了数据模型（增删字段、改表关系）
- 跳过了设计文档中明确要求的功能点
- 引入了设计文档中没有提到的新依赖

## 模式二：需求引导模式（Requirement-guided）

当只有需求文档（没有设计文档）时使用。基于需求灵活开发。

**特点：**
- 需求文档是目标导向的，不包含具体实现方案
- 你需要自己理解需求、探索代码库、决定实现方式
- 实现前先向用户简要说明实现思路，确认后再动手

**执行流程：**

1. **通读需求文档**，理解每个需求的目标和验收标准
2. **探索项目代码**，理解架构和约定
3. **核对实现前检查清单**（集成点识别、前置条件、职责拆分），见下方「实现前检查清单」
4. **用户确认后按实现计划执行**
5. **每步完成后汇报**，包括改了什么、是否有意外发现

**快速通道（CTO ⏭️ 的简单需求）：** 当 task.json 中某个 task 的 CTO 未参与（简单需求直发 DEV） 时，说明这是 CTO 判定的 L1 简单需求（≤3 个文件、无外部依赖、无技术选型）。对此类需求，可以跳过"先说明实现思路再动手"的步骤，直接执行并汇报结果。

**自主决策范围：**

在没有设计文档的情况下，以下决策你可以自主做出（同样在 commit message 中说明）：

- 函数级别的实现方式
- 代码组织和模块划分
- 具体的错误处理策略
- 测试的编写方式和覆盖范围

以下决策需要与用户确认：

- 是否引入新的依赖或框架
- 需求中未明确的功能细节（如分页策略、排序方式等）
- 对现有代码的大范围重构
- 需求之间的实现优先级（如果需求文档没有标注）

## 模式三：直接开发模式（Direct）

用户直接下达开发指令，没有关联任何文档。最高效、最灵活的模式。

**分流逻辑：**

```
用户指令
  │
  ├─ 目标明确、涉及 ≤2 个职责维度 → 直接执行，不走任务分析
  │
  └─ 涉及 3+ 个职责维度或范围模糊 → 引导用户：
     "这个指令涉及多个职责方向，建议先通过 PM 模式梳理清楚再开发。
      输入 /RDD-PM 进入需求讨论。"
```

**简单指令的执行：**

1. **理解用户指令**，必要时快速探索相关代码
2. **领域识别**：指令涉及非通用工程领域（特定框架深度使用、图形算法、专业协议等）时，按 SKILL.md 中"Skill 辅助"流程查找领域 skill
3. **如果指令明确**——直接动手，改完汇报结果
4. **如果指令模糊**——问一两个关键问题澄清，然后动手
5. **完成后简要说明**改了什么、怎么验证

## 模式四：Bug 修复模式（Bug Fix）

专门面向 bug 修复的诊断型工作流。核心节奏是"先全链路诊断、再统一修复、后验证用户可见结果"——与 Mode 1/2/3 的"先计划、后执行"逻辑根本不同。

**定位**：独立入口时作为主模式；从 Mode 1/2/3 中发现 bug 时作为侧任务（切入后回到原模式断点）。

**触发条件：**

| 触发场景 | 进入方式 | 完成后 |
|----------|---------|--------|
| 用户直接报告 bug | 输入处理路由到 Mode 4 | 等待用户下一步指令 |
| Mode 1/2/3 中发现阻塞当前任务的 bug | 从当前模式切入（侧任务） | 回到原模式断点继续 |
| Mode 1/2/3 中发现不阻塞当前任务的 bug | 记录到 bug register，不切换模式 | 不中断 |
| 修复后验证未通过（用户说"还是不行"） | 自动回到诊断环节 | 迭代 |
| QA 测试失败 | DEV 收到结果后进入 Mode 4 | 修复后重新流转 QA |

**工作流：**

```
Step 1: 理解问题（≤3 分钟，问清楚就过）
  - 用户在做什么操作？期望看到什么？实际看到什么？
  - 有报错信息吗？能稳定复现吗？
  - PM 定义的验收标准是什么？（如有需求文档）

Step 2: 全链路诊断
  │
  ├── 2.0 领域识别（可选）
  │   当 bug 涉及非通用工程领域（WebGL、音频处理、加密协议等）时，
  │   按 SKILL.md 中"Skill 辅助"流程查找领域 skill，辅助诊断阶段理解专业逻辑
  │
  ├── 2.1 定位入口代码
  │   从用户操作 → 找到代码入口点（事件处理/路由/API 调用链起点）
  │
  ├── 2.2 逐层 trace
  │   从入口沿执行路径逐层深入，每一层检查：
  │   - 输入数据格式是否匹配上一层输出？
  │   - 处理逻辑是否覆盖了当前场景？
  │   - 输出数据格式是否符合下一层期望？
  │   - 是否有未处理的边界/异常情况？
  │   → 记录所有发现的问题点（不只看报错信息）
  │
  └── 2.3 汇总诊断结果
      - 列出所有问题点，按执行路径顺序排列
      - 标注问题间的依赖（"A 不修，B 修了也没用"）

Step 3: 呈现诊断结果（多层 bug 时必做）
  单层简单 bug（原因明确、≤2 文件）可跳过，直接进入 Step 4
  向用户报告所有问题层和建议修复方案

Step 4: 统一修复
  基于诊断结果，一次性修复所有问题。不逐层逐次，不留给下一轮。

Step 5: 场景验证
  沿用户报告的完整操作路径验证最终行为。
  验证标准：用户可见的最终结果是否符合预期（不是检查报错是否消失）。
  如有 PM 定义的验收标准，逐条对照。
  │
  ├── 验证通过 → Step 6
  └── 验证未通过 → 回到 Step 2（最多 3 轮）
      3 轮后仍未通过 → 向用户报告全部诊断发现，请求协助

Step 6: 汇报
  - 诊断发现了什么（问题层数、根因）
  - 修了什么（文件、改动摘要）
  - 验证结果（用户可见行为确认）
  - 如有仍在关注的风险点，主动说明
```

**快速通道：** 当 bug 原因一目了然时（typo、缺 import、简单逻辑反转），可跳过 Step 2-3 直接修复。**硬性规则**：快速修复后 Step 5 验证未通过时，**必须**回到 Step 2 执行完整诊断——不允许再走快速通道。

**侧任务执行规则：** 从 Mode 1/2/3 切入时：① 记录断点（一句话说明当前做到哪了）② 执行 Bug 修复流程 ③ 回归检查（修复是否影响当前任务实现计划）④ 恢复原模式断点

**退出边界：** Bug 修复需要新功能 → 建议用户 `/RDD-PM`；涉及架构变更 → 建议用户 `/RDD-CTO`；bug register 累积 3+ 待处理 → 建议用户安排批量修复。

**Bug Register：** 不阻塞当前任务的 bug 记录到 `.rdd/bug-register.md`（格式见 [bug-register-template.md](bug-register-template.md)）。当前任务完成后 DEV 检查 register 待处理项。

## 实现前检查清单

> 以下检查适用于所有工作模式（模式三简单指令可酌情简化）。通读文档后、动手编码前完成。

### 集成点识别与衔接验证

这是实现前最容易遗漏、实现后最易出问题的关注点，分两步：

**实现前 — 识别集成点：**
- 列出本次改动涉及的所有已有模块交互点（新代码与旧代码的衔接处）
- 对照设计文档，确认每个交互点是否已描述集成方式
- 未描述的交互点 → 标记为风险点，向用户标注

**实现后 — 衔接验证：**
- 接口签名是否匹配（参数类型、返回值格式）
- 数据格式是否一致（新旧代码交接的数据结构）
- 调用时序是否正确（注册/初始化/依赖加载顺序）

### 前置条件核对

- 有设计文档时：读取设计文档的"前置条件清单"，状态为 ❌ 的项向用户标注
- 无设计文档时：自行识别关键外部依赖，确认项目中是否已满足
- 未满足的依赖 → 向用户确认处理方式

### 职责拆分维度（可选心智模型）

每个文件/模块只承担一个明确的职责。实现时按以下维度组织：

- **数据层**：数据库模型、Repository、ORM 定义
- **业务层**：Service、核心业务逻辑
- **接口层**：Controller、API 路由、请求处理
- **工具函数**：Utils、Helpers、通用工具
- **配置**：Config、常量定义、环境变量

> 极复杂需求确需并行子代理时，可按此维度划分每个子代理的职责边界，并为每个子代理标注"涉及文件"列表（同一并行组内的任务，涉及文件不能有交集）。

## UX 视觉稿处理原则

UX 设计规格（`{name}-ux.md`）的「视觉稿参考」章节登记了 HTML mockup（通常为 `design/mockups/final.html`）。**这些 mockup 必须读取**，不属"不扫描归档目录"禁令范围（它们由设计规格显式登记，是交接内容的一部分）。

权威关系（源自 `rdd-ux/references/mockup-generation.md`）：

- **规格文档为权威参数源**：三层 Token、组件规格、交互时序等具体值以 `{name}-ux.md` 为准
- **mockup 为视觉参考**：用于理解整体视觉效果（布局比例、配色氛围、视觉层次、信息密度），弥补纯文字规格难以传达的"用起来什么感觉"
- **mockup 无法展示的部分**（状态流转、动画时序、交互逻辑）一律以规格文档的交互规格为准

冲突处理：

- mockup 与规格文档的具体参数冲突时（如间距、色值有出入），**以规格文档为准**
- 若 mockup 的视觉效果明显优于规格文档的参数，属于设计偏差，按「实现偏差处理原则」反馈用户或 UX（不擅自以 mockup 覆盖规格）
- mockup 路径在规格中未登记或文件缺失 → 按 handoff 依赖缺失处理，向用户确认
