# QA 流转与提交门禁

> 本文档是 [SKILL.md](../SKILL.md) 的补充材料，描述开发完成后 QA 的流转与提交门禁流程。
> QA 作为**独立角色会话**进入（非 DEV 子 agent），完整持有功能验收 + 代码质量检查 + 提交门禁三项职责。

## 触发 QA

**本条需求**开发完成并自测通过后，按 `rdd-engine/references/transition-guide.md` 的**上游协议 4 步硬流程**推进路由至 QA：

1. 推进 task.json 路由：`rdd-flow advance` 将对应行 `currentOwners` 改为 QA，同步需求/设计文档 `## 流转控制 > 当前责任人`
2. 运行 `rdd-flow next -Format markdown`，展示可流转角色
3. 推荐 QA 并请求用户确认：

   ```
   建议进入 QA 进行验证验收（功能测试 + 代码质量检查 + 提交门禁），有 N 个待处理任务。
   是否确认进入？
   ```

4. 用户确认后生成交接包，按部署模式引导：
   - **self-driven**：`start-role.cmd -Role QA -TaskId <n>` 自动开新会话窗口
   - **app-driven**：生成 packet，等待应用层切换

> 不再通过 Task 工具启动 QA 子 agent。QA 需执行代码质量检查与 git 提交，必须作为独立角色会话持有完整权限。

**用户拒绝时：**

> 接下来你可以：
> - 输入 **/RDD-QA** 手动启动验证
> - 如果还有需要调整的地方，我们继续

## QA 验证模式职责

QA 进入后依次完成（详见 `rdd-qa/references/qa-workflow.md` 第四~七步）：

| 步骤 | 职责 | 不通过处理 |
|------|------|-----------|
| 功能测试 | 运行测试 + 验收结果 | reopen 回 DEV |
| 代码质量检查 | 硬性项（编译/lint/量化规范）+ 软性备忘 | 硬性不通过 → reopen |
| 执行提交 | 功能+质量双通过 → git commit | 不提交，直接 reopen |
| 归档 | 双写归档 + 标记完成 | — |

## 重入分支（本条闭环后）

本条需求 QA 流转后，按 `next` 输出决定下一步：

- **DEV 仍有待办**（`next` 显示 DEV `taskCount > 0`）→ 推荐重入 DEV（新会话）实现下一条。可与本条 QA 验证并行：本条交 QA 验证的同时，新会话继续实现下一条
- **DEV 已清空** → 全部需求已实现并闭环，进入 EVAL

## 标记需求完成

QA 在验证模式下完成提交后，由 **QA** 标记任务闭环：

1. 调用 `rdd-flow complete` 标记任务闭环
2. 同步各需求文档 `## 流转控制 > 当前责任人` 为 `已完成`（QA 完成，两处须一致）
3. 后续若发现问题，将 `已完成` 改回对应角色（如 `DEV`）即可重启流转

> `已完成` 是唯一终端信号：`rdd-flow.ps1` 不会把它匹配给任何角色，`next`/`start` 天然跳过已闭环需求。EVAL 通过它判定哪些需求可做完整评价。
> DEV 不再执行标记完成——提交与标记闭环统一由 QA 在验证模式下完成。

## 触发 EVAL

**全部需求都已标记为 `已完成`** 后（QA 逐条通过提交的累积结果，或用户跳过 QA 时），才进入验收评价：

> 归档内全部需求已实现并闭环。是否启动验收评价？（是 / 否）

**用户确认后：**

> 输入 **/RDD-EVAL** 进入验收评价模式，对本次需求的各角色产出和协同效率做回顾性审视。

> 流水线模式下：QA 逐条通过（含提交）并逐条标记 `已完成`，EVAL 只在全部需求都到达 `已完成` 时触发——不因单条完成而过早触发评价。

**用户拒绝时：**

> 接下来你可以：
> - 输入 **/RDD-EVAL** 手动启动评价
> - 如果还有需要调整的地方，我们继续
