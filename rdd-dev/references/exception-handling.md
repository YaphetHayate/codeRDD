# 异常处理

> 本文档是 [SKILL.md](../SKILL.md) 的补充材料，包含四种异常场景的处理指南。

## 发现设计文档不可行

在实现过程中发现 CTO/UX 的设计文档与代码实际情况不符或技术上无法实现时，执行正式驳回协议：

1. **暂停该步骤的实现**
2. **记录具体差异**：设计文档说 X，实际代码/技术限制是 Y
3. **评估影响**：
   - 小偏差（命名/风格微调、小范围实现方式调整）→ DEV 直接处理，在 commit message 中说明
   - 大偏差（接口结构性变更、技术方案不可行、依赖冲突）→ 执行驳回协议
4. **执行驳回协议**（加载 `rdd-engine/references/rejection-protocol.md`）：
   - 在设计文档的 `## 驳回记录` 新增驳回记录行
   - 将设计文档的 `当前责任人` 改为 CTO（或 UX）
   - 更新 `task.md` 路由总览
   - 告知用户驳回原因

## 发现需求有遗漏或不当

实现过程中发现需求文档不完整或存在误判：

1. **继续实现已明确的部分**
2. **将遗漏/不当点整理成清单**
3. **向用户报告**：

   > 实现过程中发现了几个需求文档没有覆盖的场景：
   > 1. [场景 A] — 我的处理方式：[...]
   > 2. [场景 B] — 需要你确认：[...]
   >
   > 如果场景比较多或需求本身存在方向性问题，可发起正式驳回：
   > 在需求文档的 `## 驳回记录` 中记录驳回，将 `当前责任人` 改回 PM

## 子 agent 产出质量不达标

实现过程中如使用了并行子代理协助（如复杂需求拆分委派），审查子代理结果时发现质量问题：

1. **记录具体问题**：哪些文件、什么问题
2. **评估严重程度**：
   - 小问题（风格、遗漏）：DEV 直接修复
   - 大问题（实现偏离、逻辑错误）：整理问题清单，决定是重新启动子 agent 还是自己修复
3. **修复后重新验证**：确保修复没有引入新问题

## 实现卡住了

遇到技术难点，尝试了合理的方式仍然无法解决：

1. **判断卡住的原因**：
   - 如果是已有功能的 bug 导致卡住（非设计/需求问题）：
     - 阻塞当前任务 → 进入 **Bug 修复模式**（侧任务），按 Mode 4 的诊断→修复→验证流程处理
     - 不阻塞当前任务 → 记录到 `bug-register.md`，继续当前任务
   - 如果是设计/需求/其他原因 → 继续下面的步骤
2. **把已经尝试过的方式和结果整理清楚**
3. **向用户坦诚说明**
4. **建议**：
   - 如果是设计层面的问题 → 执行正式驳回协议，将设计文档打回 CTO/UX
   - 如果是需求不清晰 → 执行正式驳回协议，将需求文档打回 PM
   - 如果是需要用户补充的技术信息 → 直接问用户
